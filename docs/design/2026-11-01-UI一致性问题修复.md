## 一、诊断方法：离屏探针加字号档

上一轮的截图链路只出「当前状态」，无法回答「改了设置之后哪些没跟着变」。
本次给 `uat62_page_shots_probe` 加了 `--font-scale`，并且**在每页渲染中途切档**：

```
每页：① 按当前档渲染 24 帧 → ② setFontScale(目标档) → ③ 再渲染 24 帧 → 出图
```

关键在②这一步。**只在启动时直接按目标档渲染会得出错误结论**——那测的是「首次渲染」，
而真机是「同一进程内改设置」，runtime 会按 id 复用旧实例。两条路径的渲染结果可能不同。

配套工具（/tmp）：
- `imgdiff.py` — 两图逐像素差分（亮=有变化，暗红=未变化）
- `pngcrop.py` / `pnglib.py` — 裁剪放大 / 像素扫描定位几何

**差分图有个局限**：文字变大后新旧笔画大量重叠，像素差分判不出变化。判断「文字是否变大」
必须放大原图目测，不能只看差分图。

## 二、问题①：按钮圆角七档并存

### 现状盘点（改动前）

全站 `components::button`（EUI）66 处 + `ui_kit::button`（自研）46 处 + 约 39 处自绘可点击矩形，
圆角共 **七档**：8 / 10 / 6 / 14 / 16 / 11 px，加 EUI 按 level 自动取的 16(overlay) / 8(control)。

根因是两套按钮组件并存，各自一套圆角口径：
- `ui_kit::button` → `t.sizes.radius`（10px）
- `components::button` → `tokens.metrics.radius.overlay`(16) / `.control`(8)

### 规范

写入 `src/ui_kit/button.h`：

| 类别 | 圆角 |
|---|---|
| 填充按钮（高 > 28） | `t.sizes.radius`（10px） |
| 图标按钮（高 ≤ 28 的方形小按钮） | `t.sizes.radiusSmall`（6px） |
| 药丸（状态 chip / 分段控件） | `t.sizes.radiusPill` |

### 落点

- **`core::theme::componentTokensWeChat`** — 覆写 `metrics.radius.overlay` 与 `.control` 为
  `t.sizes.radius`，EUI 按钮的默认圆角随之统一，66 处调用**零改动**。
  DevDesk 未使用 colorpicker / datepicker / timepicker / segmented / tabs（这几个也读这两个槽位），
  覆写只影响 button 与 toast，反而一并对齐。
- **36 处显式 `.radius(...)`** 按上表归类改写（28 处 `8.0f` → 10px、3 处 `14.0f` → 10px、
  1 处 `16.0f` → 10px、5 处图标按钮 → 6px）。
- **5 处自绘可点击元素** 同步归类：schedule 历史行卡 / md 笔记 tab 底块 / wallpaper 卡片 /
  todo 卡片底 → 10px；md 笔记 tab 的 24×24 图标按钮 → 6px。

改后全站 `.radius()` 分布：`radius` 88 / `radiusSmall` 41 / `radiusLarge` 29 / `radiusPill` 24，
剩余字面量均为**非可点击**的卡片、图标与进度条。

## 三、问题②：文本不响应字号缩放

### 根因：字号来源分四类，其中三类不跟随全局档

`core::theme::applyFontScale` 只缩放 `SizeTokens.fontSize*` 七个字段。实际写法的分布：

| 写法 | 处数 | 是否响应 | 处理 |
|---|---|---|---|
| `t.sizes.fontSize*` | 227 | 响应（token 已乘） | — |
| `core::theme::scaled(<字面量>)` | 221 | 响应 | — |
| `fs(...)` / `mdEditorFontSize()` 等模块内助手 | 159 | 响应 | — |
| **裸字面量**（`fontSize(13.0f)`） | 5 | **不响应** | 包 `scaled()` |
| **`t.sizes.fontSizeWeChat`** | 8 | **不响应** | 纳入 `applyFontScale` |
| **EUI `metrics.typography.*`** | 66 个按钮 + 57 个输入框 | **不响应** | 纳入 `componentTokensWeChat` |
| **`ui_kit` 组件常量** | wtab / dialog_form / empty_state / selection_bar / light_toast | **不响应** | 组件内包 `scaled()` |

逐条对应的用户观察：

- **侧边栏菜单文本** → 用 `t.sizes.fontSizeWeChat`，而该 token 漏在 `applyFontScale` 列表外
- **部分按钮文本** → EUI `components::button` 的文字取自 `metrics.typography.*`，完全不接 DevDesk 的缩放体系
- **设置页 tab 文本** → `ui_kit::wtab` 的字号常量 `kWtabFontSize` 未包 `scaled()`
- **搜索框占位文本** → 输入框字号虽已包 `scaled()`，但**输入框高度与内边距是固定值**，
  字号放大后文字被框裁掉（探针实测：130% 档下「搜索笔记…」右端被截断），
  用户看到的是「字没变 / 变坏了」而不是「字变大了」

### 落点

1. `core/theme.cpp` — `applyFontScale` 补 `fontSizeWeChat`
2. `core/component_theme.h` — EUI `metrics.typography` 全部 16 个字号槽位乘 `fontScale()`
   （lineGap 属间距不缩放，与 DevDesk「只缩字号、不动间距」策略一致）
3. `ui_kit/wtab.cpp`、`dialog_form.cpp`、`empty_state.cpp`、`selection_bar.cpp`、`light_toast.cpp`
   — 组件内字号统一包 `core::theme::scaled()`
4. `module_schedule/channels/fullscreen_channel.cpp`（2 处）、
   `module_release/release_list_ui.cpp`（3 处）— 裸字面量包 `scaled()`
5. `module_schedule/schedule_ui_edit.cpp` — 11 处输入框补 `.fontSize(t.sizes.fontSizeBody)`
   （此前未设字号，取 EUI 默认 17px，与全站输入框的 14px 不一致）

### 连带回归：markdown 预览字号双乘

EUI typography 槽位纳入缩放后，markdown 的 `scaledPreviewStyle` 里
`style.h1Size *= k` 变成双乘（30 → 39 → 50.7）。
修正：字号族（bodySize / h1~h3 / codeSize / bodyLineHeight）取自已缩放的 typography，不再乘；
仅 `blockGap`（取自 spacing，未缩放）继续乘 —— 它是 syncMap 缓存键项，不乘则切档时键不变、
块高备忘不重建，新字号配旧几何会裁字。

### 遗留：输入框固定几何

字号放到 130% 后，输入框的固定高度/内边距会把文字裁掉（搜索框占位文本已实测到）。
本轮只统一了字号口径，未改输入框几何——改高度会牵动 57 处输入框与所在容器的布局，
建议作为独立工单：输入框高度随字号档线性缩放（14px 字号 → 40px 高，1.3 档 → 48px）。

## 四、问题③：滑块手柄与进度条分离

### 根因

EUI runtime 的手柄位移是**累加**语义：

```cpp
// EUI-NEO/core/runtime/runtime_state_bindings.h
const float centered = clamp(width * value - knobSize * 0.5f, 0, travel);
transform.translate.x += centered;   // 累加到 compose 期的 position 上
```

官方 `components::slider` 的手柄恰好画在 **x = 0**，靠 runtime 平移到达目标位置。
但 `ui_kit::slider` 又在 compose 期给了初值 `x = value * (w - knobSize)` —— 两段位移叠加，
手柄被推到 **2× 位置**。100% 档实测：绿色条右端在 x=267，手柄完全跑出画面外。

### 修法

`src/ui_kit/slider.cpp` — 手柄 compose 期 x 改为 0，位移全部交给 runtime transform，
与 EUI 官方组件同契约。

改后 100% 档实测：手柄圆心落在 263，绿色条右端 250 + 手柄半径 8 = 258 → 贴合，
且手柄中心恰好等于 fill 右缘（fill 宽 = w × value）。

### 测试口径同步

`tests/test_modules/test_ui_kit_slider.cpp` 原断言「compose 期 handle.x = value*(w-knob)」——
那是旧的错误契约。改为断言 compose 期 x 恒为 0，并补 fill 宽度与手柄运行时左缘的几何判据。

## 六、沉淀：字号与圆角的单一来源

写进 `.workbuddy/memory/MEMORY.md`，后续 UI 改动按此来：

**字号只有三条路**（都必须跟随全局档）
1. `t.sizes.fontSize*` token —— 已在 `applyFontScale` 内缩放，**不可再包 `scaled()`**（双乘）
2. `core::theme::scaled(<字面量>)` —— 字面量走这条
3. EUI 组件字号 —— 走 `componentTokensWeChat`，其 typography 槽位已缩放

**圆角只有三档**：填充按钮 10px / 图标按钮 6px / 药丸。散落的字面量 radius 是遗留债。

**新增工具能力**：`uat62_page_shots_probe --font-scale 1.3` 出「改设置后」的对照图，
配合 `/tmp/imgdiff.py` 做差分。这是以后验证「设置项是否真的生效」的标准手段。
