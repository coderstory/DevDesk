# 11 未来趋势与技术押注（2027-2028 推演）

> 产出日期：2026-10-21 | 调研方式：cs-web-fetch 抓取 16 次（Bing 搜索 + 目标站点正文提取）
> 与 06-发展趋势总结的分工：06 是当下横评（七大产品谁在做什么）；本报告只看轨迹与推演，回答「刚开发完会不会就过时」。
> **重要前提**：以下推演基于截至 2026-10-21 的公开信息与产品发布轨迹；所有「将会」「预计」「可能」均为趋势外推，非确定性预测。

## 一、模型能力轨迹

### 1.1 上下文窗口持续扩大对「任务记忆机制」的冲击

**轨迹**：2025 年 Gemini 率先推出 2M token 上下文窗口，到 2026 年中主流模型普遍进入 200K-1M 区间。推理侧上下文成本同步下降（Claude Opus 5.5 声称比前代便宜 40%）。训练数据的截止时间窗口也在缩小（模型更新周期从季度级缩短到月级）。

**对任务记忆的冲击**：
- 短记忆（单次会话内的任务状态、工具调用历史）正在被"直接塞进上下文"替代，不再需要精巧的 memory 摘要/压缩机制。Claude Code 的 compaction 机制就是这条线的产物——模型消化得动、成本降得够低，就不该让 agent 自己维护记忆。
- 但跨会话记忆（项目进展、决策记录、个人偏好）仍然是 agent 应用的核心差异化点。MCP Memory Server（官方维护的参考实现之一）证明了这条线的持续需求——记忆不是"记不住"而是"跨会话记得住"。
- **结论**：短记忆（单会话内）会被上下文吞食；长记忆（跨会话/跨项目）仍是刚需，但形态从"agent 自己维护"转向"协议化（如 MCP Memory）外部存储"。

**对我们的建议**：DevDesk 的任务记忆机制（事件触发、状态持久化）在短记忆侧价值会逐年缩水；长记忆侧如果仍用自建方案而非 MCP Memory 协议对接，两年后会是补洞项。建议 C 期优先评估 MCP Memory Server 接入，而不是扩展现有自建记忆。

### 1.2 推理成本下降后 agent 用量与形态的变化

**轨迹**：2025 年 agent 调用还受限于 token 成本（一次复杂任务烧掉几十万 token），到 2026 年成本已不再是主要约束。国内 Agent 产品在 2026 年爆发——信通院数据称国内 AI 智能体服务商突破 300 家（截至 2026 年 2 月）。"执行"正在取代"对话"成为核心卖点（火山引擎 2026 年 8 月综述原文结论）。

**形态变化**：
- Agent 从「一次一问」的聊天模式进化为「持续运行」的后台模式——QwenWork 的 7x24 云端长任务、Kimi Work 的长循环、Coze 3.0 的多 Agent 协作空间
- 单 Agent 拆子 Agent 并行推进成为标配（TRAE Work 的"多子 Agent 分工"、字节 Coze 3.0 的多人多 Agent 协作）
- Agent 数量激增但质量分层严重，"有的已经能稳定跑完多步任务，有的还在特定场景内测"

**对我们的建议**：DevDesk 选型「桌面壳 + agent loop + 工具注册」在形态上已经对了——2026 年国内桌面 Agent 是增长最猛的品类。但 D 期「自主性（重试/验收自评/自唤醒）」要小心过度追求全自主——目前所有产品离真正无人值守还有距离，先押「可监控的半自主」比「假全自主」更保值。

### 1.3 Computer-use 会不会动摇「工具调用」？

**轨迹**：computer-use（模型直接操控桌面/浏览器界面，不通过 API）在 2026 年集中出现：
- Anthropic: Claude Cowork（macOS 版，2026-10-13 文档已有中文安装指南）
- 智谱：AutoGLM（手机端 GUI 操作，看懂屏幕+点击+滑动+输入）
- DSH Desktop：开源桌面客户端，宣称"解锁 Computer Use 等隐藏能力"
- 华为鸿蒙小艺：系统级跨应用执行

**互补而非替代**：computer-use 解决的是"没有 API 的系统/应用"——老旧 ERP、封闭 SaaS、个人手机 App。工具调用（API/MCP）面向有标准接口的系统——代码仓库、数据库、CI/CD、文档系统。两条线不是二选一，而是覆盖互补的两类目标。

**结论**：工具调用不会被 computer-use 替代，但 agent 需要两条腿都站住。DevDesk 的核心定位是"开发者工具中枢"——目标系统（Git、文件、构建、CI）全部有 API，工具调用是更高效的路径。computer-use 作为补充能力有价值，但不应该成为主线。

## 二、协议标准化轨迹

### 2.1 MCP 全面标准化后自定义工具接口的生存空间

**MCP 现状（2026-10 证据）**：
- MCP 已是跨客户端的事实标准：Claude Code、Cursor、Codex 三家均原生支持，配置文件格式不同但协议相同（IMAI 2026 年 MCP 推荐文章实证）
- 配置文件 `.mcp.json` 可随仓库提交（project scope），全团队共享
- 官方参考实现已于 2025 年 5 月归档（server-github、server-postgres 等），仍在维护的仅剩 7 个：Everything、Fetch、Filesystem、Git、Memory、Sequential Thinking、Time
- 社区 MCP 服务器生态繁荣：Context7（最新文档）、Playwright MCP（浏览器验证）、Chrome DevTools MCP（前端调试）、DBHub（数据库查询）等
- ModelScope（中国魔搭社区）也上线了 MCP 专区

**推演**：MCP 正在走 HTTP 的路线——从一个公司的开放协议变成跨生态的基础设施。2027-2028 年预计：
- MCP 会进入 IETF/W3C 级标准化进程（目前还是 Anthropic 主导）
- 自定义工具接口如果不兼容 MCP，接入成本会越来越高（每个新客户端都要单独适配）
- 「自建工具注册 + MCP 适配层」是合理的保留——内核是自己的，但对外只暴露 MCP 协议

**对我们的建议**：C 期规划中「自建工具注册」vs「MCP 客户端」不应是二选一，而是分层——内核维持自己的工具注册表（单一注册源），对外暴露 MCP 协议兼容层。这样既保有了自有生态的灵活性，又不会被 MCP 标准化浪潮边缘化。

### 2.2 Agent 互操作协议会不会让自建 harness 贬值

**轨迹**：Agent-to-Agent 协议（Google A2A 等）在 2026 年处于早期阶段，远不如 MCP 成熟。公开信息有限（多次搜索关键词命中率极低），但概念方向明确：多个 agent 之间需要标准化通信协议来协作。

**「桌面壳 + 可插拔 agent」会不会成为标准形态**：
- 2026 年国内桌面 Agent 已经是独立执行体（阶跃 AI 桌面版、QwenWork、豆包专业版），每个产品自己闭环，没有统一的 agent 间通信
- 但 Coze 3.0 的"多人多 Agent 协作"、TRAE Work 的"多子 Agent 分工"暗示了趋势——agent 之间需要交互
- 如果 A2A 标准化（类似 MCP 之于工具连接），自建 harness 的 agent loop 可能会被标准 agent 运行时替代

**结论**：A2A 标准化是两年后的威胁，不是今天的。DevDesk 的「agent loop + 工具注册 + 事件触发」如果要在 2028 年仍有竞争力，需要预留 agent 互操作接口。但当下不应该为此推迟开发——A2A 协议尚未定型，现在"对接"等于对接空气。

## 三、开发工作流轨迹

### 3.1 PRD 到 MR 流水线产品化后，人审环节往哪收缩

**现状**：2026 年 AI 编码 agent（Claude Code、Cursor、Codex、TRAE Work 等）已能完成从需求理解到代码生成的完整链路。火山引擎综述中"执行正在取代对话成为核心卖点"同样适用于编码领域——agent 不再是提建议，而是直接改代码、提 MR。

**人审收缩方向**：
- **逐行 diff 审 → 政策/架构/验收审**：当 80%+ 代码由 AI 生成时，逐行审查失去了其原有的"发现低级错误"价值（AI 不犯低级错误，但会犯高级错误——架构方向错、安全边界错、业务理解错）
- 人审的核心价值从"代码是否正确"变为"方向是否对、安全边界是否守住、业务逻辑是否准确"
- 代码审查看似被削弱，实则需要更高认知密度——不是审查每一行，而是审查关键决策

**对我们的建议**：E 期「需求文档→合并请求流水线（MR 留人审）」的判断是对的——MR 环节人审不应该被自动化掉。但人审口径要校准：不是审"这行代码有没有 off-by-one"，而是审"这个设计选择在业务流程上是否成立"。

### 3.2 AI 生成代码占比上升对代码审查这件事的意义影响

- 当 AI 生成代码占比超过某个临界点（50%？70%？），「代码审查」这件事本身从"质量把关"变为"意图对齐审查"——检查 AI 是否理解了正确的事情，而不是检查实现细节是否有 bug
- AI 审 AI（agent 审 agent 提交的代码）会成为标配——2026 年已有产品（Claude Code 的 code-review skill、Cursor 的 inline review）
- 但"最终人审"不会被替代——责任归属在法律和业务层面无法转移给 AI

## 四、桌面/本地 agent 轨迹

### 4.1 操作系统级 agent 集成会不会吞掉桌面 agent 应用

**证据**：2026 年操作系统级 agent 正在密集上线：
- Windows 11 26H2（2026 年 9 月推送）深度集成 Copilot
- 华为鸿蒙小艺（HMAF）：系统级跨应用执行
- 小米 miClaw：澎湃 OS 内跨设备调度（手机+车+家居）
- 联想天禧：PC 端系统级 Agent，本地部署个人记忆
- Apple Intelligence：macOS/iOS 深度集成

**推演**：OS 级 agent 的优势是权限高（能做的事多）、入口统一（用户不用额外装软件）；劣势是通用（不可能针对开发者场景做深度优化）、封闭（锁定生态）。

**结论**：OS 级 agent 会吃掉"通用助手"市场（帮我订机票、整理桌面、设置闹钟），但不会吃掉"专业工具"市场（帮我重构这个模块、排查这条日志链路、审这个 MR）。DevDesk 定位是开发者工具中枢，与 OS 级 agent 是上下游关系（OS agent 做通用的，DevDesk 做专业的），不是竞争关系。

### 4.2 隐私/本地模型会不会成分水岭

**轨迹**：2026 年国内在隐私/本地部署方向有明确的政策推力：
- 信创（信息技术应用创新）要求政企场景数据不出域
- OpenOcta 八爪鱼定位"信创友好的开源桌面级 Agent 框架，支持全内网离线部署"
- Apple Intelligence 的核心卖点是"本地处理优先，云端仅做补充"

**推演**：隐私不会让每个用户都跑本地模型（硬件门槛太高），但"本地数据处理 + 云端推理"会成为主流折中方案。这意味着：
- Agent 产品的数据流设计需要能切分"什么留在本地、什么上云"
- 纯云端 agent 在政企市场会被拒
- 「本地模型推理」作为可选项（而非默认项）能覆盖两类市场

**对我们的建议**：DevDesk 的 C++ 桌面端定位在隐私维度有天然优势（本地数据不需要上云）。但 D 期如果引入云端自主性（自唤醒等），需要明确数据边界——哪些数据永远不离开本机。

### 4.3 个人数据主权方向的信号

- 联想天禧的"本地部署个人记忆"（用户数据不离开设备）
- MCP Memory Server 的知识图谱式长期记忆也是本地运行的
- 趋势：用户的个人数据（偏好、历史、决策记录）正从"存在服务端"回流到"存在本地"

**结论**：个人数据主权是 desktop agent 相比 cloud agent 的持久竞争优势。DevDesk 作为本地应用，在这条线上已经领先。

## 五、A 到 E 逐期保值性审查

| 路线图分期 | 长期资产（怎么变都有用） | 过时风险（可能落地即旧） | 该加的对冲（现在就埋） |
|-----------|----------------------|----------------------|-------------------|
| **A 收口**<br>文件+搜索+GitLab 只读 | 工具注册表（单一注册源）是 MCP 适配层的底座；文件/Git 操作是所有 agent 的通用需求 | 自建搜索若不做语义化升级，会被 MCP + 向量检索方案替代 | 工具接口预留 MCP 协议适配缝——每个工具定义不写死调用协议，而是通过 ProtocolAdapter 层抽象 |
| **B 对接**<br>技能导入器 | 可插拔架构本身是长期资产——无论 MCP 还是 A2P 都是"插什么"的问题 | 自建技能格式如果与 MCP Server 定义不兼容，会导致生态隔离 | 技能定义格式对标 MCP Server manifest——tool name、description、input schema 三字段一一对应 |
| **C 扩展**<br>MCP 客户端评估 | MCP 客户端本身就是对接标准化趋势的押注 | 「自建工具注册」如果不加 MCP 适配层，会在 MCP 成为 IETF 标准后被边缘化 | 工具注册内核保持，对外暴露 MCP 协议层；不要用 MCP 替代自建注册（内核要单一注册源），而是加一层协议转换 |
| **D 自主性**<br>重试/验收自评/自唤醒 | agent loop 与事件触发机制是任何自主性的基础 | 「完全自主」是两年内不可能稳定达成的目标，过早追求会浪费资源 | 从「可监控的半自主」做起——agent 的每个自主决策都有 trace + 可回滚；自唤醒能力加数据边界守卫 |
| **E 流水线**<br>需求文档→MR | MR 留人审的设计判断正确；流水线的编排引擎长期保值 | 如果 PRD 解析、代码生成等环节完全自建而不对接 Claude Code/Cursor/Codex 等成熟 agent，会被"别人已经做好了"替代 | 流水线中的各环节设计为可替换——代码生成可以是 DevDesk agent，也可以是 Claude Code via MCP；PRD 解析可以是自建也可以是外部 skill |

**总体判断**：路线图方向正确，没有「全期报废」的致命风险。最大的过时风险集中在协议层——C 期如果不做 MCP 适配（或不以"协议可换缝"标准加固自建工具层），会在 2027-2028 年 MCP 标准化浪潮中被迫返工。其他各期在架构正确的前提下，功能实现早晚不会影响长期保值性。

## 六、设计原则建议

1. **工具注册表 = 单一真相源，MCP = 对外口音**。内核维持自建注册表（单一注册源，插件状态一处管理），对外统一通过 MCP 协议暴露。不在内核里同时维护两套工具定义体系。

2. **MCP 适配缝现在就埋，不要等 C 期**。每个工具定义的结构体预留 `protocol` 字段（初始值 `"native"`），序列化/反序列化走独立的 ProtocolAdapter。现在代价是一天的工作量，C 期返工的代价是重构整个工具层。

3. **不要自建记忆系统**。已有的任务记忆机制维持现状不动，但不扩展。跨会话记忆直接对接 MCP Memory Server（官方维护的参考实现）。自建记忆在 2027 年之后没有存在理由。

4. **agent loop 与事件触发是核心资产，不要换成外部运行时**。MCP 标准化了工具连接，A2A 可能会标准化 agent 间通信，但 agent 自己的决策循环、状态管理、事件响应是产品的差异化内核——这是 DevDesk 的"灵魂"，不能用别人的框架替代。

5. **computer-use 是补充能力，不是主线**。DevDesk 的目标系统（Git、文件、构建、CI）全部有 API。computer-use 只用于"没有 API 的边缘场景"（如操作老旧 IDE、调试 GUI 工具），不需要作为核心能力投入。

6. **「可监控的半自主」比「假全自主」更保值**。D 期的自主性目标应该校准为：agent 的所有自主行为有 trace（可追溯决策依据）、有回滚（可撤销错误操作）、有人审钩子（关键操作前等待确认）。追求"完全无人值守"是 2028 年之后的事。

7. **个人数据主权 = 桌面 agent 的防火墙**。所有用户数据（偏好、历史、决策记录、项目上下文）默认本地存储，云端访问必须显式授权。这条线在 OS 级 agent 和 cloud coding agent 面前是持久的差异化优势。

8. **不要自建 PRD 解析器、代码审查引擎、技能市场**。这些是"别人已经做好的"能力——PRD 解析有 Claude、代码审查有 code-review skill/MCP、技能市场有 MCP World。DevDesk 的价值是编排和集成，不是重新发明这些组件。E 期流水线中的每个环节都设计为可替换的外部能力接入点。
