### 第3章 人的操作流程：用户从头到尾做什么

**一句话使命**：单独成章，配完整流程图，讲清楚一个不写代码、不读代码的用户在 DevDesk 开发中的真实角色与操作节奏——提需求、关键节点拍板、等结果、验收点验、反馈问题。

**要点清单**：
1. **分工前提（先把这个交代清楚）**：代码对用户不可见，用户不写任何一行代码；用户的工作面 = 文档（中文说明）+ 中文日志 + 截屏 + 测试报告 + 可运行的软件包（Windows exe / macOS app）；所有代码层面的决策（架构、实现方式、bug 修复方案）由 AI 自主完成，用户只在需求与验收节点介入。
2. **用户的实际操作界面**：不是 IDE、不是代码编辑器——是 Claude Code 的对话窗口（打字提需求、看报告）、文件管理器（看截图、装软件包）、DevDesk 应用本身（真机点验）。逐一说明每个界面上用户做什么、看到什么。
3. **用户的操作节奏（配流程图）**：
   - 阶段 A「提需求/给方向」：用户用自然语言描述想做什么——可能是一句话（"把设置页放到侧边栏"），可能是一段方向性描述（"智能中枢的特化三轴是..."）。
   - 阶段 B「关键节点拍板」：AI 拿出方案（设计文档、选择题）后，用户从中选定方向。不是每个细节都问——只问不可逆的、影响方向的决策。
   - 阶段 C「等待执行」：AI 自主派子任务、写代码、跑测试、截屏——用户不需要守着，回来的时候结果已经在桌面。
   - 阶段 D「真机验收点验」：用户拿到安装包，在自己的电脑上实际使用——点按钮、拖拽卡片、搜索文档——用"人眼+人手"验证"看起来对不对、用起来顺不顺"。这是代码测试无法替代的最后一道关。
   - 阶段 E「反馈问题」：用户用自然语言描述遇到的问题（"这个按钮为什么没反应""这块区域看起来是空白""字体太小了"），不用定位代码——AI 自己去排查、修复、再交付。
   - 循环：E 反馈 → AI 排查修复 → D 真机复验 → 直到通过。
4. **用户"不做什么"的清单**（同样重要）：不看代码、不改代码、不跑编译、不定位 bug、不写测试、不管理 git 分支——这些全部是 AI 的活。这份"不做清单"本身就定义了人机分工的边界。
5. **纪实案例**：选 2 个真实交互片段（如"UAT6 用户反馈弹窗按钮出框 → AI 排查 → 修复 → 用户复验通过"），用讲故事的方式还原用户视角的真实体验。

### 第4章 AI 的执行流程：任务的六阶段流水线

**一句话使命**：单独成章，配完整时序图，讲清楚一个任务从"收到用户需求"到"交付安装包"在 AI 系统内部经过的全部步骤，以及每一步的纪律为什么存在。

**要点清单**：
1. **主会话"只编排不实施"的铁律**：主 AI 会话不写代码——它只做需求梳理、任务拆分、派子任务、审计结果、合并代码。为什么这么设计？讲清楚"既写代码又审代码 = 失去第二方视角"这个逻辑。
2. **六阶段流水线（逐个阶段讲清"做什么、为什么、不过怎么办"）**：
   - **阶段 1 实现**：子任务在 worktree 隔离分支上完成改动，原子提交。要求 commit sha + 文件清单 + 改动说明，三者缺一不算完成。
   - **阶段 2 独立审计**（强制关卡）：另派一个只读子任务做审计——审计者不得是实现者本人。按六个维度逐条核查（正确性、回归面、平台对称性、静默失败面、测试有效性、文档口径），产出结构化 findings 文件。
   - **阶段 3 按审计修**：逐条处理 findings——修，或明确写"不修并附理由"。未处置完不得进测试。
   - **阶段 4 测试**（审计通过后才准跑）：定向单测 + 真窗口探针 + 真网 live 测试 + 真机截图验证。交付前三问（存量数据升级验过吗？真实网关验过吗？目标平台真机验过吗？）。
   - **阶段 5 串行合并与发布**：功能分支合并进集成分支，合并后在集成分支上重建 + 覆盖安装到 /Applications。没合并 = 没交付。合并必须串行（多线同时合会撞锁）。
   - **阶段 6 真机验收**：用户在自己的机器上点验。涉及视觉/交互的改动，交付后由用户亲眼验证——代码测试绿不等于"看起来对"。
3. **调度纪律（六阶段之外的系统约束）**：
   - 子任务并发上限 8 个，但编译/测试槽只有 1 个（多线同时编互相拖慢）。
   - 同文件同时间只有一个写者。
   - worktree 用完即清（合并后立即删除隔离目录，禁止残留）。
   - 构建超时上限 3 分钟——长构建放后台跑。
4. **为什么这么重？**：每一个阶段、每一条纪律都是真实事故"撞"出来的——不是设计偏好。本章末尾附一张速查表：每条纪律对应的事故编号（指引到第5章对应条目）。

### 第5章 预防机制：用什么解决了什么问题

**一句话使命**：按"问题 → 机制 → 真实事故实证"三段式，逐条讲清楚 DevDesk 开发中最核心的预防性机制——每条机制都来自至少一个真实事故的教训，不是纸上谈兵。

**要点清单**：
**写作指引**：本章程式——17 个条目不摊薄：选 10-12 条最有代表性的写完整"问题→机制→实证"三段式，其余条目并入表 5-1（一句机制+一句事故概要），正文不展开。

本章按**预防的对象**分节，每节下有若干条目，每条按"问题 → 机制 → 实证"三段式展开：

**实证来源口径（诚实声明）**：本章机制的实证分两类——标【本项目】的来自 DevDesk 自身事故（git 与项目文档可查）；标【方法论沿袭】的来自 rs-host、winui3、monitor 等兄弟项目的事故，经跨项目经验库沉淀后被 DevDesk 全额继承为纪律。不标注来源会变成编造，本报告逐条标注。

**5.1 防"AI 改了不该改的"（范围边界机制）**
- 条目：镜像复述（写操作前先复述要做什么等确认，防 AI 自扩展范围）【方法论沿袭】
  - 实证：AI 因"既然改了 A 顺便改 B"导致范围外修改的事故
- 条目：只修需求交付物缺陷（审计发现分三类：需求缺陷/本次引入非需求/历史遗留，后两类不修）【方法论沿袭】
  - 实证：PDCA 审计中 AI 试图顺手修 8 项非需求发现被用户制止
- 条目：加字段封装独立方法（给已有功能加东西时新建独立方法，只在末尾加一行调用，不动既有装配逻辑）【方法论沿袭】
  - 实证：改动大量已有装配代码导致回归风险的事故
- 条目：scope-drift-audit 只审边界不审正确性（审计范围外变更时，明确不管"逻辑对不对"，只管"动了什么多出来的东西"）【方法论沿袭】

**5.2 防"多线并行互相踩"（隔离与并发机制）**

### 第6章 自动复盘：事故如何沉淀为经验

**一句话使命**：讲清楚 DevDesk 的开发经验是怎么从"人脑记忆"变成"系统记忆"的——每次事故触发一次复盘，复盘产物沉淀为永久规则，规则在后续每一次开发中被自动加载和检查。

**要点清单**：
1. **核心论点**：如果开发经验只存在人的脑子里，人一走就丢；如果只在文档里，没人翻就是废纸。DevDesk 的经验存储在一个"每次 AI 启动都自动加载"的位置（CLAUDE.md 与 memory 文件），它不是用来查的——是用来"每次干活前先读一遍当规矩"的。
2. **经验的三个层次**：
   - **本仓库规则（CLAUDE.md）**：项目级硬纪律——六阶段生命周期、交付流水线四律、反事故红线、已踩过的坑。每次 AI 会话启动时自动加载，成为该会话的"行为边界"。
   - **本项目记忆（MEMORY.md）**：项目特有但非全局性的经验——开发平台已切回 Windows、子任务并发上限 8、交付口径"不报数字报场景清单"等。指向各子文件，粒度更细。
   - **跨项目经验库（memory/01~09）**：九个领域分类（交付纪律、反幻觉、AI 编排、用户协作、Windows 桌面、Tauri/Rust 前端、Python 脚本、工具链环境、Claude Code 记忆体系），约 120 条可检索的经验条目。本项目只是产出这些经验的源头之一——大部分条目来自多个项目的共同教训。
3. **闭环机制**：
   - **触发**：一个事故 / bug / 近失误发生并修复后，AI（或用户）识别出"这类问题已经有通用性"——不是单点 bug，是一种模式。
   - **沉淀**：把事故提炼为一条纪律——"什么问题 → 什么规则 → 为什么（一句话实证链接）"。写入对应领域的 memory 文件。
   - **保鲜**：每条经验标注 `last_verified`（最晚验证日期），超过 90 天标为"可能过时"，超过 180 天标为"很可能过时"——在 AI 读取时会提示复核。
   - **激活**：每次 AI 会话启动时，用户级 `~/.claude/CLAUDE.md` 通过 `@import` 把九个 memory 文件全文注入——AI 动手前已经知道了所有已知坑。不需要人去"记得提醒 AI"。
4. **cs-retro 自动复盘**【方法论沿袭】（解释：一个定期运行的自动化流程，让 AI 回顾最近的工作日志，自动找出"值得沉淀成经验"的模式）：
   - 工作原理：定期扫描最近的对话记录 → 识别重复出现的问题模式、被用户纠正的错误类型 → 提炼候选经验条目 → 经查重和泛用性检查 → 写入 memory 文件。
   - 与 CLAUDE.md「反事故红线」段的关系：cs-retro 产出是经验"素材"，经人工确认后升格为项目级硬纪律（写入 CLAUDE.md）。
5. **纪实案例**：选 2-3 条经验"从事故到条目"的完整生命周期——例如"子代理报告需三证才能信"（源自虚假完成报告）、"追加消息必须对账"（源自 UAT6 两起漏做）、"测试绿不等于可用"（源自真机 UAT 三连爆）。另附案例 4「累积核对清单的诞生与强制化」【本项目，2026-10-21 当日全链闭环】：多轮融合覆盖事故（后轮改写挤掉前轮注入，每轮只验本轮、全绿仍漏丢）→ 建全历史标记累积清单 + 逐项回归 → 同日升级为项目级 hook（改基线文件自动核对、丢标记即拦）→ 上线实测出"装载时机"坑并订正。从事故到机器强制到自我订正的完整闭环。

### 第7章 AI 行为监控：多层防御的审计体系

**一句话使命**：讲清楚"一群 AI 在干活，怎么保证不出乱子"——不是靠信任，是靠"不同 AI 互相检查、每层检查有不同视角、数字不达标就拦住不放行"。

**要点清单**：
1. **核心设计原则**：AI 可以犯错，但错误必须在到达用户之前被至少一道独立于实现者的关卡拦住。实现者和审查者必须是两个不同的 AI 会话——既写又审等于自己查自己，没有信息增量。
2. **多层审计体系（从内到外）**：
   - **第一层：独立审计关卡（每个改动的必过关）**【本项目】。实现者做完改动后，另派一个只读子任务按六个维度（正确性、回归面、平台对称性、静默失败面、测试有效性、文档口径）逐条核查，产出结构化 findings 文件。审计者不得是实现者本人——这是硬红线。
   - **第二层：多轮递升 PDCA 审计（里程碑级关卡）**【方法论沿袭】。在功能开发完毕后的收口阶段，启动多轮审计——每轮审计范围自动递升，直到连续 N 轮没有新问题才算通过。每一轮审计独立于上一轮（不同审计员、不同视角），防止单一审计员的盲区成为系统盲区。
   - **第三层：追加消息对账（运行时关卡）**【本项目】。对在飞子任务追加任务时，有概率被静默忽略（消息投递与代理收尾存在竞态）。解决方案不是修复投递机制，而是"对账"——追加即登记，完成通知回来后逐项核对，缺项自动补做。
   - **第四层：无人值守 watchdog（长时间运行关卡）**【方法论沿袭】。长时间无人值守时，定期检查所有在飞子任务是否仍存活（心跳检测）。卡死的任务先尝试唤醒续跑，唤醒失败再终止并重新派发。不靠一次派发永远正确——靠"持续检查+自动修复"。
3. **审计产物的结构标准化**：每条 finding 必须带 `file:line`（精确定位）+ 问题描述 + 影响面 + 修复建议；六个维度必须逐条给出结论（"未发现问题"也要写明"已核"）。标准化不是形式主义——是确保不同审计员、不同轮次的产出可以相互比对、追踪闭环。
4. **边界与局限**：审计体系能防"AI 犯了人类能想到检查的错误"，但防不了"人类也没想到要去检查的那类错误"——后者的唯一防线是第3章的用户真机验收（人的眼睛和手感是最终安全网）。
5. **纪实案例**：选 2 个审计发现并阻止线上事故的真实案例——例如 scope-drift-audit 发现某次改动"顺手"删了无关代码被拦下，独立审计发现平台只验了一侧被标记。

   - 产品：六个业务模块全功能运行、双平台原生支持、CI 自动构建与测试、安装包交付。
   - 开发体系：六阶段流水线 + 四律交付纪律 + 九大类跨项目经验库 + 多层审计防御 + 自动复盘闭环。
   - 数字一句带过（"约 1600+ 条测试 / 约 1900 次提交 / 一个月密集迭代"——仅作体量感，不展开分析）。
2. **方法论本质**：DevDesk 的开发方法不是"AI 写代码"——是"用户定义需求边界 + AI 在机制约束下自主执行 + 多层 AI 互审代替人审 + 经验自动沉淀到启动上下文"。它的可复制性不取决于用户有没有技术背景，取决于有没有把这套机制完整复制过去。
3. **可复制清单（本章的核心产出）**：
   - **必备机制**（缺一则系统退化到"AI 随手改代码"的裸奔状态）：
     1. 项目级 CLAUDE.md——AI 启动时自动加载的硬纪律文件（行为边界、反事故红线、已知坑清单）
     2. Worktree 隔离——每个代码改动在独立的代码副本里进行，互不污染
     3. 独立审计关卡——实现者≠审计者，每个改动必经
     4. 先红后绿——修复类改动必须证明测试"会失败"再修到通过
     5. 经验沉淀闭环——每次事故 → 一条纪律写入启动上下文，后续所有会话自动继承
     6. 流程强制层（hooks + 守卫脚本）——把"要求 AI 走流程"翻译成"机器闸门"：基线内容被改坏当场拦、合并后必过门禁、提交前递先红后绿。最小形态 = 一个累积核对脚本 + 几条项目级 hook
   - **推荐机制**（有更好，没有也能跑）：
     7. 跨项目经验库（按领域分文件，`@import` 注入）
     8. 自动复盘（cs-retro 类定期扫描，自动提炼经验候选）
     9. 多轮递升 PDCA 审计（里程碑级收口关卡）
     10. 无人值守 watchdog（长时间运行的心脏跳检测）
     11. 交付前三问（存量数据升级/真实网关/真机——三个"单测覆盖不到"的维度）
   - **配套基建**：
     12. 编译缓存（ccache）——多工作区并行编译的前提
     13. 构建脚本封装——禁止手敲构建命令（唯一执行路径 = 脚本）
     14. 真窗口探针（probe）——模拟真实点击/键盘/拖拽/渲染的自动化测试
4. **适用边界**：这套方法最适合的场景——用户懂"要做什么"但不需要懂"代码怎么做"的中大型项目；技术栈有成熟的 AI 训练数据覆盖（C++/Python/TypeScript/Rust 等主流语言）；涉及 GUI/交互的项目需要真机验收环节。不适用的场景——极小型项目（单文件脚本不需要worktree隔离）、对实时性要求极高的底层系统开发。
5. **起步指南**：一个新项目从零搭建这套方法的最小步骤——(1) 写第一版 CLAUDE.md（项目概况+工具链+核心约束）；(2) 建立构建脚本（单命令构建+测试）；(3) 启用 worktree 隔离；三条上线即可开始"派子任务→独立审计→合并→真机验收"的最小循环。(4) 随事故自然生长——第一次撞上"改丢内容 / 不走流程"类事故时，把对应检查做成脚本或 hook；机制是被事故撞出来的，不必预先设计全套。
