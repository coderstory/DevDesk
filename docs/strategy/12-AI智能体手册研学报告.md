## 二、分章精读笔记

### 第 1 章 · AI 原生应用的新阶段

**核心论点**：AI 应用正从 Chat/RAG/Workflow/Copilot 走向 Agentic Application——模型不再是「被调用的生成引擎」，而是能维持任务状态、分解目标、调用工具、根据反馈调整行为的执行主体。Coding Agent（Claude Code、Codex 等）率先验证了这条路。单 Agent（Single-Agent）是基础形态，Long-Horizon Agent（跨会话持续执行）和 Multi-Agent（多角色协作）是沿时间跨度和协作结构的两个扩展方向，不是必然升级阶梯。

**可落地设计点**：
- 用六个特征判断一个应用是否进入 Agentic 阶段：以任务结果为中心、运行时决定部分路径、能影响外部环境、跨步骤维持状态、自主行为受确定性约束、可观测可评估持续改进
- Workflow 与 Agent 长期共存（Hybrid）：确定性流程用 Workflow，不确定判断用 Agent
- 企业按「最低充分架构」选型——自主性授予越多，对等的边界与证据要求越高
- 企业成熟度四档 L1-L4：辅助生成→受控自动化→自主执行→规模运营

**可信度**：工程共识级（Anthropic、OpenAI、Google 公开实践佐证）

### 第 2 章 · Agentic Application 参考架构

**核心论点**：Agentic Application 的核心是「组件视图 + 平台视图 + 生命周期视图」三视图互补，五个能力责任域（业务应用层 / 构建编排层 / 生产运行层 / 治理控制层 / 调优层）。五项稳定原则：Model 与 Harness 解耦、编排层与 Runtime 解耦、状态外置、自主性与权限匹配、可观测/安全/评估是运行前提而非补丁。

**可落地设计点**：
- Context/State/Memory/Knowledge/Skill 五类对象的严格区分（表 2-3）
- Harness 编排层七大核心能力（Loop/终止、指令工程、规划委派、工具管理、Middleware/策略钩子、压缩续行、人在回路/验证）——和 DevDesk 现有模块高度吻合
- Agent Release 作为最小发布单元：模型版本 + Harness 版本 + Prompt/Context/Memory/Skill + 工具清单/权限 + Runtime/Sandbox + 评估基线，六类要素缺一不可复现
- 执行面 / 数据与资源面 / 控制面三平面划分

**可信度**：工程共识级（AWS/Google/Microsoft/Anthropic/LangChain/OpenAI 公开实践提炼）

### 第 3 章 · Harness 的主流构建方式和责任边界

**核心论点**：四种构建入口——高代码 Framework 自主构建（AgentScope）、产品化 Harness 复用（QwenPaw/Qoder SDK）、托管 Agent 服务（Qoder Cloud Agents）、云产品快速构建（阿里云 AgentCore）——不是成熟度阶梯，是「谁来承担 Harness/Runtime/Sandbox 职责」的责任分配。构建前先固定 Agent Contract（为谁工作/接受什么/交付什么/禁止什么/什么证据算完成）。

**可落地设计点**：
- Harness 构建八对象检查表：Agent Contract、Execution、Context & State、Capability、Environment、Control、Interaction、Quality
- Plan Mode 三步控制：「只读探索→写入计划→人工确认→进入执行」，计划获批前工具白名单限制写操作
- 所有构建入口都要区分 Task 与 Session、Event 与 Trace、Artifact 与 Outcome

**可信度**：工程实证级（有具体代码示例和产品对照）

### 第 4 章 · 任务编排、长程推进与协作流转

**核心论点**：Harness 执行内核 = Prepare→Model→Act→Observe→Verify 五阶段 Loop + 显式任务状态机。Planning 不是展示模型思考过程，是把任务结构外部化为 Harness 和用户都能读取、修改、验证的控制对象。Subagent 的价值在于上下文隔离/能力隔离/并行执行三个具体问题，不是多一个角色包装。完成验证必须由环境事实决定，不接受模型自述「已完成」。

**可落地设计点**：
- 任务状态十态枚举：CREATED/RUNNING/WAITING_INPUT/WAITING_APPROVAL/WAITING_EVENT/PAUSED/VERIFYING/COMPLETED/FAILED/CANCELLED
- 三类规划模式：轻量 Todo / Plan Mode（先计划再执行）/ Planner-Executor（分阶段长期）
- 预算护栏多维：步骤数/时长/Token/费用/工具调用次数/子任务并发数/高风险动作次数
- Subagent 委派七项契约：目标与边界、已知上下文、能力权限、预算、输出证据、失败语义、验收条件
- 五层完成验证强度：结构验证→环境验证→确定性验证→独立模型验证→人工验收
- 无进展检测信号：连续相同工具+相似参数、同一错误反复、Plan 不变、工作区无新事实

**可信度**：工程实证级（AgentScope 代码示例 + 贯穿案例）

### 第 5 章 · 信息：上下文、状态与可复用能力资产

**核心论点**：有限模型窗口与持续增长的任务世界之间需要独立的信息组织机制。Context Builder 是确定性管线（收集→权限过滤→相关性排序→Token 预算分配→压缩→编译），不是把所有内容塞进更长窗口。State 与 Context 严格区分：State 是权威任务事实（存模型窗口之外），Context 是单次调用的局部视图。Context Manifest 记录「本轮模型到底看到了什么」，支撑可解释、可回放、可审计。

**可落地设计点**：
- System Context 六层分层编译：Platform Policy → Agent Contract → Tenant/Project Rule → Runtime Reminder → Selected Skill → Tool Descriptors
- Context Manifest 字段：source_type/id、scope、version、trust_level、permission_basis、selected_reason、token_count、transform、content_hash
- 压缩四步 Commit→Compact→Rebuild→Validate（关键事实必须先入权威状态再退出上下文）
- Continuation Package：Goal+Acceptance、Current Plan/Todo/Blockers、Structured Facts & Decisions、Workspace/Artifact Manifest、Active Async Tasks、Permission & Budget Snapshot、Next-step Brief
- Memory 四类分层（Working/Episodic/Semantic/Procedural）+ 写入六问过滤（是否可预期价值/验证过的事实还是推测/归属哪层/含不含敏感数据/是否已存在/错谁改）
- Skill 渐进式披露三层：发现层（只给名+描述+适用+风险）→选择层（加载 Manifest）→执行层（按需读取细节）
- 多租户资产六作用域：Global / Tenant / Project / User / Session / Task

**可信度**：工程实证级（Context Manifest 有具体 YAML 示例，Memory 写入有六道闸门）

### 第 6 章 · 行动：受控执行、验证反馈与交付准备

**核心论点**：模型输出工具调用只是意图，不是授权。一次受控行动 = Schema 校验→身份绑定→策略判定→审批→执行→Observation→状态/Trace。Function Calling / MCP / A2A 分别在模型-Harness、Harness-能力、Agent-Agent 三层，不能混用。Preview-Approve-Commit-Verify 四步处理高风险动作。

**可落地设计点**：
- 统一 Action Request 字段：action_id/task_id、capability_id/version、arguments、actor、purpose、risk_classification、idempotency_key、timeout、approval requirements
- Tool 设计六要素：名称说明业务目的+非目标、输入 Schema 明确类型枚举边界、输出区分结构化结果+摘要+原始引用、声明只读/副作用/可逆/幂等、错误稳定分类、凭证留执行侧不进模型
- 权限三态：ALLOW（记录依据）/ DENY（返回原因+允许替代项）/ ASK（指定审批人）
- Trace 端到端关联：Agent Version → Session/Task → Context Manifest → Plan/Todo → Model calls → Action Requests → Tool results → Workspace changes → Verifier → Outcome
- 区分 Agent Harness（单次任务完成门禁）与 Evaluation Harness（跨版本比较）

**可信度**：工程实证级（有 SDK/CLI 代码示例 + 贯穿案例的 YAML 示例）

### 第 7 章 · Agent 运行时与沙箱

**核心论点**：Sandbox 不是「给 Agent 一台虚拟机」，是按任务配置、有隔离边界和明确生命周期的执行环境。三类典型负载：工具执行（Agent use sandbox）、长时任务（Agent in sandbox）、训练评测（批量并行）。状态分层降低等待成本：从持续运行→浅休眠→深休眠→仅保留文件后重建。

**可落地设计点**：
- 五种沙箱环境类型对应任务：Code / Browser / Computer / AIO / MCP-Skill 环境
- 会话亲和与工作区挂载分离：前者管「请求到哪个环境」，后者管「环境挂载什么数据」
- 实例故障恢复三步：确认旧实例已停（围栏机制）、核查外部操作结果、从检查点继续
- 模板/Fork/快照/Reset 四机制支撑并行探索
- 围栏（Fencing）：新实例接管前先使旧实例写入权限失效，仅更新控制面编号无效

**可信度**：工程实证级（E2B、阿里云 Agent Sandbox 产品对照）

### 第 8 章 · Agent 状态存储与语义资产

**核心论点**：Agent 需要四类持久化对象——运行时状态（Event Log/Checkpoint）、工作区与产物（快照/Artifact）、记忆与知识、业务语义与本体——各有一致性要求，不能全塞进向量库。Event Log 提供只追加的顺序事实，Checkpoint 提供可信恢复点，快照提供可回退版本，Artifact Store 提供可寻址可保留可交付的成果。Lakebase 作为参考：统一对象身份/版本/权限/生命周期治理，底层按对象特性选引擎。

**可落地设计点**：
- Event Log 只追加、任务级强一致（不同任务不共用全局日志）
- Checkpoint 至少含：当前阶段、已完成/未完成步骤、工具调用结果引用、工作区版本、子任务状态、等待条件、状态版本
- 增量快照：只保存变化集，恢复时组合最近完整快照+后续增量
- 执行租约+状态指针：保证同一时刻只有一个实例推进任务
- 工作区分层：可复用基础层（只读）+ 共享数据层 + 私有可写层，Copy-on-Write
- Artifact 生命周期：Draft→Validating→Ready→Published/Rejected→Archived/Deleted
- Memory/Knowledge 治理边界：Memory 来自 Agent 经历（需写入过滤），Knowledge 来自企业文档（需来源权限同步）

**可信度**：工程实证级（Lakebase 参考架构完整）

### 第 10 章 · Agent 异步任务与自动化流程（略读要点）

核心：区分四种触发——用户直接触发、定时/Cron、事件驱动（Webhook/消息）、子任务回调。异步任务需要稳定 task_id、幂等键、超时、取消传播。长任务从队列中释放执行资源，事件到达时从权威状态恢复。

### 第 11 章 · Multi-Agent 协作与编排

**核心论点**：多 Agent 编排的核心不是「让多个 Agent 互相调用」，而是围绕共同目标建立分工、依赖、状态共享和结果聚合。组织拓扑三种：主管-执行、对等协作、分层编排，不是成熟度阶梯。Context 共享不是「所有人看同一窗口」，而是共享来源（目标/约束/状态/产物），每人按角色/任务/权限取最小充分子集。

**可落地设计点**：
- Handoff 交接四类信息：目标、已知事实、待处理事项、可用引用
- 团队级停止条件：总时间/成本预算、最大委派深度、派生任务数、单任务重试次数、连续无新增有效产物的轮次
- 结果聚合三层：执行者提交（候选产物）→ Leader 接受（可进入下游）→ 根 Task 完成（覆盖总目标），三层不互相替代
- 团队治理：入站权限（谁可调用 Agent）与出站权限（Agent 可访问什么）独立配置
- 团队通信模式三种：Direct/Handoff、Shared Message Space、Event-driven/Pub-Sub

**可信度**：工程共识级（A2A 协议配图 + 贯穿案例扩展）

### 第 13 章 · Agent 的可观测性

**核心论点**：Agent 可观测 = 从用户请求到任务完成的全链路因果追踪。Session/Trace/Span 三层模型。执行语义十二种标准分类：ENTRY/AGENT/WORKFLOW/STEP/LLM/RETRIEVAL/MEMORY/TOOL/GUARDRAIL/COMPACTION/HITL/INTERRUPT。eBPF 无侵入采集可补「代码改不了」的观测缺口。审计 = 观测事实→候选信号→上下文研判→已确认事件，三层证据链。

**可落地设计点**：
- Trace 因果链必须关联：Agent 版本 → Context Manifest → Plan/Todo → Model 调用 → Action → Tool → Workspace 变化 → Verifier → Outcome
- 审计最小证据链：主体与范围、意图与授权、执行事实、结果与证据
- Coding/通用 Agent 观测三来源组合：原生插件回调 + 生命周期 Hook + 本地 transcript/日志/数据库
- Token 口径：缓存读取与写入分开、汇总时不再相加、缺失标估算不记零
- eBPF 补「实际发生的运行时证据」：进程/文件/网络/命令行，但不能替业务授权

**可信度**：工程实证级（LoongSuite Pilot 开源 + OpenTelemetry GenAI 语义约定 + 阿里云产品截图）

### 第 14 章 · Agent 安全

**核心论点**：Agent 安全需「防护与管控兼具」——防护防被打穿（供应链/注入/越狱），管控防不越边界（身份/权限/每次调用校验/数据出域阻断）。身份安全是核心：Agent 需自己的「数字工牌」，用户长期凭证不交给 Agent，运行时注入短期令牌。

**可落地设计点**：
- SSRF 是联网 Agent 关键风险：抓取/预览/代理请求都可能成为非预期网络入口
- 拒绝钱包攻击（DoW）：攻击者不断制造补充工作让 Agent 持续消耗 Token/API/并发槽位
- 会话级沙箱隔离：用完即弃、空闲超时回收、每会话独立临时凭证
- Agent 出站流量默认拒绝、按需放行、阻断云元数据端点
- 动态最小授权：Token Exchange 实现权限收敛——Agent 拿到的令牌只含被授权的最小 scope
- OWASP Top 10 for Agentic Applications 2026 为威胁建模起点

**可信度**：工程实证级（OpenAI/Hugging Face 真实入侵案例 + OWASP 标准引用）

### 第 15 章 · AI 资产的发现与管理（略读要点）

核心：企业需 Agent 资产目录——Agent 实例/Skill/MCP Server/Tool/Prompt 全部都有版本、所有者、依赖关系、使用记录。版本漂移检测与回滚。与 DevDesk「插件状态单一注册源」设计红线高度相关。

### 第 16 章 · Agent 行为生成与质量验证

**核心论点**：在角色标准、失败代价、身份连续三样制度前提都缺位的当下，**仿真（Simulation）是唯一立刻可做的验证手段**。Simulation = 用户模拟 + 环境模拟（全替身/混合/隔离真实依赖三种模式）。证据交付分三层：Records（原始记录）→ Observations（事实性观测）→ Evidence（面向评价项的引用），不把评估结论与原始材料混在一层。

**可落地设计点**：
- 仿真边界两条：不触达未授权生产账户/数据/网络、不产生不可控真实业务副作用
- 禁止把工具调用顺序固定成脚本——被测的就不再是 Agent 的决策
- 每次替换前问一句：这个对象是「考察的内容」还是「设定的条件」？内容不能换，条件必须换并写清换成什么
- 替身实现六种机制按开放度：脚本→录制回放→规则→状态机→模型生成→混合
- Run 四状态独立：执行状态/仿真有效性/证据完整性/任务质量，不能压成单一成功/失败
- 用户模拟三层模型：Persona（底色）+ 认知状态（允许与客观不一致）+ 行为策略（反应规则+状态机+时钟耐心）
- 时间分离四账：业务日历时间、仿真逻辑时间、单调时钟、墙钟时间
- 故障注入四步记录：计划注入→执行器生效→目标命中→恢复验证，缺一不可信
- 场景规格十字段组：identity/sut/user/environment/interaction/participants/events/execution/evaluation_ref/provenance

**可信度**：工程实证级（完整数据契约 + yaml 示例 + Wajo/Fo 模拟世界实践）

### 第 18 章 · Agent 调优总览（略读要点）

核心：调优沿模型和 Agent 两条主线。模型线 = 微调/RLHF/推理优化；Agent 线 = Trace→失败聚类→根因→Harness Patch→回归→灰度发布。常见 Patch 与根因一一对应：缺事实→调 Context/Knowledge，错误经验→修 Memory，不会执行→补 Skill，工具误用→改 Schema/权限。不是从单条失败直接改 Prompt。

### 第 23 章 · 受控自进化

**核心论点**：自进化不等于让 Agent 在生产中自由修改自己。任何由模型/轨迹生成的 Prompt/Memory/Skill/Harness 补丁都应视为候选变更，经过可复现评估、安全检查、版本化、灰度和可回滚发布后才能进入生产。优化闭环五阶段：Trace+Outcome→Failure Cluster→Diagnosis→Harness Patch→Regression→Release Gate→新版本。受控自进化需限定变更范围（如只允许修改 Prompt 措辞不改结构）、每一变更都有对应的回归集。

**可落地设计点**：
- 自进化变更范围分级：L1 调整 Prompt 措辞 / L2 修改 Memory 条目 / L3 修订 Skill 步骤 / L4 改动工具选择策略 / L5 改 Harness 编排逻辑，每级对应不同的证据要求和审批门槛
- 回归集必须同时包含原失败用例+相邻正常用例+安全对抗用例

**可信度**：工程方向级（有方法论框架，部分实现仍在早期）

### 第 29 章 · GOAI Agent Infra 赛道（略读要点）

核心：多 Agent 协同的前沿竞赛作品。关键信号——下一代 Infra 方向集中在「Agent 可观测性」「沙箱与隔离」「跨 Agent 通信协议」「自进化闭环」四轴。与第 30 章 Agentic OS 展望呼应。

### 第 30 章 · 从 Agentic Application 到 Agentic OS

**核心论点**：当同一组织运行多个 Agent、多种框架、多个租户时，六类跨应用工程约束（任务标识不统一、执行环境成本决定并发经济性、能力元数据不足、Context/State 边界被侵蚀、授权难随任务派生与收回、证据采集点分散口径不统一）需要在应用之下建立一个共享层——Agentic OS。下沉判据三条：复用性（多个应用重复实现）、强制性（必须由被约束方之外执行）、可验证性（需要独立证据来源）。Agentic OS 管理九类核心对象：Agent 身份、Run、Session、Workspace、Skill、Tool/MCP 端点、Budget Lease、Policy、Evidence。三层结构：Agent 运行服务层→系统承载层→治理与证据层。

**可落地设计点**：
- Run 不等于进程——一个 Run 可跨进程/副本/区域，可中途挂起
- Budget Lease 是被忽略但最关键的「可控自治」对象：一次授权同时限定资源、操作、有效期与撤销方式
- Evidence 三态区分：计划中的操作/已发出的操作/已确认结果的操作——直接决定恢复策略
- 自治阶梯 L1-L5：建议→单步获准→有界自主→长任务自主→组织级自治，每级的边界和证据要求递增
- 「自治程度上限不由模型能力决定，由可撤销范围与可证明范围决定」

**可信度**：方向级（工业实践仍在早期，ANOLISA 等开源项目 v1.1 多数组件 0.x 版本）

### Personal Agent 专题（精读）

**核心论点**：2026 年 9 月 Personal Agent 密集发布（Cue/Manus 2.0/Muse/dots/Grok Bot/Fo），共同特征是把长期运行环境、个人身份、触发条件、审批和记忆管理整合为面向普通用户的完整产品。技术要点六项：持久状态（不随会话关闭丢失）、分层记忆（区分情节/语义/程序+工作记忆）、任务账本（可恢复状态机）、事件触发（控制环非定时器）、身份延续（跨模型/主机仍为同一 Agent）、重要动作授权。中国 C 端靠「生态内嵌+信任变现」、B 端靠「数字员工」。

## 四、设计原则建议

1. **「任务事实不活在上下文里」**（用于 A 期）：现有 context note 从自由文本升级为结构化 Task State（阶段/Plan/Todo/Artifact/阻塞/剩余预算），模型上下文从权威状态重建而非从消息历史猜测进度。每次 COMPLETED 之前强制写回关键事实。

2. **「权限不只在入口查一次」**（用于 C 期）：每次高影响工具调用（当前及未来的 GitLab 写评论、文件写操作）都经过身份绑定→策略判定→审批→执行→结果验证五步，权限传到链路末端（tool-call 级别的授权而非 session 级一次性通过）。

3. **「无进展先重规划、不盲重试」**（用于 D1/D2 期）：D1 失败重试前加无进展检测（连续相同工具调 N 次+相似参数、同一错误反复出现、工作区无新文件/Artifact），检测命中后要求模型基于结构化证据重新规划而非原地重跑。D2 做完自检引入验证器链：结构验证→环境验证→确定性验证→人工验收，逐层升级。

4. **「说看到就留 Manifest」**（用于 C/D 期审计）：每次调模型前生成 Context Manifest（来源/版本/Token/可选信任级），审计/调试时从 Manifest 查「模型到底看到了什么、为什么」，不依赖事后还原拼接文本。

5. **「委派是借不是给」**（用于 E 期）：E 期角色间交接用结构化 Handoff（目标/已知事实/待处理项/Artifact 引用），子角色从父角色继承预算租约（父任务取消时子任务同时失效），子角色的权限 ≤ 父角色授予的最小 scope。

6. **「仿真省下实错成本」**（用于 E 期 QA 角色）：QA 角色用全替身/混合/隔离真实依赖三种模式跑仿真，回归用例必须包含原失败场景+相邻正常场景+安全对抗场景。仿真结果不直接等于发布授权——同一份证据包给质量/合规/回归三个视角各自解读，不混层。

7. **「Measure 不是数字是因果」**（用于 D 期 + E 期）：现有三表审计升级为 Trace 因果链——Agent 版本 → Context Manifest → Plan/Todo → Model 调用 → Action Request（含身份+权限判定） → Tool 结果 → Workspace 变化 → Verifier → Outcome，每一步的 Span 可独立查询和关联。观测的目的不是看数字、是回答「这次运行的每一步谁做的、凭什么、产生了什么结果」。
