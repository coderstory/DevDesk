## 一、背景与目标形态

**方针**。凡机制与研究系列报告（07~12）重合的，优先按已验证方案设计、不自研——前人已验证的骨架与模式直接采用，只在我们三条特化轴（无人值守、C++ 原生桌面常驻、业务绑定）上做原创设计。三轴释义：无人值守 = 触发驱动 + 自动重试 + 自唤醒；C++ 原生桌面常驻 = 系统托盘 + 桌面感知（剪贴板/窗口/文件状态）；业务绑定 = 自有模块工具面 + 公司内部 GitLab / 敏捷平台对接。

**现状**。智能体现在支持六种启动方式（手动、定时——按时间规则如「工作日每天9点」、每天、闹钟——某个绝对时刻跑一次、事件、常驻），约 21 个内置动作能力，事件触发（首批三个动作事件——待办新建/待办完成/笔记保存——含冷却窗口，即同一事件短时间内不重复触发（冷却时长在详细方案时根据事件类型分别调整）），任务级便签（context note，随任务持久、跨运行生效），预算护栏（单次运行时间上限 + 模型调用次数上限 + 同一任务同时只跑一份），三张审计表（任务定义、运行记录、每轮对话消息）。能力面已铺开，当前瓶颈在「用起来顺不顺」而非「能力够不够」。功能全貌详见业务功能清单，技术资产详见技术能力清单与软件架构清单，运行流程详见流程场景清单。

**目标**。智能中枢的终极形态是一条从需求到代码的完整流水线：智能体扮演三个角色——PM 负责理解需求并拆成任务、QA 负责测试与审计、开发负责写代码——从一份需求文档出发，最终产出 GitLab 合并请求（MR，Merge Request，交给人审查的代码变更单）。途中每一步都自带质量闸（独立审计——审查者与实现者不是同一个人、先红后绿——先证明测试会失败再修到通过、预算护栏），最后一道门永远是人（决策记录卡 ADR 0001）。

## 三、分期路线（A → E）

> 以下各期批次划分可在各期详细方案时微调（拆分/合并子批），但档位与边界以决策记录卡为准、不可动。B 与 D 的交错配对顺序在 B 期详细方案时落实。

### A 期（收口）

**目标**：把现有功能收到「顺手」——触发呈现统一、任务可定制、异常原因可见。

**内容清单**：
1. **触发方式在界面上统一**。六种触发方式在界面上归为四大类：手动点 / 按时间（下面再分三种：定时规则 cron 如「工作日每天9点」、每天、闹钟一次性） / 等事件发生 / 一直跑着。底层保存方式不动，只改界面怎么展示。
2. **任务加一个「角色设定」栏**。每条任务可以写自己的系统提示词（告诉模型它这次扮演什么角色、守什么规矩），跟全局的运行环境系统提示词分开。AI 草稿同步升级：以前只帮你生成一句话目标，现在升级为一口气生成三件套——目标 + 角色设定 + 记忆建议，但涉及权限和「单次运行里模型来回调工具的次数上限」的部分，仍然不听模型的建议。
3. **撞闸和失败原因看得见**。每次任务「没跑起来」（被某个闸门拦住、触发条件没满足）或者「跑了但失败了」，界面上都能看到原因，不模糊过去。
4. **对冲——工具接口预留 MCP 协议适配缝（11 报告 §5/§6，现在埋、防 C 期返工）**。现在先把工具接口留一个「协议类型」的标记位置（默认标「自用」），将来要接外部标准时不用拆工具重写——技术实现为每个工具定义预留 `protocol` 字段（初始值 `"native"`），工具调用序列化与反序列化走独立的 ProtocolAdapter 抽象层。评估为约一天量级，A 期方案阶段核定后排期，防 2027-2028 年 MCP 标准化浪潮下被迫从头重写工具层。MCP 已是跨客户端事实标准（Claude Code/Cursor/Codex 三家原生支持，11 报告 §2.1），工具注册表内核保持自建（单一真相源）、对外通过协议适配层统一暴露。
5. **任务状态与预算护栏多维化（12 报告第 4 章，手册工程实证级）**。任务运行状态从现有五态升级为十态枚举：CREATED（已创建）/ RUNNING（运行中）/ WAITING_INPUT（等输入）/ WAITING_APPROVAL（等审批）/ WAITING_EVENT（等事件）/ PAUSED（已暂停）/ VERIFYING（验证中）/ COMPLETED（已完成）/ FAILED（已失败）/ CANCELLED（已取消），等输入、等审批、等事件、暂停、验证中五种中间态是「任务为什么停着」的明确信号，不再靠猜。预算护栏从当前三指标（迭代上限 / 墙钟 / Token）扩充为六维——步骤数 / 时长 / Token / 费用 / 工具调用次数 / 子任务并发上限，撞闸后向用户展示明确终态与未完成清单，不静默截断。「等审批」态依赖 C 期权限三态的「每次问」审批机制——C 期落地前该态不可达，十态先上九态、等审批随 C 期激活。
6. **评估项——运行记录补「最终结果」字段（07 报告第 4 节）**。给运行记录补 outcome 字段，记录这次运行最终是圆满、部分完成还是中断——具体落库方式 A 期方案时定，也供 D2 自检结果落库复用。
7. **内置环境上下文注入（2026-10-21 用户指示：Claude Code 同款能力很必要；本条按「必要且充分」从权威参照推导，非例举）**。按「模型会因不知道而犯什么错」反推六类必注环境事实，每次运行组装进系统提示词：
   ① 时空锚定——当前本地日期时间（已有；opencode core/date 同款）；
   ② 机器环境——操作系统类型与版本、CPU 架构（x64/arm64）、路径写法提示（Windows 反斜杠与盘符）、**外网受限声明**（模型默认假设能联网）；
   ③ 位置与仓库——工作区根路径、应用数据根、关联仓库路径、是否 git 仓库、git 分支（经 `.git/HEAD` 文件直读，不引入子进程；更丰富的 git 状态留 E 期工具）——对应 opencode core/environment 块（工作目录 / 工作区根 / 是否 git 仓库 / 平台）；
   ④ 任务与运行元数据——任务名与编号、本次运行编号、这是第几次运行、上次运行的最终结果（与本节第 6 条「最终结果」字段联动）；
   ⑤ 能力与边界声明——可用工具总数、环境限制（无子进程、外网受限、不可逆操作须授权），防模型反复尝试注定失败的动作；
   ⑥ 预算余量——剩余迭代数 / 墙钟 / Token（无人值守场景特有，Claude Code 与 opencode 均未注入；手册「剩余预算进任务状态」的直接应用——让模型知道自己还能干多少、该收尾了）。
   红线：只注环境事实，**绝不注密钥与配置敏感项**；按任务场景取最小充分集；运行期间环境变化（如跨天）按 opencode 的变更检测补一行更新，不整块重注。
8. **候选——任务汇总「一览」提到列表层（旧账转入 2026-10-21）**：不打开详情弹窗就能横向比较各任务的成功率与耗时；需先定列表行布局（宽度预算已被状态徽章占满），A 期方案时一并裁决。

**设计参考**（08 报告探针一、三）：最小 agent 循环骨架参照 smolagents（huggingface，约 1000 行核心，已克隆本地 `../smolagents`）——代码即行动格式比 function-call JSON 更省 token、表达力更强；多 agent 运行时切换参照本地 `../opencode2`（anomalyco/opencode）的 build/plan 双模式设计。
**设计参考**（12 报告第 5 章——任务记忆结构化）：现有任务级 4KB 自由文本便签（context note）评估升级为结构化 Task State Schema——阶段 / Plan / Todo / 阻塞 / 剩余预算，每次 COMPLETED 前强制写回关键事实。「任务事实不活在上下文里，上下文只是给模型看的视图」——模型上下文从权威状态重建而非从消息历史猜测进度。

**验收要点**：触发配置呈现四类统一、草稿三件套（目标 / 角色设定 / 记忆建议）可用、每次「没跑 / 失败」都有可读的原因文案。

### B 期（对接能力）

**目标**：给智能体接上外部世界——文件、搜索、GitLab。分三批，每批配 D 期一块能力。

#### B1：文件工具组 + 事件扩容第一批

- **文件工具组**：列出文件 / 读文件 / 写文件 / 移动文件，只限专用工作区（决策记录卡 ADR 0002）。超出工作区的路径一律拒绝，不开例外。
- **事件扩容第一批**：在现有三个动作事件之外，补齐写操作路径上的核心事件。候选：待办更新、笔记新建、Claude 配置切换、应用启动等，具体清单在 B1 期详细方案时锁定。**必答题（旧账转入 2026-10-21，此前挂起等拍板）**：智能体自己的工具写入（todo.*/md.* 等）要不要发事件——存在自触发循环风险（智能体写 → 触发事件 → 派发新运行 → 再写）；候选解法 = 事件携带来源标记、工具路径写入打标跳过。B1 立项时必须先拍死这道题再扩事件。

#### B2：搜索工具 + 事件扩容第二批

- **搜索工具**：面向公司外网受限环境的搜索源设计。具体搜什么（本地全文索引、内置文档、受限外网 API 等）在 B2 立项时做一次明确决策（做不做、做哪些），本文档不预判结论。
- **事件扩容第二批**：B1 之后剩下的场景事件补全。

#### B3：GitLab 只读工具组

- 列出合并请求列表 / 读代码变更内容 / 读流水线状态（决策记录卡 ADR 0003 第一档）。这三项只读不产生外部可见影响，第一批就做。

**设计参考**（09 报告 4.1 / 4.3 节）：(1) ADR 0003 第一档的三项（列 MR / 读 diff / 读流水线）为最小承诺，MR 详情与读讨论为同档只读扩展，B3 按五件套实现——列 MR / MR 详情 / 读 diff / 读讨论 / 读流水线状态，GitLab API v4 对应端点已列明；(2) 事件接入采用 webhook + 新式签名验证（HMAC-SHA256）推到本地 HTTP 服务，另配手动粘贴 MR 链接兜底——不走 GitLab CI（DevDesk 是桌面应用，没有 CI runner 环境）。

**候选工具组（具体归哪批在各批详细方案时锁定）**：桌面感知工具组——读剪贴板、感知当前窗口和前台应用、拍文件系统状态快照（这是桌面应用相对网页方案的独有能力）。

**验收要点（全 B 期）**：新工具按现有注册机制接入后就可以被任务使用（破坏性动作仍然受全局授权闸管控，按工具允许清单——只有列在上面的才放行——留到 C 期）；文件工具写入只落在工作区、读业务数据路径被拒绝；GitLab 只读三件套可以正常拉取合并请求列表和代码变更内容。

### C 期（扩展机制）

**目标**：把「加一个新工具 / 新事件」从改核心代码降为配置级操作。

**内容清单**：
1. **「运行外部脚本」工具（script.run）决策**：按决策 D-R2 的验证结果决定是否做。如果做——只允许指定目录 + 超时限制 + 输出截断，它要推翻「软件绝不运行外部程序」的旧规矩，开工前必须写一条决策记录卡（ADR）记下理由和约束；如果验证没通过就放弃这条路。
2. **技能清单导入器**：自动把技能目录（含工具声明和事件订阅）注册进智能体运行环境，不再要求每加一个新技能就要改注册代码。**用户侧体验对标 Claude Code 的插件/技能/MCP 三种安装面**：能力安装 = 把技能目录放进指定位置（或粘贴 MCP 服务器地址）即注册生效、无需改代码；已装能力在界面可查、可停用、卸载即注销——单一注册源保证一处管理（ADR 0004）。技能格式以 anthropics/skills 官方规范为起点（已克隆本地 `../anthropic-skills`，含 SKILL.md 格式 spec + progressive disclosure 加载机制 + 官方模板；08 报告探针二）。工具注册参照 07 报告第 3 节四元组——名字 + 说明 + 参数定义 + 执行函数；外部工具带着自己的参数定义进来、不需要提前编译（接外部技能与工具服务器的前提）。
3. **权限升级**：从全局「允不允许破坏性操作」一个总开关，升级为按工具逐个设置允许清单——每个工具在每条任务上可以单独设为读 / 读写 / 禁用，破坏性工具默认禁用、必须显式打开。用户在弹问时选过「始终允许」就记下来、后续同类不再问（07 报告的 saved rules）。
4. **MCP 客户端通道评估**（趋势修正建议第一项，开工前的必答题）：MCP（Model Context Protocol，一种让 AI 工具连接外部数据和服务器的通用插座标准）客户端——即「作为客户端连接别人现成的 MCP 工具服务器（比如 GitLab MCP 服务器、文件系统 MCP 服务器等）」——是否作为扩展机制的一等通道。与「运行外部脚本」工具并列裁决。区分：当客户端连别人的现成服务器——在讨论范围内；自己建服务器或实现完整 MCP 协议——不在讨论范围内（仍在「明确不做」清单里）。如果做，必须另写一条决策记录卡。
5. **候选——工具执行进度回调（07 报告 Top5 第 5 项）**：长任务（抓取、批量处理）实时把进度推给界面——是否做、哪批做，C 期开工必答题时定。

**关键事实输入**（09 报告发现）：官方 GitLab MCP 服务器（modelcontextprotocol/servers-archived）已归档，仅含 9 个仓库管理类工具（建仓库/建分支/建 Issue/建 MR/读文件等）、没有任何 MR 审查工具（无 list_merge_requests、无 get_merge_request_changes、无 create_merge_request_note）；社区实现搜索无可靠结果。因此该评估项的基线预期修正为「自建 B3 工具面为主，MCP 客户端通道看生态成熟度再定」。
**关键事实输入**（11 报告 §2.1——MCP 标准化大势）：MCP 已是跨客户端事实标准——Claude Code、Cursor、Codex 三家均原生支持，配置文件格式不同但协议相同；社区 MCP 服务器生态繁荣（Context7、Playwright MCP、Chrome DevTools MCP、DBHub 等）；MCP 预计 2027-2028 年进入 IETF/W3C 级标准化进程。分层结论——内核保持自建工具注册表（单一真相源），对外加 MCP 协议兼容层，不做「自建 vs MCP」二选一；内核是唯一注册源、MCP 是对外口音（11 报告 §6 设计原则 1）。
**设计参考**（12 报告第 6 章——权限三态一致性注）：手册的权限三态（ALLOW 放行 / DENY 拒绝 / ASK 每次问）与 07 报告三段式权限闸同构、互为印证——两者都要求每个工具调用经过「身份绑定→策略判定→审批→执行→验证」五步，高风险动作走 Preview-Approve-Commit-Verify 四步确认。
**设计参考**（12 报告第 5 章——审计升级 Context Manifest）：C/D 期审计能力评估引入 Context Manifest——每次调模型前记录「模型到底看到了什么」：来源类型与 id、版本、Token 消耗、可信级别、选择理由、变换方式（压缩/重排/截断）。支撑事后追溯「为什么做了这个决定」，不依赖事后还原拼接文本。与现有三表审计（任务定义/运行记录/每轮对话消息）互补——Manifest 补充「上下文快照」维度，填上当前审计表粒度缺口。

**验收要点**：导入器可把一个新技能目录注册出可用的工具与事件，不手写注册代码；工具允许清单可逐工具控制，不依赖全局开关。

### D 期（自主性）

**目标**：让智能体少问人——自动重试、做完自检、自己唤醒自己、失败通知。D1-D4 穿插于 B/C 各批之间交付，不与它们绑死顺序。自主性按「可监控的半自主」校准（11 报告 §6 设计原则 6）——每个自主决策可追溯（有决策依据记录）、可回滚（可撤销错误操作）、关键动作有人审钩子（操作前等待确认），不追求「完全无人值守」。

**内容清单**：
1. **D1 失败自动重试**：每条任务可以设置重试次数和间隔。只在瞬时错误（网络不通、对方服务器返回 5xx 错误、超时）时重试；业务逻辑错误（工具返回了有效结果但语义不对）不重试。**候选（旧账转入 2026-10-21）**：智能体直连路径的供应商故障自动切换——代理路径已有「备用供应商单跳重试」，直连未随迁；出现真实多供应商场景时随 D1 重试一并设计。

**设计参考**（10 报告 2 节）：失败分类铁律——瞬时错误退避重试（指数退避：失败后等待时间按 1 秒 → 2 秒 → 4 秒翻倍，上限 3 次）、逻辑错误不重试而进反思链（带着错误日志重新推理）、同类错误 3 次熔断（按 10 分钟窗口 + 按任务独立计数，不设全局统一熔断器）。理论依据：ExpeL（三连败同类错误 = 规则缺陷，单次失败 = 概率噪声）+ ANNEAL（持久符号修复让复发率从 72-100% 降到 0%）。
**设计参考**（12 报告第 4 章——无进展检测）：重试前先做无进展检测——连续调用相同工具且参数高度相似、同一错误反复出现、Plan 长时间不变、工作区无新增事实或产物。检测命中后先要求模型基于结构化证据重新规划，再决定是否继续重试；不原地盲跑。
2. **D2 做完自检**：任务新增「什么算做完」标准栏（自由文本，用户自己填）。每次运行结束前强制模型对着这个标准自己检查一遍；不够格就带着上一轮的教训自动重跑，最多重跑一次——重跑一次还不过就停、标失败，不无限循环。

**设计参考**（10 报告 1 节）：(1) 机械打分表——把「什么算做完」拆成 pass/fail 条目（编译通过？测试增量通过？），不给模型自由打分空间（文献实证：LLM-as-a-Judge 有位置偏见 + 冗长偏见 + 自我增强偏见，同一模型既干活又打分必高估）；(2) 审查者与执行者分离——至少用不同 system prompt，预算允许时用不同模型路由；(3) 不退化门——每次改完代码跑一条与改动无关的回归用例集，退化了就回滚（RSEA 结论：不加 hold-out 验证的自我进化是高风险高方差）。
3. **D3 自己唤醒自己**：智能体自主安排「稍后再看一眼」——复用现有闹钟（一次性定时触发）的底层机制，以工具形态暴露给模型。跟用户自己设的闹钟区分：自唤醒是智能体在运行中自己安排的后续触发。醒来先自检的验证器复用 D2 的验证框架，D2 先行或与 D3 同批交付。

**设计参考**（10 报告 3 节）：三边界——(1) 单任务最多自唤醒 3 次，第 4 次转人工通知并附前 3 次完整轨迹；(2) 随时可取消——每次自唤醒前检查取消令牌（本地文件标记或内存 flag）；(3) 醒来先自检——跑一条轻量自检（读系统时间 + 心跳日志 + 检查上次任务是否真完成），自检不过不安排新任务直接上报。理论依据：Generative Agents 的定时反思→计划生成→执行循环 + RSEA 的「不退化才升级」。
4. **D4 失败升级通知**：重试仍然失败时通知用户，附带失败原因和已经试过的手段清单。
5. **评估项——跨会话记忆（11 报告 §1.1/§6 设计原则 3）**：跨会话记忆（项目进展、决策记录、个人偏好）不自建，评估对接 MCP Memory Server（官方维护的参考实现之一）；现有任务级便签维持现状不扩展。短记忆（单会话内的任务状态）随上下文窗口扩大和成本下降正在被「直接塞进上下文」替代（11 报告轨迹推演），长记忆形态从「agent 自己维护」转向「协议化外部存储」。
6. **候选——方案分叉对比（07 报告第 4 节 fork 机制）**：同一任务从某一步分叉出两条路线各自跑完再对比结果——是否做，D 期开工必答题时定。

**验收要点**：瞬时错误可自动重试成功、非瞬时错误重试后正确停；做完自检不过时可见「教训 + 重跑」一轮记录；自己唤醒自己的工具可创建一次性的后续触发。

### E 期（需求文档 → 合并请求 完整流水线）

**目标**：智能体承担 PM / QA / 开发角色分工，从需求文档走到合并请求。

**角色模型**：每个角色 = 一套独立的系统提示词（告诉模型它扮演什么角色）+ 可用工具子集 + 阶段闸门。PM 负责理解需求和拆任务；开发负责写代码；QA 负责测试和审计。三个阶段串行推进，上一阶段产出通过质量闸后才进入下一阶段。设计参考（07 报告第 2 节）：每个角色绑定一个模型、各自可用的工具子集、步数上限；给审查类角色绑便宜模型省钱、给只读角色禁用写工具。

**流水线路径**：需求文档输入 → PM 产出任务分解 → 开发产出代码变更 → QA 产出测试和审计结论 → 建合并请求（MR）。全程内建质量闸（独立审计——审查者与实现者分离、先红后绿——先证明测试会失败再修到通过、预算护栏），合并请求留人审合并（决策记录卡 ADR 0001）。

**质量闸三层**（趋势修正建议第二项，采纳为 E 期设计基准）：① 测试闸——QA 角色的自动测试、先证明会失败再修到通过；② AI 审查闸——独立审查，实现者和审查者不能是同一个智能体实例——既写又审等于自己查自己；③ 人工合并闸——合并请求留人审（决策记录卡 ADR 0001）。三层缺一不可、顺序不换。

**评估项——预算租约（12 报告第 4/30 章，设计预留于 D 期、随 E 期任务派生落地实现）**：子任务从父任务继承预算租约（Budget Lease），父任务终止时子任务预算同时失效。防「任务已取消、子任务还在烧 Token / API 费用」的反模式。租约含资源上限、操作范围、有效期与撤销方式，一次授权同时限定四维。预算租约依赖任务派生机制（父子任务在 E 期流水线才首次出现，现有任务模型无父子概念）——D 期仅做概念定义与接口预留，具体实现随 E 期任务派生机制落地。

**本文档不预设的项**（E 期开工必答题时定）：
- 试点项目选型（哪个仓库 / 哪种需求类型先跑）
- 角色切分粒度（PM 与 QA 是否合并、开发是否再拆前后端）
- 人审界面（审查合并请求时的交互是 DevDesk 内置还是走 GitLab Web UI）

**设计参考（10 报告 4 节）**：交接物 = 带版本号的结构化卡片（JSON/Markdown artifact），不是自由文本聊天记录——PM→开发用需求卡片（功能描述 + 输入/输出契约 + 边界条件清单），开发→QA 附带自测覆盖清单（改了哪些 + 对应场景 + 未测项），下游角色必须引用上游卡片才能开工，闸靠系统拦截（缺少上游 artifact 摘要则系统层拦截、不进入推理）不靠 agent 自觉。理论依据：MetaGPT 的 SOP 编码（下游消费上游文档不能跳过）+ SWE-agent 的 ACI 概念（交接物应是机器可解析的结构化记录，非自然语言文档）。

**设计参考（09 报告 4.2 节）**：建 MR 阶段最小工具面四件套——建 MR / 发评论 / 行内讨论 / 合并，其中「合并」仍受人审 ADR 0001 约束（智能体可提议合并但执行须用户显式确认）。
**设计参考**（11 报告 §5/§6 设计原则 8——外部能力接入点）：E 期流水线各环节设计为可替换的外部能力接入点——代码生成可以是 DevDesk 自建 agent 也可以是 Claude Code via MCP，需求解析和代码审查不自建（Claude Code 已有 code-review skill、社区 MCP Server 已有成熟实现）。编排和集成才是 DevDesk 的价值，不是重新发明这些组件。
**设计参考**（12 报告第 11 章——角色交接 Handoff）：PM→开发→QA 角色间交接用结构化 Handoff 四类信息——目标（Goal+Acceptance）、已知事实（Structured Facts & Decisions）、待处理项（Plan/Todo/Blockers）、可用引用（Workspace/Artifact Manifest + 上游卡片引用）。下游必须引用上游交接卡片才能开工，靠系统拦截（缺少上游 artifact 摘要→不进推理），不靠角色自觉。
**设计参考**（12 报告第 4/11 章——团队级停止条件）：E 期流水线增设全局停止条件——总时间/成本预算、最大委派深度、连续无新增有效产物轮次、派生任务数、单任务重试次数，不能只有单 Agent 的迭代上限。停止条件满足时流水线整体终止并产出未完成清单，不平滑降级继续跑。
**设计参考**（12 报告第 16 章——QA 测试闸仿真三模式）：QA 角色测试闸采用仿真三模式——回归测试用全替身（便宜可复现）、端到端用隔离真实依赖（在独立工作区里跑真实构建与测试、不触达未授权生产环境）、混合模式按场景选。前提：用户模型（Persona+认知状态+行为策略）经过质量控制；仿真结果不直接等于发布授权——同一份证据包给质量、合规、回归三个视角各自解读，不混层。

**验收要点**：从一份需求文档出发可产出完整任务分解 → 代码变更内容 → 测试结果 → GitLab 合并请求链接，全链路可追溯、每阶段有通过 / 失败的明确信号。

## 四、明确不做（防过度设计）

| 不做 | 理由 |
|---|---|
| 多智能体并行编排 | 单个智能体反复跑已经覆盖当前任务粒度；多智能体编排带来调度、通信、死锁和调试成本，当前使用强度撑不起来 |
| MCP 全协议（自己实现完整的 MCP 协议栈） | 当前工具约 21 个，不需要 MCP 协议的动态发现和协商层；做多了增加维护面和调试难度 |
| 持久化事件队列（错过不补） | 跟定时规则「错过不补跑」的既有设计一致；离线补偿是另一套复杂度，推到有真实需求再说 |
| 流式响应（一个字一个字往外蹦） | 智能体是后台执行者没有对话窗，一次性返回结果就够了；流式只在人机对话场景有价值 |
| 自动合并 MR | 决策记录卡 ADR 0001 已定：合不合并由人决定，不自动 |

## 五、维护规则

1. 改这份计划必须留痕：决策变了写新的决策记录卡（ADR），记下理由和影响面；批次微调（拆分/合并子批、调整配对顺序）在各期详细方案开头记录，不用另写记录卡。
2. 各期详细方案从本计划长出，不得与本计划的档位和边界冲突。如果实现时发现必须突破本计划的边界，先走决策记录卡流程改本计划，再来写详细方案。
3. 冲突裁决顺序：决策记录卡（ADR）> 本计划 > 各期详细方案。凡本计划与决策记录卡矛盾，以决策记录卡为准。
