# 05-技术路线图

> **截至**：2026-10-21  
> **性质**：战略路线图，是后续各期实现 spec 的唯一派生来源。术语见 GLOSSARY.md；硬边界（流水线终点、文件工具范围、GitLab 分档）见 docs/adr/ 下的 0001、0002、0003。  
> **所属套件**：战略规划基线（docs/strategy/），与业务功能清单、技术能力清单、软件架构清单、流程场景清单四份文档共同构成智能中枢开发拍板的唯一底稿。

## 一、背景与目标形态

**现状**。智能体已具备六种触发类型（手动、定时 cron、每天、闹钟、事件、常驻）、约 21 个内置工具、事件触发（首批三个动作事件：todo.created / todo.completed / md.saved，含冷却窗口）、任务级记忆（context note）、预算护栏（单次运行墙钟上限 + token 上限 + 单一闸 startRunExclusive）与三表审计（运行记录 / 工具调用 / 错误日志）。能力面已铺开，当前瓶颈在「用起来顺不顺」而非「能力够不够」。功能全貌详见业务功能清单，技术资产详见技术能力清单与软件架构清单，运行流程详见流程场景清单。

**目标**。智能中枢的终极形态是 PRD→MR 流水线：智能体承担 PM（需求澄清与任务分解）、QA（测试与审计）、开发（实现）的角色分工，从产品需求描述出发，产出 GitLab 合并请求（MR）交人审查合并。途中每一步都带内建质量闸（独立审计、先红后绿、预算护栏），最后一道门永远是人（ADR 0001）。

## 二、已拍板决策

## 三、分期路线（A → E）

> 以下各期批次划分可在各期 spec 时微调（拆分/合并子批），但档位与边界以 ADR 为准、不可动。B 与 D 的交错配对顺序在 B 期 spec 时落实。

### A 期（收口）

**目标**：把现有功能收到「顺手」——触发呈现统一、任务可定制、异常原因可见。

**内容清单**：
1. **触发类型呈现统一**。六种触发类型收口为四类界面呈现：手动 / 时间（下分三种模式：时刻表 cron、每天、闹钟一次性） / 事件 / 常驻。底层配置机制不动，仅改呈现层。
2. **任务新增「角色设定」字段**。每条任务可编辑自己的系统提示词（任务级 role setting），区别于 Harness 层全局系统提示词。AI 草稿同步升级：从只生成目标一句话，升级为生成完整提示词组（目标 + 角色设定 + 记忆建议），权限与迭代上限仍不采纳模型建议。
3. **撞闸与失败原因可见性补齐**。每次「没跑成」（被单一闸拦住、触发条件不满足）或「跑了但失败」的原因，界面上都能看到，不含糊。

**验收要点**：触发配置呈现四类统一、草稿三件套（目标 / 角色设定 / 记忆建议）可用、每次「没跑 / 失败」都有可读的原因文案。

---

### B 期（对接能力）

**目标**：给智能体接上外部世界——文件、搜索、GitLab。分三批，每批配 D 期一块能力。

#### B1：文件工具组 + 事件扩容第一批

- **文件工具组**：list / read / write / move，仅限专用工作区（ADR 0002）。超出工作区的路径一律拒，不设例外。
- **事件扩容第一批**：在现有三个动作事件之外，补齐写路径的核心事件。候选：todo.updated、md.created、claude.profile_switched、app.started 等，具体清单在 B1 spec 时锁定。

#### B2：搜索工具 + 事件扩容第二批

- **搜索工具**：面向外网受限环境的搜索源设计。具体搜索源（本地 FTS5 索引、内置文档、受限外网 API 等）在立项时拷问，本文档不预设。
- **事件扩容第二批**：B1 之后剩余的场景事件补全。

#### B3：GitLab 只读工具组

- 列 MR / 读 diff / 读流水线（ADR 0003 第一档）。这三项读取不产生外部可见副作用，首期即做。

**验收要点（全 B 期）**：新工具按既有注册机制接入即可被任务使用（破坏性动作仍受全局授权闸管控，按工具白名单留 C 期）；文件工具写入只落工作区、读业务数据路径被拒；GitLab 只读三件套可正常拉取 MR 列表与 diff 内容。

---

### C 期（扩展机制）

**目标**：把「加一个新工具 / 新事件」从改核心代码降为配置级操作。

**内容清单**：
1. **脚本桥 script.run 决策**：按 D-R2 的验证结果决定是否立项。若立项——白名单目录 + 超时 + 输出截断，它要推翻「零子进程依赖」的既有决策，立项时必须另写一条 ADR 记录理由与约束；若验证未通过则放弃此路线。
2. **技能清单导入器**：自动把 skill 目录（含工具声明与事件订阅）注册进智能体运行时，不再要求每个新 skill 都改注册代码。
3. **权限升级**：从全局 `allow_destructive` 开关升级为按工具白名单——每个工具在任务级可独立授权（读 / 读写 / 禁用），破坏性工具默认禁、须显式开。

**验收要点**：导入器可把一个新 skill 目录注册出可用的工具与事件，不手写注册代码；工具白名单可逐工具控制，不依赖全局开关。

---

### D 期（自主性）

**目标**：让智能体少问人——自动重试、自评验收、自唤醒、失败通知。D1-D4 穿插于 B/C 各批之间交付，不与它们绑死顺序。

**内容清单**：
1. **D1：失败自动重试**。任务级可配重试次数与间隔。仅对瞬时错误（网络不通、上游 5xx、超时）触发重试；业务逻辑错误（工具返回了有效结果但语义不对）不重试。
2. **D2：验收自评**。任务新增「什么算做完」标准字段（自由文本，用户填写）。运行结束前强制模型对照标准自检；不够格时带上一轮的教训自动重跑，一轮为限——重跑一次仍不过就停、标失败，不无限循环。
3. **D3：自唤醒工具**。智能体自主安排「稍后再看一眼」——复用既有一次性触发（闹钟）载荷机制，以工具形态暴露给模型。与用户侧排程的闹钟区分：自唤醒是智能体在运行中自主安排的后续触发。
4. **D4：失败升级通知**。重试仍败时通知用户，带失败原因与已试过的手段清单。

**验收要点**：瞬时错误可自动重试成功、非瞬时错误重试后正确停；验收自评不过时可见「教训 + 重跑」一轮记录；自唤醒工具可创建一次性的后续触发。

---

### E 期（PRD→MR 流水线）

**目标**：智能体承担 PM / QA / 开发角色分工，从 PRD 走到 MR。

**角色模型**：每个角色 = 独立的系统提示词 + 工具子集 + 阶段闸。PM 负责需求澄清与任务分解；开发负责实现；QA 负责测试与审计。三个阶段串行推进，上一阶段产出经质量闸后才进入下一阶段。

**流水线路径**：PRD 输入 → PM 产出任务分解 → 开发产出代码改动 → QA 产出测试与审计结论 → 建 MR。全程内建质量闸（独立审计、先红后绿、预算护栏），MR 留人审合并（ADR 0001）。

**本文档不预设的项**（E 期立项拷问时定）：
- 试点项目选型（哪个仓库 / 哪种需求类型先跑）
- 角色切分粒度（PM 与 QA 是否合并、开发是否再拆前后端）
- 人审界面（审查 MR 时的交互是 DevDesk 内置还是走 GitLab Web UI）

**验收要点**：从一份 PRD 出发可产出完整任务分解 → 代码 diff → 测试结果 → GitLab MR 链接，全链路可追溯、每阶段有通过 / 失败的明确信号。

## 四、明确不做（防过度设计）

| 不做 | 理由 |
|---|---|
| 多智能体并行编排 | 单智能体迭代已覆盖当前任务粒度；多智能体编排引入调度、通信、死锁与调试成本，当前使用强度撑不起 |
| MCP 全协议 | 当前工具数量约 21 个，不需要 MCP 协议的动态发现与协商层；过度引入增加维护面与调试难度 |
| 持久化事件队列（错过不补） | 与 cron「错过不补跑」的既有语义一致；离线补偿是另一套复杂度，推迟到需求实证后再讨论 |
| 流式响应 | 智能体是后台执行者（无对话窗），批式响应足够；流式只在对话式交互场景有价值 |
| 自动合并 MR | ADR 0001 已定：合并决策保留给人，不自动合并 |

## 五、维护规则

1. 本路线图改版时，决策来源必须回写：决策变更走新 ADR 记录理由与影响面；批次微调（拆分/合并子批、调整配对顺序）在各期 spec 开头记录，不另写 ADR。
2. 各期实现 spec 从本文档派生，不得与本文档的档位与边界冲突。若实现 spec 发现必须突破本文档边界，先走 ADR 改本文档，再来写 spec。
3. 冲突裁决顺序：ADR > 本文档 > 期 spec。凡本文档与 ADR 矛盾之处，以 ADR 为准。
