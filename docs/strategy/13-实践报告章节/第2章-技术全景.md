# 第2章 技术全景：用了什么、做出了什么

DevDesk 是一个用 C++20 编写的跨平台桌面应用——C++20 是 C++ 语言的最新标准版本（2020 年发布），相当于这门语言的"最新版语法规则"。目标平台是 macOS（Apple Silicon）和 Windows 11。截至 2026 年 10 月 21 日，项目在约一个月的密集迭代中累计 1911 次提交（写作当日实测），交付了七个页面模块、110 余条可用的业务功能（截至 2026-10-21 清单口径），以及约 1600 余条自动化测试（截至 2026-10-19 全量运行数据）。这些数字本身并不重要——重要的是，这一整套软件产品完全由一个不懂 C++ 的人通过 AI 编程助手驱动开发完成，并且项目在其知识总量已超出任何单个人类掌握范围之后，仍然稳定地持续迭代。本章的任务，是用非技术读者也能理解的语言，把构成这个项目的技术积木、开发环境、以及最终交付的功能成品铺陈清楚，为后面各章讨论"怎么做到的"建立共同的认知基础。

## 2.1 技术栈：四层结构，每层只管自己的事

DevDesk 的代码组织遵循一种严格的四层分层设计。理解这四层，是理解整个项目技术架构的钥匙。

（图 2-1，见同名 SVG 文件）

**最上一层是业务模块层**，也就是用户实际能看到、用到的功能入口。目前共有七个模块：首页仪表盘、Markdown 笔记本、Todo 待办看板、Claude 配置切换器、智能体任务系统、设置页、关于页。每个模块是一个独立的"房间"——各有自己的数据、自己的界面逻辑、自己的测试用例，彼此之间不能互相调用。这种隔离不是技术洁癖，而是经验教训的产物：当多个功能模块互相依赖时，改一个模块就可能波及另一个模块的界面出错，而这类错误在 AI 并行开发多个模块时尤其难以在提交前发现。七个模块中，首页、设置、关于这三个模块被设计为"恒注册"——用户不能关闭它们；其余四个模块（笔记、待办、Claude、智能体）可以通过设置页的开关自由启用或禁用，禁用后该模块的界面入口和后台逻辑完全卸载。

**向下一层是核心层（core）**。这一层提供所有模块共享的基础设施，但它自己没有任何"业务知识"——不知道什么叫做笔记、什么叫做任务。它只提供最通用的能力：统一的错误处理机制（为什么不用 C++ 传统的抛异常？因为 AI 在调用链中容易漏掉异常捕获点，返回一个"成功或失败"的结果值比异常路径更容易被 AI 正确覆盖）、SQLite 数据库的打开与迁移管理、文件路径的跨平台解析、应用主题色的管理、以及页面路由的注册与分发。核心层的设计红线是"不能依赖上层"——它不能调用平台层的网络请求，也不能使用 GUI 框架的任何运行时功能。这条红线保证了核心层在任何时候都可以被单独测试，不受平台差异和界面框架变动的影响。

**再下一层是平台层（platform）**。这一层的职责是包装操作系统特有的能力，对上提供统一的、跨平台的接口。例如：HTTP 网络请求（基于 libcurl 库，负责所有对外通信——Claude API 调用、网页内容抓取、GitHub 仓库同步都经过它；OpenSSL 负责这些通信的加密，确保数据在网络传输中不被窃听）、本地 HTTP 代理服务（基于 cpp-httplib 库，让 Claude Code 客户端把 API 请求先发到 DevDesk，经流式转发到真实的 AI 服务端点）、操作系统的安全凭据存储（macOS 上走钥匙串 Keychain，Windows 上走 DPAPI——后者是 Windows 系统自带的数据保护接口，用当前登录用户的身份信息做加密密钥，保证 API 密钥不会被明文读取）、以及 JSON 数据的解析与序列化。平台层的物理文件组织也遵循一条严格的纪律：头文件定义平台无关的接口，具体实现按操作系统拆分成独立文件（Windows 的实现文件后缀为 `_win`，macOS 的为 `_macos`），编译时由构建系统按目标平台自动选择。业务代码中不允许出现 `#ifdef Windows / #ifdef macOS` 这样的条件分支——这条规则来自一个反复出现的事故模式：AI 在某个平台上写完代码后，往往只在当前平台编译验证，另一平台的代码路径从未被执行过，直到合并后才在 CI（持续集成，指代码提交后自动触发构建与测试的机器人）上暴露错误。

**最底层是 GUI 框架 EUI-NEO**。这是整个技术栈中比较特殊的一层——它是 DevDesk 项目维护的一个开源跨平台界面库（基于 sudoevolve/EUI-NEO 的定制分支），相当于网页开发里的 React 或 Vue，但运行在操作系统的原生图形层上——通过 OpenGL（操作系统提供的一套标准画图指令，直接操控显卡渲染界面）来绘制所有控件。它提供了应用开发所需的基础界面控件：按钮、输入框、下拉菜单、开关、表格、图表、对话框、侧边栏、虚拟列表等，总计约 50 种可用的组件类型。同时它也处理窗口管理、字体加载、DPI 缩放、鼠标与键盘事件分发等桌面应用最底层的脏活累活。DevDesk 不把 EUI-NEO 当作一个"拿来用就行"的黑盒子——项目中有一条明确的上游贡献政策：凡是遇到 EUI-NEO 自身缺陷造成的界面问题，优先在 EUI-NEO 仓库里修复，再让 DevDesk 受益。这种做法避免了"在应用层打补丁绕过框架 bug"的常见陷阱——补丁会不断堆积，最终让项目绑死在框架的一个特定版本上无法升级。

**四层之间的依赖铁律**：只能上层依赖下层，不能反过来。业务模块可以调用核心层和平台层的任何功能；核心层不能依赖平台层，也不能使用任何 GUI 框架的运行时行为；平台层可以调用核心层，但不能调用业务模块。在上面四层之外，还有一个最顶层的入口文件（main.cpp），负责初始化窗口、注册所有模块、启动应用主循环。这个文件是整个程序的"总开关"，但它不包含任何业务逻辑。

**为什么需要这么严格的分层？** 在纯人工开发的项目里，分层是一种常见的最佳实践，但通常依赖工程师的自我约束来维持。在 AI 驱动的项目中，这条纪律的紧迫性急剧上升：AI 在修改代码时天然倾向于"哪里能用就往哪里写"，如果没有硬性的分层规则约束，它会在一个本该只处理网络请求的文件里顺手塞进一段界面更新逻辑——当时看起来省了一步，但当这个网络模块需要被另一个界面模块复用时，那段"顺手塞进去"的代码就成了污染源。分层的本质不是增加复杂度，而是用结构代替记性——边界清晰了，AI 在每条边界内部的犯错成本就局限在该层内部，不会蔓延成跨层的连锁错误。

## 2.2 AI 开发环境：不止一个 AI 在工作

理解 DevDesk 的技术全景，不能只看代码本身——还需要理解 AI 是如何与这套代码交互的。

（图 2-2，见同名 SVG 文件）

**AI 编程助手的角色**：DevDesk 使用的 AI 编程工具是 Claude Code——一个命令行界面的 AI 编程助手，能够阅读代码仓库、写代码、运行构建命令、派发子任务给其他 AI 会话。用户通过自然语言向它描述需求（"加一个导入文件的功能""把设置页移到侧边栏"），它在理解意图后自主完成从代码编写到测试验证的全流程。用户本身不写代码、不读代码、不跑编译——这在第 3 章会详细展开。

**多条 AI 会话并行工作**：实际开发中，同一时刻往往有多条 AI 会话在并线干活——一条在修笔记模块的搜索 bug，一条在给智能体模块加新工具，一条在做全量代码审计。它们共用一个代码仓库，但不能互相干扰。解决这个问题的机制叫 git worktree（工作区隔离）：每当 AI 接到一个需要修改代码的任务，它就在独立的工作区副本中工作——相当于从主代码仓库复制出一份临时副本，在那里面修改、编译、测试、提交，全部完成后才把结果合并回主仓库，随即删除临时副本。这意味着每个 AI 会话都活在自己的"沙盒"里——它看到的文件状态是干净、一致、不受其他 AI 干扰的。这个机制是 DevDesk 能够同时跑 8 个并发子任务而不互相踩脚的基础。

**编译与缓存**：DevDesk 在 Windows 上使用 MSYS2 MinGW64 编译器（GCC 的 Windows 移植版），在 macOS 上使用 Apple 自带的 AppleClang 编译器。从源码到可运行程序的构建过程由 CMake（一个跨平台的构建管理和配置工具，负责描述"哪些源文件编译成哪些目标、要链接哪些库"）驱动。但 AI 开发有一个独特的问题：每次派一个新任务就要建一个新的工作区副本，如果每个副本都从头完整编译，时间开销会让开发节奏不可接受。解决方案是 ccache（编译缓存）：它会记住每次编译的结果，当同一个文件在另一个工作区里再次被编译且内容没变时，直接复用上次的结果，跳过实际编译步骤。在没有缓存时，两个工作区的同一份源码会被认为"不同"（因为它们的绝对路径不同，而编译命令里包含了路径），导致缓存永远无法命中——解决这个问题的关键技术细节是让缓存把不同工作区的路径"翻译"成同一个逻辑路径后再比对。这个话题的技术细节超出了本报告的讨论范围，但其后果对开发节奏至关重要：有缓存时，一个全新工作区的构建时间从十分钟级降到一分钟左右。

**双平台 CI 守卫**：每次代码提交到集成分支时，GitHub 的自动化流水线（CI，即持续集成）会在 macOS 和 Windows 两条独立的虚拟机上各跑一次完整的"构建 + 全量测试"。如果任一平台失败，提交会被标记为不可合并。这条机制是 DevDesk 能够同时维护双平台而不出现"这边修好了那边崩了"的基础保障——它不是靠人记着"Windows 上也得验一下"，而是靠机器自动拦。

## 2.4 技术全景小结

把上面这些信息收束成一句话：DevDesk 的技术基底是 **C++20 原生桌面应用**，靠四层分层的代码结构维持模块之间的边界清晰；它的开发环境是 **多条 Claude Code AI 会话并行工作**，靠工作区隔离和编译缓存保证效率；它的交付物是 **六个全功能业务模块加一个信息页**，覆盖了笔记写作、任务管理、AI 配置切换、后台智能体自动化四类核心场景，在 macOS 和 Windows 上均有原生的安装包交付。

这些技术选择背后有一个贯穿始终的设计原则——本文称之为"为 AI 开发而设计"：每一项技术决策都不仅回答了"这个技术能不能做到"，更回答了"这个结构在 AI 不断修改代码的过程中，能不能自己守住自己的边界"。分层结构守住了模块之间的边界，平台抽象守住了操作系统之间的边界，工作区隔离守住了并发任务之间的边界，编译脚本封装守住了构建路径的边界。在全部章节中，本章只负责画地图——把"有什么"铺在桌面上。从下一章开始，报告将逐一展开"怎么做到的"——人怎么操作、AI 怎么执行、机制怎么防错、事故怎么变经验、系统怎么审计、别人怎么照搬。
