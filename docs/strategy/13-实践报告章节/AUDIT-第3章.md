## 【必改】

### B1. 图 3-1 viewBox 高度超 A4 版心可用高度

- **定位**：`图3-1.svg:1` — `viewBox="0 0 500 840"`
- **问题**：A4 纵向页面在两侧各 20mm 页边距后，版心宽约 170mm。SVG 配 `max-width:100%` 等比缩放：170mm 宽时，高 = 840 × (170/500) ≈ **285.6mm**。A4 可用高度约 247mm（297mm − 上下各 25mm 页边距）。285.6 > 247，**超出约 38mm，会被裁或顶入页脚**。大纲 §零铁律："图不许超页宽被裁——硬红线"；超页高同理。
- **精确数值**：170mm 版心宽下，viewBox 高上限 = 247 × 500/170 ≈ **726**。当前 840 超标约 16%。
- **建议改法**：方案 (b) 压缩纵向间距，把 viewBox 降至 `"0 0 500 715"`（渲染高约 243mm，留 4mm 余量不贴边）。具体改动：
  - 主流程 8 个节点的 y 间距从 ~38px 压缩到 ~22px（每段省 16px × 7 = 112px）
  - 左侧回馈三节点（用户反馈/排查修复/重新交付）间距从 24→14（省 20px）
  - 图例区从 66px 压缩到 48px（省 18px）
  - 底部留白从 ~9px 压到 ~0（省 9px）
  - 总计瘦身约 159px → 新 viewBox 高度 = 840 − (840−715) ≈ **715**，渲染高 = 715×0.34 ≈ **243mm**，不超版心。
  - 若写手偏好宽松间距：备选方案 (c) 加宽 viewBox 到 `"0 0 550 720"`（宽增 10%，渲染高 = 720×170/550 ≈ 222mm），纵向间距可基本不变、只需微调。
- **注意**：大纲要求"泳道图，两条泳道（用户 / AI 系统）"，当前 SVG 用"用户侧 / AI 系统侧"文字标注代替垂直分界线，功能等价但视觉上不算标准泳道——**不强制改为标准泳道线**，但若改 viewBox 时一并补上左右分界竖线会更贴近大纲意图。

### B2. SVG 文字尺寸边界

- **定位**：`图3-1.svg` 全文
- **问题**：所有文本 `font-size` 为 12/13/15，满足 ≥12px。但图例两行 `y=814` 行距仅 26px（788→814），与 12px 字号比偏紧。**不构成排版错误**，但若 B1 的压缩操作波及图例高度时需留意不要进一步挤压。
- **建议改法**：压缩时优先压主流程间距，图例保持当前行距。

### B3. "约 27 个独立提交"数字需标注日期

- **定位**：第3章 L83 — "约 27 个独立提交"
- **问题**：大纲 §零铁律要求"数字一律以写作当日实测为准并标注日期"。`git log --oneline --grep=UAT6` 实测返回 **23** 个提交（2026-10-21）。"约 27"与 23 偏差约 15%，在"约"的容差内但缺日期标注。且"27"的来源不明——可能写手统计口径更宽（含 UAT6 前后的关联提交），但未在文中交代。
- **建议改法**：改为"约 20 多个独立提交（截至 2026-10-21）"或直接引证最精确的 `f7747f09`（Toast 13 处删除）和 `ea1fbfe2`（弹窗按钮底钉定）两个提交的 message 摘要，不堆总数。

### S1. "不做清单"中"不编译"表述可更精确

- **定位**：第3章 L93 — "不跑编译。用户不碰构建工具，不配置开发环境。"

- **建议改法**：L93 首句改为"不跑构建（把代码变成可运行程序的过程）"，后文"编译"统一为"构建"。或保持当前不动——当前解释已充分。

### S2. 案例一"540 像素"的具体数字溯源

- **定位**：第3章 L113 — "实际可用高度只有大约 540 像素"
- **问题**：源 commit `ea1fbfe2` 的 message 写"组件内建 clamp 后子布局仍按请求高 600 定位"，未出现 540。540 可能是写手从窗口最小高度 640 反推（640 − 标题栏约 28 − 弹窗外边距 − 弹窗标题栏内边距 ≈ 540），推算合理但与源数据不完全对齐。不构成事实错误，但若读者细究会发现源 commit 只有 600 没有 540。
- **建议改法**：改为"实际可用高度远小于请求高度"（去掉具体数字），或改为"弹窗内建了尺寸限制但子布局仍按请求高度 600 排版，于是按钮被挤出画面"（对齐源 commit 原文）。

### S3. 案例二 Toast 删除"13 处"可留但需标源

- **定位**：第3章 L125 — "全量扫描了待办模块中所有成功类提示，一共 13 处"
- **问题**：源 commit `f7747f09` 的 message 逐条列出了 13 处删除项，数量完全一致。这个数字是案例的核心细节，保留合理。但按大纲铁律应标"截至 2026-10-20"（commit 日期）。
- **建议改法**：在"一共 13 处"后加"（截至 2026-10-20）"。
