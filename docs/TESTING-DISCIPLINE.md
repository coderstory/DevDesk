# 测试纪律：防回归目的论（2026-10-31 老板定调，主会话扩充成文）

> 核心两句（老板原话为纲）：**避免形式主义，每个测试都必须有目的——防止特定功能、特定场景、特定边界出现回归**；**不看行覆盖率，看功能的场景覆盖情况、边界的覆盖情况**。

## 一、测试是什么

测试证明不了「程序正确」——它只证明「已经踩过的坑不会再踩」。因此每条用例的本质是一份**已知失败的清单条目**：谁（功能）、在什么情形下（场景）、踩了哪条线（边界）。

由此推出三条例外不了的结论：

1. **没有教训来源的用例不存在**。写不出「防什么回归」的用例，就不是测试，是仪式。
2. **覆盖率是副产品**。行覆盖率是「跑过」的度量，不是「验证过」的度量——跑过≠断言过，断言过≠防住了未来的回归。90% 行覆盖照样漏「并发时序」「空列表首元素」「断网重试半途」；反过来，一条精准的边界用例可能只覆盖 3 行代码，却防住整条业务线的资损。
3. **测试是负资产当且仅当它无目的**。每行测试代码都要跟随重构维护，假绿安全感比没有测试更糟（训练团队忽视红）。

## 二、度量什么：功能 × 场景 × 边界覆盖矩阵

不量化行覆盖率，量化**格子**：

| 维度 | 含义 | 例 |
|---|---|---|
| **功能** | 用户/系统可感知的行为单元 | 「归档 todo」「预算耗尽暂停提炼」「事件触发冷却」 |
| **场景** | 该功能被触碰的情形 | 正常流 / 重复触发 / 断网 / 配额耗尽 / 多 worktree 并发 |
| **边界** | 该情形下的临界点 | 空列表 / 首尾元素 / 数值恰等阈值 / 动画首帧与最后一帧 / 平台差异 |

- **一格一条用例**（或一组）：用例名应能读出「功能-场景-边界」三元组，读不出就是签名失败。
- **格子是明账**：每功能的清单卡（`docs/superpowers/plans/<slug>-dev-tests.md`）列已钉住与未钉住的格子；未钉住的格子不是错误，是**明账欠债**——显式记录，不假装覆盖了。
- 度量问题从「覆盖率多少」换成：「这个功能，哪几类场景会咬人？各有没有用例钉着？」

## 三、生产：什么时候写、写什么

1. **清单卡先于实现**（现行流程已含）：需求流程的测试环节先出清单卡（F-ID=验收口径的执行形态），后写实现——用例即验收口径，不是实现完成后的补救。
2. **新增用例过三问**，答不出不写：
   - 防什么**功能**回归？
   - 什么**场景**触发？
   - 卡哪条**边界**？
3. **会红性铁律**：删掉被测代码，该用例必须红。不会红的用例要么测错了对象，要么是恒真仪式。
4. **回归用例的三大来源**（合法的教训来源）：
   - 修过的 bug——每 bug 一条回归用例（bug 池纪律已含）；
   - 重构防护——改动高风险区前钉住现行为（观察缝类，如池 15）；
   - 契约固化——跨模块/跨平台契约（如 telemem 信封解析、平台行为对称性）。

## 四、维护：测试会衰老

1. **flake 是慢性病**：偶发红的用例比没有更糟——它在训练人忽视红。flake 用例限时修（等待改事件驱动/放宽容差），修不动就降级隔离，绝不留在线内钝化警觉。
2. **断言不为绿而改**：行为变了，先问行为该不该变，再改断言；顺序反了=测试沦为回归的帮凶。
3. **定期问：这条用例防的回归还可能发生吗？** 防的场景被结构性消灭（功能下线、路径删除）→ 用例随之退役，不为存量数字留僵尸。

## 五、反模式清单（形式主义的具体长相）

| 反模式 | 长相 | 判 |
|---|---|---|
| 仪式用例 | `EXPECT_TRUE(true)`、断言恒成立、只调不断言 | 删 |
| 测实现细节 | mock 到只剩实现镜像，重构必碎、行为没验 | 改为测行为契约 |
| 覆盖率驱动 | 「这个分支没跑到，补一条」——无场景无边界理由 | 删 |
| 参数轰炸 | 复制粘贴改一个字符的 N 条用例，验证的是同一件事 | 合并为一条参数化+说明 |
| 僵尸用例 | 从未红过、也不对应任何真实教训来源 | 追溯三问，答不出退役 |

## 六、评审问句（把哲学变成检查动作）

对任何一条用例（或一份清单卡），依次四问：

1. **它防什么回归？**（功能-场景-边界三元组；答不出→删）
2. **它什么时候会红？**（构造得出触发条件吗；构造不出→仪式）
3. **它断言的是行为还是实现？**（重构后该活还是该碎？该碎=测错了）
4. **它还活着吗？**（防的场景今天还存在吗）
