# 三池 MCP 业务方案（需求分析群合稿 · 待老板娘审）

日期：2026-10-29 ｜ 主笔：惨品（业务） ｜ 技术：老学究 ｜ 状态：草案，批准前零代码

## 1. 背景 / 目标
替代 markdown 台账：三条池（需求池 / bug 池 / 待办池）入 SQLite，AI 团队工具级读写，人看生成视图。

## 2. 表结构（业务视角，细节由技术稿定）
- `needs`（主表）：id / pool(需求|bug|待办) / title / priority(P0-P3) / status / blocker / owner / created / updated / detail(指针) / body(摘要正文，10-30 裁决新增供 FTS 检索，详见决策文档修订条)
- 存储（10-30 更正）：池为独立 MCP server 自持 SQLite，`pool.db` 出 git（.gitignore），每次写后导出 `docs/pool/pool-snapshot.json` 入 git 留痕（双机各写本地 db，已实施 wt-pool-fix 38b65d66）；engram 仅作 schema 参照；sqlite-vec 后置
- 子表：`dev_progress` / `bugs` / `acceptance`，`need_id` 外键
- `status_log`：每次状态变更一行 → 溯源链（一条需求摸到进度/BUG/验收全链）


## 3. 状态机（P0-P3 按 10-29 分级规矩）
- **status 全集**：`在池 → 排产 → 进行中 → 待验收 → 关闭`，旁路 `挂起(blocker)` / `拒绝`
- **流转规则**：只有 P0 允许即时打断插队（尽量卡阶段边界）；P1-P3 按池排序排产，不许插队
- **关闭前置**：需求/BUG 须有 acceptance 记录才可关闭；拒绝须写明理由入 detail
- **挂起**：只许带 blocker 字段挂起，解除时 status_log 记录原因链

## 4. 池规矩
- **单写者**：同一时刻一个 Bot 写库（沿用既有纪律），UPDATE/INSERT 单行原子操作
- **查重铁律**：开工前先检索池内是否已有同类条目/现成方案，防重复入池；派单前先 grep dev + 查池做交叠检查，防两线撞单（10-30 需-6 双实现事故教训）
- **降级**：S 级需求不立项直接干（不进池）；只有 M/L 级入池走全流程
- **视图（老板 10-29 定）**：SQLite 数据自动生成 **HTML 报告**（三池状态/排产/溯源链可视化），浏览器直开，每次池更新后重生成；markdown 台账退役。生成走只读脚本，不手维护；日报由小辣椒顺带带出，不新增流程

## 5. 工具面（AI 读写）（老板 10-29 修订）
**MCP server 独立于 app**（独立进程 + 独立 SQLite 文件，不进 DevDesk——本 app 是开发对象频繁重启，池不能随它重启丢状态）。薄封装四工具：**入池 / 捞取(按 id) / 更新(状态+字段) / 检索(FTS5 关键词)**。全员可读，写走单写者纪律。

## 6. 人员关联
- `owner` 字段 = Bot 名（jQuery/辛勤码农/…），一条目一个 owner；跨协作在 detail 指针文档里记，不另建人员表（避免过度设计）

## 7. 非目标
- 不做跨表统计报表 UI（脚本生成即可）
- 不做 sqlite-vec 相似度（条目 < 百，FTS5 够）
- 不接 GitLab/敏捷平台（后置路线图）

## 8. 验收标准
- F-01 入池一条 M 级需求 → needs 一行 + status_log 一行「在池」
- F-02 该需求指派 jQuery 排产 → status 变「排产」，dev_progress 起记录
- F-03 进行中发现 BUG 入池 → bugs 表一行，外键回 needs，从需求能查到 BUG
- F-04 验收通过 → acceptance 一行 → status「关闭」，POOL.md 视图同步生成
- F-05 FTS5 检索关键词命中标题/正文；按 P 级/状态捞取可用
- F-06 任意池更新后 HTML 报告重生成，浏览器直开可见最新状态/溯源链；报告由脚本生成，不依赖手维护
