# 债-18「UI 交互链路自动化验证缺位」需求分析

> 日期：2026-10-31 ｜ 环节：需求分析（全流程第一环，产物待独立审计）｜ 作者：产品专家
> 池编号：债-18（TODO.md 旧编号 **债-2**，债-1~6 = 池 17~22 映射，见 TODO.md 头部）
> 性质：测试基建需求，不改任何用户可见功能

---

## 0. 需求一句话

让 AI 开发闭环里的 QA/研发角色能**用一条命令 + 一份场景描述文件**驱动 DevDesk 的点击/键入/滚轮/拖拽交互并拿到「逐步报告 + 截图 + 退出码」，使交互链路验收摆脱「只能用户手点」的现状。

## 1. 登记原文（池 18 / 旧债-2）

> qa/研发可自主实证启动/截屏/日志/数据/HTTP，但**点击/输入类交互无法自主执行**（当前按 AGENTS.md §八如实标「交互链路未验证」）。长期解法：给 DevDesk 建测试自动化驱动入口（CLI/IPC 触发页面与操作）。

### 2.2 缺口到底在哪（「无法自主执行」的精确含义）

注入能力**存在**，但它是 **C++ 库形态，不是驱动入口形态**。四层缺失：

1. **每条新交互链 = 一次开发任务**。要验证新交互，必须写/改一个 C++ probe → 改 CMake → 重编译 → 注册 ctest。AI 开发模式下 qa-tester 角色拿到的是二进制与脚本，没有 IDE，写不了 C++ probe——所以「点击/输入无法自主执行」：不是技术上不可注入，而是**指令无法当场下达**。
2. **无场景描述载体**。不存在「导航→点 id→键入→断言→截图」的场景文件与通用解释器；断言逻辑散落在各 probe 的 main() 里，无法复用、无法组合。
3. **定位靠硬编码坐标**。注入原语收裸 (x,y)。probe 内部虽可 `ui.find(id)->frame` 手算中心（EUI-NEO input_runtime_probe.cpp:211 即此做法），但没有「按元素 id 点击」的通用原语，更没有把当前页元素 id 清单 dump 出来辅助写场景的工具。
4. **射程止步于 probe 进程**。probe 自己 compose 模块页（个别 probe 链 app_assembly.cpp），`main → Router → 模块生命周期 → 真实侧边栏导航 → 托盘 → 多窗`的**真 app 进程**不在注入射程内。池原文说的「CLI/IPC」指的正是对真 app（或至少 app 级组装）的驱动入口。

另有一处环境缺口（次要）：CI 无 GUI 会话，probe 门禁全 77 跳过——交互链回归保护目前只存在于本地双机。

### 2.3 既有权威文档关联

- docs/superpowers/specs/2026-09-28-devdesk-probes-design.md —— probe 架构设计（真窗 + Runtime 注入三层断言），本需求是其**脚本化外壳**的延伸，优先扩展不另起炉灶。
- docs/superpowers/plans/2026-10-19-ui-test-gap-map.md —— UI 面缺口地图；其中 G1~G5 是「覆盖面」缺口，本需求解决的是「验证手段」缺口，两者正交。
- docs/EUI-NEO-CAPABILITIES.md —— 交互能力全列（onTap/onPress/onDrag/onKeyEvent/IME 等回调齐全）；框架**没有**现成的对外事件注入/驱动 API，但内部注入队列（core::queue*Input）被双侧 probe 长期使用，缝已验证。

## 3. 问题定义（谁在什么场景被阻塞）

| 受阻角色 | 场景 | 现状代价 |
|---|---|---|
| qa-tester（AI 子代理） | 验收走查：PRD 要求「用户操作流程照走 + UI 契约截图对照」 | 启动/截屏/日志/数据/HTTP 五类证据可自主采集；交互链类只能标「交互链路未验证」（AGENTS.md §八），验收结论不完整 |
| 用户（不熟 C++，纯 AI 开发） | 每轮 UAT（UAT62 已历 W0~W3.5 六轮） | AI 修一轮→用户手点验一轮，交互回归成本全部压在人身上；「改按钮位置导致点击失效」类回归只有用户能发现 |
| developer（AI 子代理） | 修 UI bug 后自证 | 只能靠无头单测模拟状态，无法自证「真点击后行为正确」，修复闭环缺最后一环 |

用户价值一句话：**交互链路验收从「提需求等人写 probe / 等用户手点」变成「一条命令当场出报告」。**

## 4. 方案空间（只列不选，选择留给技术方案环节）

| # | 方案 | 一句话优劣 |
|---|---|---|
| A | **CLI 场景驱动入口**：独立 driver 可执行（如 `devdesk_ui_driver --script scene.json`），进程内起真窗+Runtime，按场景文件步骤执行动作/断言/截图，退出码汇总 | 优：与 probe 同构、注入/截图/临时数据根/键码映射基建全现成、双平台一致；劣：测的是 driver 进程的组装复现，非真 app 全链；需定场景 schema |
| B | **IPC 注入运行中实例**：给真 DevDesk 开本地控制通道（platform::http_server 可复用），外部命令→主循环转 core::queue*Input→查询元素树 | 优：唯一能测真 app 全链（启动/托盘/多窗/真实导航）的方案；劣：生产代码常驻测试缝（安全面+主循环改动+双平台各验），测试关注点外溢到产品。**B-lite 变体（审计补）**：同一二进制 + `--ui-driver` 启动开关（默认关）可绕开「常驻缝」论据（platform::http_server 已被 mcp/claude_proxy 两个生产模块在用，进程内本地服务非架构异物）；B 的真难点实为 (a) UI 控制权注入的定性（远程操纵用户界面，与代理转发/MCP 工具不同）与 (b) HTTP 线程→主循环 `Runtime::update` 的跨线程注入 marshaling |
| C | **EUI-NEO 注入缝正式化**：把 queue*Input + `find(id)->frame` + 帧驱动提升为框架公开测试 API | 优：一次改动框架侧收益最大，顺带消除 probe_harness glfwKeyToInputKey 与 window_input_backend mapGlfwKey 的双份映射隐患；劣：只解决注入原语，不解决「谁下指令」，仍需 A 或 B 作入口 |
| D | **录制回放**：录真用户操作→生成脚本→回放 | 优：脚本获取成本低；劣：框架无录制基建，录制器本身即 L 工程，回放端仍要 A/B；本项目场景由 AI 编写比录制更精确，收益错配 |

**排序建议**（依据见 §5，最终取舍待技术方案 + 审计）：A+C 组合 ≈ 90% 核心价值候选；B 的「真 app 进程」部分建议进非目标（风险外溢生产代码，且 probe 已证明 app 级组装可覆盖多数验收场景）；D 进非目标。

## 5. 推荐方向与依据（方向建议，非技术选型定论）

**推荐方向：A（CLI 场景驱动入口）为主干，C（框架注入 API 正式化）为地基。**

依据：
- **同类产品先例**：Playwright/Selenium（driver + 脚本 + 退出码 + 截图是行业标准形态）、Flutter `integration_test`（框架内注入，非 OS 级事件合成）。
- **本软件一致性**：probe_harness.h 已是「进程内注入 + 断言 + 截图 + 诚实跳过」的事实标准，driver 是它的脚本化外壳而非新范式；临时数据根（test_support.h DataRootEnv）、退出码纪律（0/1/2）、Skipped 单独计数全部沿用既有惯例。
- **可行性已被 POC 级实证**：五类注入原语 + 真点击链在 5 个以上在库 probe 中长期运行，无需再 POC（此为「已 POC 验证」项）。
- 技术选型（场景文件格式 JSON/YAML、driver 是否复用 probe_harness 编译单元、EUI-NEO API 暴露面）**待确认**，留技术方案环节。

## 6. 非目标（明确不做）

| 不做什么 | 理由 |
|---|---|
| OS 级事件合成（SendInput / CGEvent / xdotool 类），不控制任何第三方应用 | 平台强耦合、权限面大（macOS 辅助功能授权）、且框架内注入已够用 |
| 远程桌面式全 GUI 自动化、图像识别找控件（OCR / 像素模板匹配） | 元素 id 是 DOM 级可靠定位源，图像识别是伪需求 |
| 录制回放（方案 D） | 收益错配（见 §4） |
| 多窗口/独立子窗驱动（module_* 独立子窗、弹层第二窗） | 本期不做：主射程=app 组装内模块页；子窗注入射程留开放问题 7，待技术方案定 frame 树遍历范围后裁决（审计 P1-2 补；2026-10-31 编号勘误：原文误标"开放问题 8"，实指 §13 第 7 条） |
| OS 原生控件交互覆盖（系统文件对话框、原生托盘菜单、IME 候选窗） | 不在 Runtime 命中链内，属平台层；如实标注不可测即可 |
| 替代无头单测 / 既有 probe；回补 2026-10-03 轻量化裁决删除的 8 个 probe 面 | 覆盖面缺口（G1~G5）与本需求正交，各有各的补法 |
| CI 无显示环境的离屏渲染（xvfb / OSMesa）承诺 | 现状「诚实跳过」不劣化即可，离屏方案作为开放问题单列 |

## 8. 用户操作流程（验收照走）

以「todo 新建任务」为例的一条场景（示意，非格式定稿）：

```
1. 用户（或 qa-tester 子代理）写场景文件 scene-todo-new.json：
   前置：临时数据根；动作：切到 todo 页 → 点 "todo.board.new"（id）
        → 键入 "缴费" → 按 Enter → 断言列表出现含「缴费」的卡片 → 截图
2. 执行：bash scripts/build-test-run.sh 之外或之内，一条命令跑该场景
3. 读结果：逐步报告（每步 pass/fail + 中文原因）+ 截图文件 + 退出码
4. 验收方（审计/qa/用户）只需看报告与截图，不需要人手点一遍
```

验收时审计者照此流程独立跑一条自选场景，确认「写场景→跑→看报告」无 C++ 环节。

## 9. 完整状态集（自查清单）

**命令行入口（本需求的「界面」）**：

| 状态 | 预期 |
|---|---|
| 空态：场景文件 0 步 / 空文件 | 报错退出（非 0），提示「场景无步骤」——防假绿，对齐 devdesk_tests 0 命中退 2 口径 |
| 错误：场景文件不存在 / JSON 解析失败 | 非法入参退出码，stderr 中文指出文件与行 |
| 错误：id 不存在 | 该步 fail，stderr 给出「相近 id 候选」（来自元素树 dump），场景继续或中止由失败策略定（待方案） |
| 错误：断言失败 | 该步 fail + 截图留证（失败现场截图价值最高），退出码非 0 |
| 边界：超时（wait 上限 / 单步驱动超时） | 步骤 fail + 中文超时原因，不挂死（ctest 超时兜底之上还要自身兜底） |
| 边界：超长文本键入 / 元素在滚动容器视口外 | 键入原语按 UTF-8 全量注入（queueText 语义）；视口外元素 = frame 中心仍在 DOM 坐标内可点（待方案确认是否需要滚动到位原语） |
| 边界：首次运行（无既有数据） | 临时数据根为空 → 页面空态本身即被测状态之一，场景可断言空态 |
| 平台差异：macOS / Windows | 注入原语走 core::queue*Input，框架层已双平台；GLFW 键码映射双平台一致；**验收必须双平台各跑同一条场景**（AGENTS.md §三硬约束） |
| 环境缺失：无显示会话（CI） | 金丝雀判定 → 退出码 77 = Skipped，诚实跳过不假绿 |

**可撤销性**：场景跑在临时数据根，进程结束即弃，天然不污染真实数据——无需 undo 设计。

## 12. 规模预估：M

**理由**：
- 五块核心基建（注入原语、帧驱动、截图、临时数据根、键码映射）**全部现成且已被在库 probe 实证**，剩的是场景 schema 定稿 + 步骤解释器 + id 定位封装 + id dump + 门禁接线——组装型工程，非能力攻坚。
- 抬出 S 的因素：新增可执行目标与 CMake 接线、场景格式是长期契约需独立审计、双平台验证义务、EUI-NEO 侧若采纳方案 C 有跨仓提交。
- **若 F-09（真 app 进程 IPC）被拉回范围则升 L**（生产代码改动 + 安全面 + 双平台主循环接线）；本分析建议其保持非目标以守住 M。
- **若方案 C 全量正式化**（EUI-NEO 公开头文件 API + 框架文档 + 双仓发布纪律）则按 **M 上限~L 下沿** 排期（C 暴露面现自标「待确认」，升档条件与 F-09 对称，审计 P2 补）。

## 13. 开放问题（留给技术方案 / 审计）

1. 场景文件格式（JSON / YAML / 自定义 DSL）与失败策略（fail-fast vs 收集全部失败）。
2. 元素 id 稳定性契约：场景引用的 id 要不要登记表（TIN-10 式 configure 期校验）？id 重构静默断场景的风险怎么兜？
3. driver 进程的页面组装深度：仅模块页（现状 probe 形态）还是含 app_assembly 级 Router？决定 F-06 导航原语的实现语义。
4. 视口外元素是否需要「滚动到位」动作原语，还是首版只支持可见元素。
5. CI 离屏渲染（xvfb 等）要不要排期——现状 macOS 本地门禁已闭环，CI 缺口是否可接受由用户裁决。
6. 与既有 probe 的关系：driver 场景是否逐步替代部分重复 probe（对齐 2026-10-03 轻量化方向），还是永久并存。
7. 方案 B（IPC 真 app 进程）本期不做，**B-lite（启动开关形态）留作后续可选**——「托盘/多窗真 app 全链」场景的验收替代手段需审计确认；B 的真难点=跨线程注入 marshaling 与 UI 控制权定性（审计 P1-1）。
