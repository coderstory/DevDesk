# 池 53 · 发布任务详情「补发布态 + 编辑态 UI 重设计」需求分析（L 级）

> 来源：池 53（P1，2026-10-31 登记）；老板 2026-10-31 口述原话：①「发布功能里，任务详情只有编辑态，没有发布态。发布态下不能编辑，需要按流程一个一个的执行。」②「当前编辑态的 UI 不太好，不够现代化，感觉是为了凑需求要素硬堆控件，设计不合理、不够人性，体验不好。」
> 定性：**L 级**——新交互形态（双模式）+ 状态机语义变更 + 详情页整体 UI 重设计。
> 前置事实：`release_detail_ui.cpp` 上帝文件已于 2026-10-31（commit 5c65a645）三拆为 `release_detail_ui.cpp`（343 行入口）/ `release_detail_draw.cpp` / `release_detail_logic.cpp` + `release_detail_internal.h`。本需求在拆分后结构上做，不再背文件拆分债。DSH 侧 bot 正在该模块并发，本文只定需求与矩阵，不含技术方案。

## 一、背景与现状（拆分后实测）

**模块当前行为：**

- 任务状态五值：draft / pending / running / done / voided（`release_types.h:19`，文本编码落库）+「已超时」标记（计算得出，不入库）。
- 任务详情（执行页）**只有一个形态**：任务级前置区（提测 / CAB / nacos 工单 / DB 工单 / 公告 5 张卡，各含「填单号 + 勾完成」）+ 环境区（环境卡 → 服务卡 → 步骤行：合并分支 / 5 项配置 / 部署 / 验证）。Draft 与 Pending / Running 共用同一布局，仅靠逐控件禁用区分（`release_detail_logic.cpp:17` isReadOnly 只认 Done/Voided；isConfigPhase 认 Draft/Pending）。
- → 老板说的「只有编辑态」属实：提交（Draft→Pending）后页面形态不变，单号输入、配置编辑、跳过、移除、排序仍可操作，「发布」没有自己的界面形态。
- 「按流程一个一个执行」已有半套：页头「下一步」按钮按固定流程序依次定位（`performNextStep`：提测→CAB→nacos 工单→DB 工单→公告→各环境[合并分支→配置→部署→验证]，`release_detail_logic.cpp:1325`）；但清单本身允许乱序勾选，视觉无引导。
- 已知缺口：分支编辑 UI 未实现（`updateTaskService` 无 UI 调用方，设计文档 §13 已登记为后续票据），本轮交互设计需面对「分支只读展示」的现状。

**编辑态 UI 病灶清单（控件实测，「硬堆控件」的具体所指）：**

1. 页头一行堆 6 类元素：←返回 / 固定标题「上线任务」/ 日期 / 状态 chip / 进度文本 / 校验+提交（或下一步）+作废（或恢复），主动作随状态在「提交」「下一步」间漂移（`release_detail_draw.cpp:1174-1290`）。标题无任务身份信息。
2. 前置区 5 张 160px 高卡片平铺一格（kPrereqCardH=160、kPrereqCardMinW=220），「填单号」（编辑要素）与「勾完成」（执行要素）混在同一张卡，准备期与发布期视觉无区分。
3. 服务卡步骤行 40px 高度上挤 6 类控件：拖拽手柄、状态点、标签、上/下移箭头、查看按钮、跳过开关、完成勾选（kStepRowH=40 + kDragHandle 系列）。
4. 只读性没有页面级声明，全靠逐控件变灰；「现在处于哪个阶段、此刻该做什么」要用户从按钮组合自行推断——这正是「只有编辑态」的体感来源。

**历史底稿**（`.scratch/release-module` issues，2026-10-31 已清理，git `cfc5dfb8~1` 可追；只作语义佐证，不作设计基准）：

- issue 10 状态机：配置中→待执行→执行中→已完成；提前勾选不改状态；超时只是标记；已完成不可单步撤回；作废可恢复且不占当天名额。
- issue 08 执行清单：步骤「不要求按顺序」+「下一步」引导；撤回需二次确认并留日志；改内容自动撤回旧确认。
- issue 07 前置项：单号为空则完成勾选禁用；**可提前完成**。
- issue 06 校验：提交自动校验不过不放行；「提交后仍可改配置并自动重新校验」——**此条与本需求「发布态不能编辑」冲突，按老板令废除**（见 F-03）。

## 二、用户价值（一句话）

发布日当天打开任务详情就知道「现在该做哪一步、别的都不用看」，填单配置改不了、做过的每一步留痕；准备期则在另一个专注填写的界面里一次配齐。

## 四、「发布态」状态机定义

### 4.1 三模式映射

依据：同类产品先例——变更/发布管理工具普遍将「计划草稿」与「执行冻结」分阶段（ITIL 变更管理的 Planning / Implementation 分离，GitHub Release 的 draft / published 两形态）。

| 模式 | 覆盖状态 | 内容域（单号/配置/分支/跳过/移除/排序） | 保留交互 |
|---|---|---|---|
| 编辑态 | Draft 配置中 | 全部可编辑 | 校验、提交、作废 |
| 发布态 | Pending 待执行 + Running 执行中 | **全部只读** | 勾选确认、撤回、下一步、校验（只读跑）、作废 |
| 归档态 | Done 已完成 + Voided 已作废 | 全部只读 | 无（Voided 保留恢复） |

- 迁移：提交 Draft→Pending（已有，校验门禁）；**Pending→Draft 撤回提交（新增，F-02）**；Pending→Running 时间基准自动（已有）；→Done 全部完成自动（已有）；作废/恢复（已有，恢复按时间+进度重推 `restoredStatus`）。
- **语义变更声明**：issue 06「提交后仍可改配置并自动重新校验」被本需求废除——发布态改内容只有两条路：撤回提交（未开跑）或作废重建（已开跑）。依据：老板令（需求源头，最高优先）。

### 4.2 流程步骤模型（发布态主视图的组织序）

- **流程轨道为发布态专属**（2026-10-31 审计裁决）：编辑态主动作=提交，不放轨道引导；轨道 = performNextStep 既有固定序：任务前置（提测→CAB→nacos 工单→DB 工单→公告）→ 各环境（服务按任务内顺序：合并分支→配置 n 项→部署→验证）。轨道顺序不再新造，与「下一步」同源（本软件一致性）。
- **推进** = 勾选确认，门禁沿用既有函数（单号已填/时间窗已到/内容非空，`release_detail_logic.cpp:380-440`）。
- **回退** = 撤回（Done 前任意步可撤、二次确认、日志；既有语义保留）。
- **跳过** = 仅配置项、仅编辑态决定；发布态只读展示「已跳过」。
- **失败** = 不引入状态值；该步不勾 + 日志补记备注；重试 = 再做外部操作后再勾。
- **顺序约束（默认软引导）**：「下一步」高亮指向轨道第一个未完成且已解锁步骤；已解锁未完成的步骤允许提前勾（保留 issue 08 自由度，依据：本软件一致性——历史底稿既有决策 + 发布日真实存在并行等待）；未解锁（时间窗未到/门禁未过）**可见但不可操作**。硬锁方案已裁决不用（2026-10-31 老板拍板 A 软引导，开放问题 1 关闭）。
- **兜底出路（2026-10-31 审计裁决，P0 死锁防护双保险之一）**：Pending 期填错/漏填 → 撤回提交回编辑态补齐再重提交（衔接 F-02）；**不在发布态开任何豁免补填口子**（保 F-03 只读，豁免方案已弃）。入口侧防呆见 F-20 提交校验扩展——两道保险写死后，前置步骤无死锁可能。

## 五、编辑态 UI 重设计：用户价值与信息架构原则

原则（逐条对应病灶；全部待 ui-ux-designer 出视觉方案后定稿）：

1. **模式先于控件**：页面第一眼回答「现在是准备期还是发布日」——模式徽标/界面基调随模式切换（F-10/F-11）。
2. **主动作唯一**：页头每个状态只一个主按钮（Draft=提交，Pending/Running=下一步，Voided=恢复），校验/作废降为次级或收纳。依据：本软件一致性——同视口主按钮唯一已是页内既有约定（`release_detail_draw.cpp:1279` 注释）。
3. **准备与执行分层**：编辑态把「填」收进单据式表单流（前置 5 卡 → 按单据分组的紧凑行），「勾」弱化为随填随勾；发布态反之，勾是主角、值全只读（F-12/F-14）。
4. **步骤行控件减负**：拖拽手柄/上下移/查看/跳过收纳进次要区（hover/菜单/次行），主行只留 状态点+名称+状态+完成（F-13）。取舍依据：无先例推断，具体收纳方式交 UI 定稿。
5. **标题承载任务身份**：固定「上线任务」改为「上线任务 M/D（星期·状态）」。依据：无先例推断，交 UI 定稿。

## 七、用户操作流程（验收照走）

- **准备日**：新建任务（列表侧）→ 进详情=编辑态 → 按单据流填前置单号与公告 → 逐服务核对分支（只读展示）→ 填/粘贴配置内容、必要时跳过 → 点校验看清单 → 提交。
- **发布日**：进详情=发布态 → 「下一步」提示确认提测 → CAB → 工单 → 公告 → 依环境顺序合并分支/部署/验证；当前步高亮、未来步锁定可见 → 某步做错 → 撤回（二次确认）→ 重做 → 全部完成自动转已完成（归档态回看）。
- **例外流**：发布前发现配置错 → 撤回提交回编辑态改完再提交；发布中发现配置错 → 作废（进度冻结）→ 修复 → 恢复或重建；当天重建撞唯一名额 → 直接打开已有任务（既有语义）。

## 八、完整状态集

**编辑态（Draft）：**
- 空态：任务无环境/无服务 → 清单区空态说明 + 「去基础配置」指引；无 nacos/DB 内容时对应工单卡不出现（scanTicketNeeds 既有条件）。
- 错误：loadError 整页（已有）；保存/提交失败 notice（错误样式）；校验不过 = 标红 + 清单弹层。
- 边界：公告/配置超长多行粘贴（字数统计已有）；重复点提交幂等；Esc 逐层关弹层（模块层既有）。

**发布态（Pending / Running）：**
- 待执行未到时间：轨道可见、步骤锁定、页头提示开始时间。
- 执行中超时：步骤标红「已超时」仍可勾（既有）。
- 门禁拒绝：缺单号/时间未到 → notice 指名缺项。
- 撤回 / 作废 / 恢复失败（当天已有任务唯一约束）各有确认与报错文案。
- 状态写库失败：静默标志 + 一次 notice，不每帧弹（既有 statusWriteFailed）。
- 重启：状态与进度按时间+进度重推（restoredStatus 既有）。

**归档态（Done / Voided）：** 全只读；Voided 置灰 + 恢复入口；配置内容仍可查看。

**平台差异：** 本页无平台分支代码，双平台同构；拖拽/键盘 Esc 双平台语义一致，无新增平台差异项。
