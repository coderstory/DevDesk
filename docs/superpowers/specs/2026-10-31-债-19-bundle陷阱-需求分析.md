## 1. 需求一句话

让任何人在构建之后拿到的 `build/DevDesk.app`（若存在）不可能装着旧二进制——要么它永远是新鲜的，要么它不存在，要么它陈旧时会大声报警。

## 2. 用户价值一句话

验收者（qa 子代理、老板、未来 agent）双击 `build/DevDesk.app` 验收时，跑的就是最新代码，不会再出现「测试全绿、新功能却不存在」的全盘假象。

---

## 3. 病灶机理（源码实证，自包含）

### 3.1 两条产物路径各自何时写什么

| 产物 | 写入者 | 何时写入 |
|---|---|---|
| `<build>/DevDesk` 裸二进制（+ assets/fonts） | `cmake --build`（POST_BUILD 拷资源） | **每次**构建（`build-test-run.sh` 常规路径、手工 cmake 均是） |
| `<build>/DevDesk.app` bundle | `platform/macos/build-app.sh`（rm -rf 重建 → 拷裸二进制 → 刷 Info.plist 版本 → 生成图标 → 拷 assets → 签名） | **仅**两个调用方触发：`scripts/package-macos.sh`（打 DMG）、`scripts/build-test-run.sh --install`（装 /Applications） |

关键事实：CMakeLists.txt 里虽有 `devdesk_app` custom target（封装 build-app.sh，`DEPENDS DevDesk`），但它**不挂 ALL**——常规 `cmake --build` 不会构建它。bundle 组装脚本自己头注释也明示：「本脚本是 .app bundle 组装的唯一入口：常规构建只重建裸可执行，不碰 bundle」。

### 3.2 陈旧 bundle 的产生时间线

1. 某时刻跑过一次打包或 `--install`（如本机 2026-10-30 21:26），build/ 留下一个**快照式** bundle；
2. 之后每次常规构建（不带 --install）只更新裸二进制，bundle 纹丝不动；
3. 同目录里新旧两个产物并存，且**名字上毫无差别提示**。

### 3.3 实证（2026-10-31 12:47 本机）

```
build/DevDesk                        2026-10-31 12:45:26  40,253,272 bytes  ← 新
build/DevDesk.app/Contents/MacOS/DevDesk  2026-10-30 21:26:34  40,019,360 bytes  ← 旧（15 小时前）
```

### 3.4 触发假象的条件与现有防线

- `build-test-run.sh` 自己的「启动」段用的是裸二进制（`APP_BIN=$BUILD_DIR/DevDesk`），脚本内路径**正确**；
- 陷阱只落在脚本外的人工/agent 验收：Finder 双击 `.app`、`open build/DevDesk.app`、`cp -R build/DevDesk.app /Applications/`——macOS 直觉都找 `.app`；
- 现有防线：`--install` 流程内建 sha256 防陈旧断言 A/B（只保护安装路径）；qa lesson 登记了人工核验法（二进制 mtime + `strings` 新符号）——**依赖每个验收者记得查**，无机制保证；
- 为什么判据不能只用 mtime：cp -R / ditto / touch -t 可造任意 mtime（build-test-run.sh 头注释已论证），内容级判据（sha256）才可靠。

### 3.5 双平台差异

**此陷阱 macOS 独有。** Windows 无 bundle 形态：`build-release/DevDesk.exe` 裸二进制就是唯一产物，Inno Setup 直取它打包，「壳」概念不存在。（Windows 侧「已安装目录里的旧版本」是另一个问题，不属本债。）

## 4. 目标 / 非目标

**目标**
- G1：验收者拿到的 bundle（若存在）与本次构建产物内容一致，或陈旧时必然出声；
- G2：不破坏既有 `--install` / `package-macos.sh` 两条链的任何断言；
- G3：常规迭代构建的开销增量有上限、可接受。

**非目标**
- N1：不改 Windows 侧任何构建/打包路径（陷阱不存在，不动）；
- N2：不解决「/Applications 已装版本陈旧」问题（`--install` 防陈旧断言已覆盖安装路径）;
- N3：不动 CMake 业务构建定义（`add_executable` 层）；
- N4：不做 mtime 伪造防御（那是恶意场景，本债只防「无意陈旧」）。

## 5. 修法候选（4 个）

### 候选 A：构建后自动重组 bundle（含「存在才维护」变体 A'，推荐）

**做法**：`build-test-run.sh` 构建成功段（macOS 分支）自动调 `platform/macos/build-app.sh` 重组 bundle。推荐变体 **A'**：仅当 `$BUILD_DIR/DevDesk.app` **已存在**时才重组——bundle 的存在意味着有人用过它，维护义务随之成立；从未打过包的纯开发树零开销。调用时置 `DEVDESK_SKIP_LSREGISTER=1`（防写用户 LaunchServices 库）；签名沿用 build-app.sh 默认 ad-hoc（秒级）。可选优化：bundle 内已有 `.icns` 且源图未变时跳过图标十档重生成（图标是最慢环节）。

**改动面**：`build-test-run.sh` +10 行内；build-app.sh 可选加「沿用 icns」小开关。

**优点**：根治——两个产物永远同步，验收者拿哪个都是新的，不依赖任何人记规则或看警告；与仓库既有「构建成功后跑守卫链」风格一致。

**风险**：①每次触发多拷 ~62MB（40MB 二进制 + 22MB assets，本机实测尺寸），估 +2~5 秒；②重组失败算不算构建失败需拍板（本分析推荐硬失败，与守卫链「不静默绿」风格一致，见 §7 开放问题）；③签名策略需定（建议照签，未签名 bundle 双击可能被 Gatekeeper 拦，反而制造新假象）。

**双平台影响**：macOS only（脚本平台分支内）；Windows / Linux 路径零改动。

**工作量**：S。

### 候选 B：构建后校验报警（不重组）

**做法**：构建成功段检查：若 `$BUILD_DIR/DevDesk.app` 存在且 bundle 内二进制 **sha256 ≠ 裸二进制 sha256**（40MB 文件哈希约百毫秒）→ 打显式警告：「⚠ build/DevDesk.app 是陈旧 bundle（bundle 内 sha256 xxxx vs 裸二进制 yyyy），验收勿拿它，真产物是 build/DevDesk；要新鲜 bundle 跑 --install」。bundle 不存在则零打扰。

**改动面**：`build-test-run.sh` +8 行内，最小改动。

**优点**：零副作用、零重组开销；保留「bundle 只在打包/安装时才组装」的既有架构语义；把静默陷阱变成出声陷阱。

**风险**：①**没根治**——报警可被无视（很多 agent 只看尾部 ✅ 行，警告在中间可能被漏），假象从「静默」降级为「有警告」而已；②依赖验收者读到警告。

**双平台影响**：macOS only；Windows 零改动。

**工作量**：S（最小）。

### 候选 C：把 .app 移出常规构建路径（改产物布局）

**做法**：bundle 产物不再落 `$BUILD_DIR/DevDesk.app`，改落 `$BUILD_DIR/dist/DevDesk.app`（build-app.sh 输出目录改 `${DEVDESK_BUNDLE_DIR:-$BUILD_DIR/dist}`）。常规 build/ 根目录只剩裸二进制——「同目录新旧两产物」的迷惑源被物理消灭；验收者在 build/ 根看到 .app 的直觉引导随之消失。极简变体 E：常规构建开始时直接 `rm -rf $BUILD_DIR/DevDesk.app`（不留 bundle，打包/安装时现组），改动更小但破坏性更强，不单列。

**改动面**：跨 3 个脚本（build-app.sh、package-macos.sh、build-test-run.sh --install 段的 APP_DIR/MACOS_DIR 路径）+ qa lesson 核验口径 + 相关文档；gitignore 无影响（build/ 整体已忽略）。

**优点**：根治迷惑源本身；不改构建时长；产物语义清晰（build/ 根=开发产物，dist/=交付形态）。

**风险**：①路径变更波及打包链回归（DMG、--install 两链都要重验）；②外部肌肉记忆/文档若引用旧路径会断（本仓文档有多处 `build/DevDesk.app` 字样）；③「存在才维护」的好处没拿到——dist/ 里的旧 bundle 若被直接引用同样陈旧，只是不在眼前。

**双平台影响**：macOS only；Windows 零改动。

**工作量**：M（跨脚本路径重构 + 打包链回归验证）。

### 候选 D：CMake 侧把 devdesk_app 纳入 ALL

**做法**：CMakeLists.txt 里 `add_custom_target(devdesk_app ALL ...)`，让每次 `cmake --build`（含手工 cmake 路径，不只脚本路径）都重组 bundle；需同时把 `WORKING_DIRECTORY`/`DEVDESK_BUILD_DIR=$CMAKE_BINARY_DIR` 传给 build-app.sh。

**优点**：CMake 原生依赖图保证顺序；覆盖手工 cmake --build 的路径（A/B/C 都只覆盖脚本路径）。

**风险**：①**多树并发坑**：build-app.sh 默认 `BUILD_DIR=$PROJECT_DIR/build`，若接线漏传 `$CMAKE_BINARY_DIR`，worktree 的 Release 树组装时会把**主 Debug build/ 的二进制**装进 bundle——比现陷阱更隐蔽，必须专门验证；②每次构建都触发图标十档缩放（比 A' 更频繁、更慢）；③改 CMakeLists 触及构建配置，评审面大于改脚本。

**双平台影响**：`if(APPLE)` 保护，Windows 不生成该 target；但 configure 行为变化需 CI 验证。

**工作量**：S~M。

## 6. 拍板要素表

| 候选 | 改动面 | 风险 | 双平台影响 | 工作量 | 根治程度 |
|---|---|---|---|---|---|
| **A' 构建后自动重组（存在才维护）** | 1 个脚本，+10 行 | 重组失败语义需拍板；+2~5s/次触发 | macOS only，Windows 零改动 | **S** | 根治（bundle 恒新鲜） |
| B 校验报警 | 1 个脚本，+8 行 | 报警可被无视，未根治 | macOS only | S（最小） | 半根治（出声陷阱） |
| C 移出构建路径 | 3 脚本 + 文档 | 打包链回归；路径波及面 | macOS only | M | 根治迷惑源（但 dist/ 内仍可陈旧） |
| D CMake ALL 纳管 | CMakeLists + 接线 | 多树并发坑隐蔽；改构建配置 | 需 CI 验证 configure | S~M | 根治（且覆盖手工 cmake——⚠ 审计注：手工 cmake 路径已被本仓门禁禁用（AGENTS.md §五 + PreToolUse 硬阻断），该优点实际价值近乎为零） |

### 推荐：候选 A'（构建后自动重组，「存在才维护」变体）

**理由（依据标注）**：
1. **同类产品先例**：macOS 开发生态（Xcode、cargo-bundle 等）的惯例是「构建目标 = 最终可交付形态」，裸二进制是中间产物；本仓反着放（裸=真、壳=旧）才需要每个验收者记住特例。A' 把形态掰回惯例。
2. **本软件一致性**：build-test-run.sh 已有「构建成功 → 守卫链逐道断言、不静默绿」的成熟风格，A' 是同一哲学的延伸；B 的「可被无视警告」在守卫链里属于被明确否定过的形态（0 命中当绿、静默跳过均被判过红）。
3. **90% 核心价值 + 最小改动面**：S 级改动根治问题；「存在才维护」把开销限定在真正用过 bundle 的树上，纯开发树零增量，兼顾 G3。
4. B 可作为 A' 的内部组件保留（重组失败时的诊断输出正是 B 的 sha 对比），不必二选一。

若老板嫌 A' 的触发开销不可接受，退而求其次选 B（立即止血，成本最低）；C/D 不推荐（C 收益被「dist/ 内仍可陈旧」削弱，D 的多树坑隐蔽性超过收益）。

## 7. 验收口径草案（按候选各自的验收判据）

| F-ID | 功能点 | 优先级 | 状态 | 验收判据 |
|---|---|---|---|---|
| F-01 | 陈旧检测/重组判据 | 核心 | 待方案 | 预置一个旧 bundle（二进制与裸二进制 sha256 不同）后跑构建：A' → bundle 内二进制 sha256 == 裸二进制；B → 出现警告且包含双方 sha 前 12 位 |
| F-02 | 无 bundle 空态 | 核心 | 待方案 | 首次构建（构建目录无 DevDesk.app）不产生 bundle（A'）、不报警（B）、构建零增量 |
| F-03 | 新鲜 bundle 幂等 | 核心 | 待方案 | 已新鲜的 bundle 再跑构建：A' 重组后仍一致、无假红；B 不报警 |
| F-04 | 副作用隔离 | 核心 | 待方案 | A' 触发路径不写 /Applications、不 lsregister（DEVDESK_SKIP_LSREGISTER=1 生效）、不污染仓库源树 |
| F-05 | --install 全链回归 | 核心 | 待方案 | 改动后 `--install` 全链仍绿：防陈旧断言 A（签名前）/ B（已安装）+ Info.plist 版本断言 + 特征串后置验 |
| F-06 | package-macos.sh 回归 | 核心 | 待方案 | DMG 打包仍产出有效签名包（C 改路径后为必测项） |
| F-07 | 文档/经验一致性 | 边缘 | 待方案 | qa-tester lesson 核验口径更新（A' 下降级为历史注记；B/C 下补充报警/新路径口径）；相关文档中 `build/DevDesk.app` 语义与实态一致 |
| F-08 | Windows 零影响 | 边缘 | 待方案 | Windows 侧构建/打包路径零改动，交叉编译守卫照绿；Mac 上以 `check-windows-cross-compile.sh` 守卫为准，Inno 包产出不受影响——待 Windows 主机下次构建回填清单卡确认（双机口径，审计补） |

**状态自查覆盖**：空态（F-02 无 bundle）；错误态（F-01 陈旧检出后 A' 硬失败 / B 出声）；幂等（F-03）；首次（F-02 即首次构建）；平台差异（F-04/F-08）；可撤销性——本债所有候选都不删用户数据、不动源树，无撤销需求。

## 8. 开放问题（拍板时需一并定）

1. **A' 重组失败算不算构建失败？** 推荐：硬失败（与守卫链「不静默绿」一致）——构建声称产物齐备，齐备不了就该红；代价是 bundle 磁盘异常时会挡开发迭代。
2. **A' 是否照签？** 推荐：照签（ad-hoc 秒级）——未签名 bundle 双击可能被 Gatekeeper 拦，制造「点了没反应」的新假象。
3. **触发开销上限**：F-03 场景增时建议 ≤10s（本机 62MB 拷贝实测推算），超出则加「沿用 icns」优化后再收。
