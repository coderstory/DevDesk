## 一、需求一句话

把桥插件（dsh-zcode-plan-bridge fork，0.5.4 线）对 ZCode 0.17.x 内核回合协议**已适配与未适配的面**全部盘清并固化：桌面内核（3.17.1 客户端，内核 0.17.1）与 npm 内核（zcode-app-cli 3.16.3-41，内核 0.17.0）双内核差异收敛为「绕过决策 + 可诊断失败」，残余未适配的服务端请求逐项确认降级语义，协议探针固化为升级回归工具。

**用户价值一句话**：桌面客户端一升级内核，桥接链路不再以「回合莫名报 Select a model / 模型清单空转」的方式坏掉，而是 doctor/protocol 一条命令就能指出「哪段协议变了、当前 CLI 是哪只内核、该指哪条路径」。

## 三、症状全集盘点（0.17.x 内核下桥接链路已知异常）

> 置信度分级：高=本机实测复现且有代码/commit 实锤；中=代码路径可推 + 部分实测；低=仅 bundle 静态证据，未实测。

### S-1 桌面内核：一切回合报「Select a model before continuing」

- **现象**：`zcodeCliPath` 指向桌面内置 zcode.cjs（3.17.1 客户端，内核 0.17.1）时，桥能起 app-server、能建会话，但一切回合报「Select a model before continuing」。
- **根因定位**：**模型枚举段**（`session/create` → `settings.model.available`）。桌面内核在 app-server 模式下模型注册表恒空（返回 `available = []`）；连带 **session/setModel 段**对着空注册表报「Provider Registry 中不存在 Model」。登录态、双 env、注入配置均已实测排除（SKILL.md 核心结论 1：唯一根因）。
- **内核 bundle 旁证**：setModel handler 读 `f.selection ?? ule(f.registry,…)`；setThoughtLevel 报「Select a model before choosing reasoning effort」——注册表空载是内核态行为。
- **既有处置**：绕过（`zcodeCliPath` 显式指 npm 版，SKILL.md 核心结论 1/3）。本单**不重开**该决策。
- **残余**：误选桌面内核时失败形态是「装好了但一切回合神秘报错」，诊断成本高（10-30 深夜实际踩过一轮才定位）。→ 归本单（诊断化，见 F-01/F-04）。
- **置信度**：高。

### S-2 catalog 空时兜底模型表是占位路由（zai-api），standalone 注册表不认

- **现象**：CLI 上报空清单（桌面内核 / 未登录 / 探测超时）时，`effectiveCatalog()` 返回 `FALLBACK_CATALOG`（providerId=`zai-api` 占位），`resolveRoute()` 拿它去 `session/setModel` → 注册表不认 → 失败被 catch → 回退会话默认模型。npm 内核正常登录时会话默认模型有效，**尚可活**；桌面内核下默认模型也为空 → **死**（S-1 的加速器）。
- **根因定位**：模型枚举段 → 路由解析段（resolveRoute/pickCatalogEntry）→ session/setModel 段。历史注脚：06132f2 曾修（改读 CLI 持久化 defaultModelSelection），0.5.2 merge 后修法被取代、问题回到现源。
- **残余**：降级路径（a）发出的 setModel 必然失败（白等一个 RPC 超时），（b）日志只有一行 warn，(c) models 输出把占位路由当真清单报给用户。→ 归本单（F-01/F-05）。
- **置信度**：高（代码路径可读 + 06132f2 commit 实锤；触发条件=降级态，npm 正常路径不触发）。

### S-3 未显式适配的服务端请求：requestUserInput / requestOfficialMcpAuthHeaders / mcp/ui\*

- **现象**：0.17.x 服务端请求面 6 个（bundle 实提），桥显式适配 4 个；`interaction/requestUserInput` 与 `interaction/requestOfficialMcpAuthHeaders` 落「未知方法统一回 `{}`」兜底；`mcp/ui*` 家族同理。README 通道原理 8 已把该兜底定为 deliberate 设计（3.16 实测「对应功能降级，但不挂会话」）。
- **残余**：
  - `requestOfficialMcpAuthHeaders`：降级语义已被 README 记录，风险低——只需在代码注释/探针里登记，无开发。
  - `requestUserInput`：CLI 侧存在 `v4AnswerToUserInputResponse` 应答转换（bundle 可见），`{}` 是否为合法应答（被当作取消？空回答？抛错？）**未实测**。若 agent 在回合中触发 ask-user 类交互，桥回 `{}` 的后果未知。→ 归本单（F-02，专项确认后决定显式拒绝或维持 `{}`）。
  - `interaction/providerRuntimeHeadersCancelled` 是通知（`e.notify`，无 id），桥转发给 listener 后被 `session/event` 过滤器忽略——语义正确，无需应答。**非残余，登记为已覆盖**。
- **置信度**：方法面=高（bundle 实提）；`{}` 应答后果=低（未实测，这正是残余所在）。

### S-4 session/setThoughtLevel 未使用；reasoning 档位仍走 setModel options

- **现象**：0.17.x 内核新增独立 `session/setThoughtLevel` 方法（双内核 bundle 均有）；桥继续用 `session/setModel` 的 `options.reasoningLevel`（3.16.3 实测工作）。
- **残余**：0.17.1 内核是否仍认 `options.reasoningLevel`、`setThoughtLevel` 是否为其偏好通道——未测。方法面一致 ⇒ 大概率行为不变，风险低。→ 归本单**验证项**（F-06），非开发项。
- **置信度**：中。

### S-5 打断协议（session/stop 带请求 ID）——已适配，回归在飞

- **现象/历史**：CLI 只把 `session/stop` 当 request 处理、忽略无 ID 通知；abort 时桥必须主动发带请求 ID 的 stop，否则回合锁占住、服务端跑完整轮烧额度。上游 0.5.2 已修（4445e61），fork 已并（37dfee7）。
- **归属**：行为修复的回归收尾归 **BUG-23**；本单只在协议面登记（探针断言覆盖 stop 为 request 形态），不重复开发。
- **置信度**：高。

### S-6 权限协议 approvalMode:"user-once"——已适配

- `authorization.js` KNOWN_APPROVAL_MODES 白名单 + 未知 mode fail-closed 拒绝 + 两种策略均保持会话 build 模式。**非残余，登记为已覆盖**。置信度：高。

### S-7 UI 长时间「正在加载模型」——已修

- 0.5.2 有界等待（模型查询 15 秒上限，超时先给备用清单、后台探测成功自动刷新）。**非残余**。置信度：高。

### S-8 版本面：ZCode CLI 内核线无兼容声明、桌面内核误选无拦截

- `package.json` 只声明 DSH 宿主线（engines.dsh，有 compatibility.test.mjs 守卫）；**ZCode CLI 内核线没有任何声明或守卫**。桥自动探测按「版本择优」会选桌面内核（runtime 目录名 3.17.1 > npm 3.16.3），显式配置是唯一护栏——踩坑已两次（SKILL.md 核心结论 3、桌面内核升级引爆注册表空载）。
- **残余**：桌面内核身份（zcode.cjs 无 package.json 清单 + builtin 版本代理）doctor 已能读到原材料，但没有输出「这是桌面内核、app-server 不受支持」的判定。→ 归本单（F-04）。
- **置信度**：高。

### S-9 双内核同步税：桌面升级写新 builtin，老 npm CLI 可能解不了

- README 实锤过 3.14.x + 新桌面共存启动即崩（#207）；现稳态 3.16.3-41 + 桌面 3.17.1 实测可用。桥 spawn 不注入任何 ZCODE_*（deliberate），CLI 自解析 release。残余 = 升级窗口的回归工具缺位（每次桌面/npm 任一升级要人工重验）。→ 归本单的**工具化目标**（F-03 固化 protocol 探针为升级回归步骤），修码为辅。
- **置信度**：高（历史实锤 + 当前稳态实测）。

## 六、验收口径草案（每症状的复现/修复判据）

> 环境基线：本机（macOS arm64）双内核并存——npm `/opt/homebrew/bin/zcode`（3.16.3-41，内核 0.17.0）与桌面 `/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs`（3.17.1，内核 0.17.1）。诊断命令一律带 `--cli-path` 显式指内核，避免探测择优干扰。

**F-01 降级路径诊断化**（对应 S-1/S-2）
- 复现：`node bin/dsh-zcode-plan-bridge.js models --cli-path /Applications/ZCode.app/.../zcode.cjs`（桌面内核，未修前）→ 空清单 → 回退 FALLBACK_CATALOG 输出 zai-api 占位条目，无「为何空」的说明。
- 修复判据：

  2. 按实测结果二选一落地：显式拒绝（带 reason 的合法应答形状）或维持 `{}` + 代码注释写明实测依据与日期；

## 七、用户操作流程（验收照走）

1. （不烧额度）`node bin/dsh-zcode-plan-bridge.js doctor --cli-path /opt/homebrew/bin/zcode` → 看到 npm 版身份判定 + 各前置绿。

3. （不烧额度）`node bin/dsh-zcode-plan-bridge.js models --cli-path /opt/homebrew/bin/zcode` → 真实清单；同命令指桌面内核 → 「空清单+原因」而非占位假清单（F-01）。

## 八、完整状态集自查（分析覆盖度核对）

- **空态**：catalog 空（S-2/F-01）、models 无清单、探针会话拿不到 sessionId——均已入验收判据。
