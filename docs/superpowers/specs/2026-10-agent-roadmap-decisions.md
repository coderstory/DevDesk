## 1. 排期决策：先 M3 后 M4

**决策**：先做 M3（可用性收口），再做 M4（事件触发 + 记忆）。M3 做完后，用户在真机上实际使用一段时间，再动 core 层（M4 的 EventBus 与 context note 都要进 core / migrations）。

**理由（用户口径）**：M1/M2 功能面已经铺开，当前瓶颈是「用起来顺不顺」而不是「能力够不够」；core 一动（事件总线、表结构）回归面就大，必须建立在「现有功能已被真机使用验证稳定」的地基上。

**含义**：
- M3 全部改动收敛在 module_agent 层（UI + 既有纯函数扩展），零 core 改动、零 migration。
- M4 开工时点由用户在真机使用后明示，不由开发侧自行判断。

## 2. M3 范围（四项全做）

**决策**：M3 = 可用性收口，四项全部纳入，缺一不交：

1. **run 完成桌面通知**：run 从 running 进入终态时发桌面通知；`completed` 可静默（不响），`failed` / `limited` 必响。通知形态是 toast 还是系统通知**未定**——见 M3 计划的「实现期核实项」。
2. **cron 常用模板下拉 + 下次触发时间预览**：任务弹窗的 cron 输入框旁加常用表达式模板下拉（如「工作日 9 点」「每小时」）；表单内实时预览「下次触发时间」，非法表达式显示校验错误。
3. **run 详情一键复制最终回复全文**：详情弹窗加复制按钮，一键复制最终 assistant 回复全文（现有复制 chip 是逐条消息的，不是最终回复全文）。
4. **代理未启 / 槽位解析失败时错误行带「去 Claude 页」直达引导**：详情弹窗错误行与页内错误行在这两类错误出现时，附「去 Claude 页」引导（直达 Claude 页而非让用户自己找）。

**理由（用户口径）**：四项都是日常真实使用中天天撞到的缺口——run 跑完不知道结果、cron 表达式记不住写错、想拿回复要逐条点复制、代理没起只看到一句报错不知道去哪修。M3 不加任何新能力，只把已有的能力收口到「顺手」。

## 3. M4 决策 1：事件总线 = 纯进程内 EventBus

**决策**：事件总线是 core 层的**纯进程内**发布/订阅（EventBus）：
- core 层提供轻量 publish/subscribe 接口；
- todo / markdown 业务点在写路径 emit 事件；
- Scheduler 订阅事件、按任务配置入队起 run。

**明确不做**：不持久化事件；app 未运行期间发生的事件**错过不补发**。

**理由（用户口径）**：与 cron 既有语义完全一致（spec §5.1「错过的触发不补跑」）——事件触发的价值是「app 开着时自动响应」，不是「离线补偿」；持久化队列 + 补发是另一套复杂度，当前使用强度撑不起。

## 4. M4 决策 2：首批事件 = 三个动作事件

**决策**：首批事件只做**动作事件**，共三个：
- `todo.created`（新建待办）
- `todo.completed`（完成待办）
- `md.saved`（笔记保存）

各在对应 service 的写路径加一行 emit 即可。

**不做**：`todo.overdue` 等**状态事件**（需要额外轮询判定「何时变得逾期」，不是写路径顺手可得的）。

**理由（用户口径）**：动作事件在 service 写路径一行 emit 就有，成本极低；状态事件要引入轮询判定逻辑，成本与收益不匹配，砍掉。

## 5. M4 决策 3：防抖 = 冷却窗口

**决策**：防抖用**冷却窗口**实现：
- 以「任务 × 事件」组合为键，窗口内该组合的事件不重复起 run；
- 窗口时长可配，**默认 5 分钟**。

**明确不做**：批量聚合（窗口内攒一批事件、合并成一次带上下文的 run）**留到 M5 评估**，M4 不做。

**理由（用户口径）**：冷却窗口一行逻辑就能挡住高频写入场景（如连续编辑保存笔记触发 `md.saved` 风暴）引发的 run 连发；批量聚合要先有真实的高频场景与效果数据，M5 再看。

## 6. M4 决策 4：记忆 = 任务级 context note

**决策**：记忆做成**任务级 context note**，不做全局记忆：
- `agent_tasks` 表新增 context note 列（**migration 顺延当前最大版本号**，不插中间版本）；
- UI 可编辑（任务弹窗内）；
- 注入位置 = **system prompt 末尾**；goal 仍是首条 user 消息，位置不变；
- run **正常结束**（completed）时自动 append「最终回复前 500 字 + 时间戳」到 note；该行为**任务级可关**（每任务一个开关）；
- note 总长 **4KB 上限，滚动丢最旧**（超出时从头部丢弃最旧内容）。

**理由（用户口径）**：任务级才可控——每个任务记自己的经验，互不污染；全局记忆一行坏内容会毒害所有任务。4KB 上限 + 滚动丢最旧，防 context 无限膨胀；自动摘要只取最终回复前 500 字是「最便宜的连续性」，够用。

## 7. 暂不做清单（M3/M4 均不触碰）

| 项 | 不做的理由（用户口径） |
|---|---|
| 持久化事件队列 | 见决策 1：与 cron 语义一致，错过不补发 |
| 状态事件（todo.overdue 等） | 见决策 2：需轮询判定，成本不对称 |
| 批量聚合 | 见决策 3：留 M5 评估，先要真实场景数据 |
| 自动 LLM 摘要（对 context note 做 LLM 提炼） | 500 字截断的原始追加够用；LLM 摘要引入额外成本与不确定性 |
| 多 agent 编排 | 单任务单 run 的模型刚验证，编排远超当前需要 |
| MCP | 与 spec D-6 一致：仅内置工具 |
| 流式响应 | run 是后台自动化，无对话窗，流式无处消费 |
| OpenAI function_calling | 与 spec D-3 一致：只支持 Anthropic tool_use |
