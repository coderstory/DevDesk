## 结论先行

1. 两池缺口全部在 DevDesk 侧接口层（引擎 get_memories / get_memory 能力已 POC 实证齐备），最小改动面 = 简报口径：gateway 加 2 方法 + panel_state 换 2 处闭包，curator/proposal_store 消费侧零改动。
2. 对简报最小改动面的唯一修正：**池 32 真闭包内做错误码分流（not_found → ok(-1)，网络类 → ok(baseVersion)）**，理由见 F-32-2——不做分流会破坏 forget 撤销链（重录入型撤销卡的引擎条目本来就不存在）并让「引擎临时不在」误判为「目标已变」。
3. events 伪用户结论（实查非猜）：**现状扫描链只覆盖默认用户，events 伪用户不在 decay 扫描范围**，本批不扩 scope，见 §三。

## 一、池 31：decay 遗忘清单接真（闲置判定 = updated_at 代理，老板 2026-10-31 拍板）

  - 新小结构 `MemoryListItem { std::string id; std::string text; std::int64_t updatedAtEpoch = 0; }`（不复用 MemoryHit：那是 search 语义带 score/dateText，污染契约；created_at 无消费方不取——最小 90%）

- 接口变更全量适配清单（实现期以编译错误清单为准补齐）：生产实现 1 处；测试假实现 4 处——test_memory_proposals.cpp:31 FakeEngine、test_memory_hook.cpp:25 FakeRetriever、test_memory_mcp_search_tool.cpp:31 FakeRetriever、test_memory_infer.cpp:37 InferFakeEngine；tests/probes 如引用接口同步补。

### F-31-2 解析纯函数：parseListResponse + isoToEpochSec（含 findMemoryIdByText 去重）

- `telemem_client.cpp` 新增 `parseListResponse(const std::string& httpBody)` → `Result<std::vector<MemoryListItem>>`，声明提升到 telemem_client.h（与 parseSearchResponse/parseAddResponse 并列，公开供单测钉住）。解析链同形于 findMemoryIdByText 内联解析（:329-364）：SSE 剥离 → parseJsonRpcResult（isError 判错现成 :51-91）→ content[0].text 二次 parse → results[] 逐条 {id, memory, updated_at}。
- `isoToEpochSec(const std::string& iso)` 纯函数：ISO-8601 UTC（"2026-10-27T12:34:56Z"）→ epoch 秒；空/非法 → 0。池 32 get_memory 共用，单测钉一次。
- **去重重构**：findMemoryIdByText 改为先 parseListResponse 再按正文精确匹配 id（同形解析消重；其对外契约不变）。
- **fail-safe 语义**（curator 现成消费逻辑）：updated_at 缺失/解析失败 → updatedAtEpoch=0 → curator.cpp:37 `m.lastUsedAt <= 0` 跳过该条（保守不动，不误删）。

### F-31-3 panel_state：decayMemories fail-closed lambda 换真闭包

## 二、池 32：baseVersion 真值（updated_at 作版本 token）

### F-32-1 gateway 接口：IMemoryRetriever 加 getMemoryVersion

- `telemem_client.h`：`virtual core::Result<std::int64_t> getMemoryVersion(const std::string& memoryId) = 0;`（纯虚，同 F-31-1 全量适配）。
- `telemem_client.cpp`：实现 = `callTool("get_memory", {memory_id}, 10000)` → `parseGetMemoryResponse` 纯函数（content[0].text → updated_at → isoToEpochSec）。**not_found 形态 → `core::ErrorCode::NotFound`**（delete 后 get_memory 回 not_found，评估报告 POC 定案；具体信封形态以实现期 live 抓包为准，isError 与 error 字段判错 parseJsonRpcResult 已覆盖）。

### F-32-2 panel_state：trustSnapshotVersion 换真闭包（含错误码分流，本卡修正点）

- `panel_state.cpp:40-45` `trustSnapshotVersion(baseVersion)` 函数签名与两调用点（acceptProposal :552、createUndoCard :602）**零改动**，函数体换真闭包 `realTargetVersion(baseVersion)`：
  - `getMemoryVersion(tid)` 成功 → 如实返回引擎真值；
  - **NotFound → 返回 ok(-1)**（条目不存在，版本记 -1）；
  - **网络/引擎不在类错误 → 返回 ok(baseVersion)**（放行，交给执行层）。
- proposal_store.cpp:419-436 校验链零改动，全场景推演（`v.isFail() || v.value() != p.baseVersion`）：
  | 场景 | 引擎真值 | 判定 | 结果 |
  |---|---|---|---|
  | forget 正向卡·目标未变 | ==baseVersion | 放行 | 执行删除 ✓ |
  | forget 正向卡·目标被改 | 新 updated_at | ≠ → expired | 证据失效 ✓（池 32 核心价值） |
  | forget 正向卡·目标被删 | NotFound→-1 | ≠ → expired | 自动过期重提 ✓（评估报告预期语义） |
  | forget 撤销卡（重录入，baseVersion=-1） | NotFound→-1 | == → 放行 | addDirect 重录入 ✓ |
  | invalidate 撤销卡·目标在 | 建卡时记真值 :626 | == → 放行 | 执行删除 ✓ |
  | invalidate 撤销卡·目标已删/被改 | -1 / 新值 | ≠ → expired | ✓ |
  | add 卡（targetIds 执行前空） | — | 循环不进 | 现状不变 ✓ |
  | 引擎不在时点接受（任意卡） | 网络错→ok(baseVersion) | == → 放行 | executor 失败 → 保持 pending 可重试 ✓（**现状语义不退化**） |
- **为什么必须分流**（对简报最小改动面的修正）：不分流而让 fail 直接透传，则 (a) forget 撤销卡建卡即败（createUndo :620-625 目标版本不可得——重录入型撤销的引擎条目本来就不存在，这是撤销的**前提**不是失效信号）；(b) accept 校验层把「引擎临时不在」误判成「目标已变」→ expired，毁掉面板「可再点接受重试」契约（panel_state.cpp:558-562）。NotFound→-1 与网络→baseVersion 两个放行值刚好让上表全部场景自洽。
- 同秒改两次不可区分（ISO 秒级 granularity）：审核门控流程下风险可忽略（评估报告已声明），不加防御。

## 三、events 伪用户：decay 扫描范围结论（实查现状，非猜）

- 证据：`src/module_memory` 全目录 grep `user_id` **零命中**——DevDesk 全部 MCP 调用（search_memories / add_memory / get_memories / delete_memory）从不传 user_id；本卡新增 listAll / getMemoryVersion 同样不传。
- 引擎侧（评估报告 POC）：不传 user_id → 落默认用户 `telemem-mcp`；会话事件记忆在伪用户 `events` 下，需显式 `get_memories(user_id="events")` 才可见。
- **结论：现状与新方案的 decay 扫描都只覆盖默认用户，events 伪用户的会话事件记忆不在扫描范围。** DevDesk 自管理记忆（addDirect/addInferred 通道）全落默认用户，即 decay 治理对象（提案链产出的记忆）已全覆盖；events 是 telemem 内部会话流水，是否纳入遗忘治理属产品口径（评估报告遗留待决策），本批不扩 scope。getMemoryVersion 按同口径查默认用户，与 listAll 一致，无跨用户错位。

## 四、失败路径

| 故障 | 行为 | 兜底 |
|---|---|---|
| get_memories 超时/网络失败 | listAll fail → decayMemories 闭包如实传 fail → runDecayScan fail | panel_state.cpp:257 现有 `LOG_INFO("decay 扫描未执行")`，下轮 6h 重试；fail-closed 不出假卡 |
| 清单超 kDecayScanListLimit(200) | 超限部分本轮静默不扫 | 个人库量级远低于此；常量可调；不做分页（引擎无 offset/cursor） |
| updated_at 缺失/解析失败 | updatedAtEpoch=0 | curator `lastUsedAt<=0` 跳过，保守不删（curator.cpp:37 现成） |
| get_memory 工具级 isError / not_found | NotFound 明确错误码 | 校验闭包分流（F-32-2 表），语义各自正确 |
| 引擎不在时点接受 | 闭包放行 → executor 失败 | 提案保持 pending + 面板可重试（现状契约不变） |

## 七、取舍与开放问题

- 取舍：新结构 MemoryListItem 而非扩 MemoryHit（search/list 契约分离）；listAll/getMemoryVersion 纯虚强制全量适配（简报硬约束）；NotFound→ok(-1) 分流（§二修正点）；limit 200 不做分页；events 不扩 scope（§三）；池 31 本地使用时间表（search 命中记 lastUsedAt）不做——updated_at 代理已拍板，更准方案留待产品翻案。
- 开放问题（2 个，主会话 2026-10-31 核对通过时授权自决，取值留痕如下）：
  1. **OQ-1 events 伪用户：本批不扩 scope**（与 §三结论一致化）。后续如需把 events 会话流水纳入遗忘治理，另行入池评估（需显式 `get_memories(user_id="events")` 第二通道 + 治理口径产品拍板）。
  2. **OQ-2 kDecayScanListLimit 沿用 200**：与 findMemoryIdByText 既有 get_memories 口径一致。超限截断行为明确：超出部分本轮不扫描且无提示，个人库量级远低于此；如后续库规模增长到触发截断，调此常量即可（引擎 limit 无上限，POC 定案）。
- 实现段补充决策（2026-10-31 实现期）：版本校验闭包的**错误码分流逻辑**落在 proposals 层新内联工厂 `makeTargetVersionFn(baseVersion, lookup)`（proposal_store.h，紧邻 TargetVersionFn 契约位）——panel_state 的闭包持有真 HTTP 引擎无法单测，提出纯逻辑后 lookup 注入即可四分支钉死；panel_state.cpp 内真闭包 = `makeTargetVersionFn(baseVersion, [](id){ TelememHttpRetriever{}.getMemoryVersion(id); })` 薄委托。
- F-ID 覆盖：F-31-1~4（接口/解析/闭包/测试）、F-32-1~3（接口/闭包分流/测试），实现完成后回写池矩阵（待测试）。
