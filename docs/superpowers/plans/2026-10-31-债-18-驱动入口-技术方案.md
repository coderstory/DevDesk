## 0. 结论先行（≤5 条）

1. **命中回读选「EUI-NEO 小步暴露」**（§1，P0 必答）：在 `dsl_runtime.h` public 段新增一个只读查询 `hitTestInteractiveAt(x, y, dpiScale)`，内联转发既有 private `hitTestInteractive` 机器——机器每帧都在跑（`runtime_lifecycle.h:130`），暴露 ≈10 行，不是能力攻坚；DevDesk 侧复刻命中判定不可行也不该做（clip/变换/z 序/disabled 树四层逻辑复制即负资产）。降级静态近似只覆盖 z 序悬浮一类，挡不住动态截胡，与 F-05 的审计动机（防假绿灯）不符。
2. **六组装件全部落在 `tests/ui_driver/`，零 probe_harness 改动**：driver 可执行 `#include probe_harness.h` 复用五原语/截图/金丝雀/帧驱动/键码映射，新增代码 = 解析 / 键名表 / 判定 / 报告（底层四件）+ 解释器 / id dump（编排两件）六个 header-only 组件 + main（§3，含分层纪律：纯函数一律落零 probe_harness 依赖的底层头）。
3. **场景 schema 定稿为单 `type` 判别键的 JSON**（§4）：`{version, settings, steps[]}`，步骤类型 click/type/key/scroll/drag/wait/assert/screenshot/dump 九种；键码契约 = 「语义键名→GLFW 键码」一层新表 + 复用 `glfwKeyToInputKey`，**不产生第二份 GLFW→InputKey 映射**（既有双份留方案 C 档 2）。
4. **「滚动到位」原语首版不纳入**（§5.2）：clip 外点击必 miss 是框架事实（`runtime_input.h:139-153`），scrollIntoView 需自算目标滚动容器与偏移 = 复刻布局知识；首版边界如实写进文档——场景仅支持可见元素，视口外用 `scroll(dx,dy)` + `wait` 组合显式驱动。
5. **方案 C 本期取「部分前移」档**（§6）：仅 hit-test 只读查询一项前移，公开注入 API + 键码映射单源化 + 框架集成指南章节全部拆出为独立后续项。规模结论 **M 维持**（上限方向）：六组装件纯组装、唯一框架增量 ≈10 行 + 单测、唯一 src/ 触点 = `platform::json` 解析错误详情 additive 重载（可回退）、双平台验证 = 同一场景两机各跑。

## 1. P0 必答：命中回读二选一（对比 + 推荐）

### 1.1 两案对比

| 维度 | 选项 A：EUI-NEO 小步暴露 | 选项 B：`assertNoEqualZOverlap` 静态近似 |
|---|---|---|
| 改动面 | EUI-NEO `dsl_runtime.h` public 段声明 + `runtime_input.h` inline 定义（≈10 行）+ 框架单测 ≈60 行 + 能力文档一行 | 零框架改动 |
| 覆盖面 | **动态**命中判定：点击后当帧该点实际接收指针事件的元素（含 toast/弹层/遮罩在点击瞬间截胡、clip 裁剪 miss、disabled 树、变换矩阵） | 仅 z 序悬浮一类（且需场景作者指定 popupId）；**动态截胡不在判定范围**——静态扫描判不了「点击那一刻谁接住事件」 |
| DevDesk 侧实现 | `driver_steps.h` 编排执行（帧后查询）+ `driver_checks.h` 判定：断言命中 id ∈ 目标子树 | 要「近似」到可用，得在 DevDesk 复刻 hit-test 四层逻辑（clip 交集 / `hitMatrixForElement` / `orderedChildren` 逆序 / disabled 树）——**复制即负资产且必然随框架演化漂移** |
| 假绿灯风险 | 实际命中 ≠ 目标 → 步骤 fail，stderr 给双方 id + frame + 截胡者诊断 | toast 类截胡静默通过——**正是本需求要消灭的形态**（需求分析 F-05 审计 P2 补的动机） |
| 跨仓义务 | 有：先推 EUI-NEO `fork` 再推 DevDesk（AGENTS.md §一，纪律成熟） | 无 |
| 先例 | Playwright hit-target check 的框架内等价物（调研 §3.1）；结果消费形态 = deferred check（点击后当帧补验，与 Playwright double-click 第二击同构） | assertNoEqualZOverlap 本身是弹层场景专用断言，非通用 hit-target 检查 |
| F-05 完整性 | 命中回读按需求分析原文完整交付 | F-05 以「部分交付 + 报告如实标注未验证处」交付，核心 F-ID 缺角 |

### 1.2 推荐：**选项 A（小步暴露）**

依据（按权重）：

1. **机器已在框架内且每帧消费**：`Runtime::update` 每帧调 `resolveHoverTarget`（`EUI-NEO/core/runtime/runtime_lifecycle.h:130`），`hitTestInteractive`（`runtime_input.h:49`）是 const 纯查询（不改 hover 缓存）。暴露 = 在 public 段加一个转发的 inline 只读方法，无新逻辑、无状态、无双平台分叉——成本近乎下限。
2. **B 的可用近似不存在**：真正防住「点击被截胡」只有复刻命中判定一条路，而那条路在 DevDesk 违反代码负资产纪律（§1.1 第三行）；`assertNoEqualZOverlap` 是弹层 z 碰撞扫描器，拿来当通用 hit 代理是错位使用。
3. **driver 的产品价值 = 报告可信**：命中回读失败诊断（「目标 id X 的中心点实际命中了 id Y」）是交互链报告里最值钱的一类结论；没有它，z 序/弹层类回归继续只有用户能发现。
4. **跨仓提交义务是流程成本而非技术风险**：AGENTS.md §一已有「先推 EUI-NEO fork 再推 DevDesk」硬纪律与 CI 失败先例警示，照办即可。

**B 不作为首版、也不作为回退保留**：若审计推翻 A，B 的落地形态 = click 步骤无命中断言 + 报告按 AGENTS.md §八精神在未验证处如实标注——不静默绿。`assertNoEqualZOverlap` 本身不进本首版原语集（无场景要求）。

**两案通吃的豁免口**（对齐 Playwright `force`）：click 步骤可加 `"force": true` 跳过命中断言，场景作者显式声明「我知道该点会被截胡/我只要事件送达」。默认 `false`（断言开启）。

### 1.3 暴露接口定稿

```cpp
// EUI-NEO/core/dsl_runtime.h —— public 段新增（唯一框架 API 增量）
/// 只读命中查询：返回 (x, y)（逻辑像素 × dpiScale 换算后）命中的首个可交互元素 id
/// （interactive && !disabled，z 序最顶层优先，clip 外 miss）。纯查询，不改
/// hover 缓存 / 触发任何回调。测试/驱动设施专用，app 主循环不应依赖。
std::string hitTestInteractiveAt(double x, double y, float dpiScale) const;
```

定义 inline 在 `runtime_input.h`（与 private `hitTestInteractive` 同文件）：构造 `PointerEvent{x*scale, y*scale, action=Move}` 直接调 private `hitTestInteractive`。**不**走 `resolveHoverTarget`（它会写 hover 缓存，有副作用）。

**为何是「新鲜查询」而非暴露每帧已算出的 hover target**（选项 A 的两个子形态中裁定前者）：每帧 hover target 是带缓存语义的内部状态——`resolveHoverTarget` 写 `hoverTargetCache*`（`runtime_input.h:73-90`）、`canReuseHoverTarget` 按动画/树变/坐标变判失效；把它暴露成公开 API 等于把框架内部缓存契约升格为公开 ABI，且读到的是「上一帧悬停结果」而非「该点此刻命中」。`hitTestInteractive` 是 const 无状态纯查询，随查随得、幂等、可并发断言多点，暴露面最小。

> 坐标空间说明：probe 窗口不可缩放、`pollOnce` 恒传 `pointerScale=dpiScale=1`（`probe_harness.h:281-288` 自注释），driver 场景内逻辑=物理，换算恒等；接口仍带 dpiScale 形参对齐框架 Physical 约定（`runtime_input.h:397-409` 注释），不为 driver 破例。

## 2. 总体架构：driver = probe_harness 的脚本化外壳

```
devdesk_ui_driver (新可执行, tests/ui_driver/)
  main: 参数解析 → 金丝雀(probe::initializeWindowBackend 复用) → 临时数据根组装(F-08)
        → 真模块注册表 + Router + app::compose(uat62/module_toggle 同款装配)
        → 解释器逐步骤执行(帧循环) → 报告汇总 → 退出码
  复用层（零改动）: probe_harness.h 五原语/截图/金丝雀/pollOnce/composeModuleFrame
                    walkElements / glfwKeyToInputKey / decodeKeyModifiers
                    EUI-NEO core::queue*Input / Ui::find / Element.frame
                    test_support.h DataRootEnv / TestDb / ScopedAppRouter / seedAppConfigJson
                    platform::json parse/stringify
  新增层（六组装件）: §3
```

与既有 probe 的关系：**driver 不替代任何 probe**（probe 是 C++ 独占判据，driver 是脚本化交互链），二者并存；probe 门禁口径变化仅「ctest 总数 +N」，TIN-10 自检同步登记。

## 3. 六组装件设计（落点 / 复用关系 / 测试面）

统一惯例：header-only（对齐 `probe_harness.h` / `test_support.h`），namespace `ui_drive`；main 只做装配不做逻辑。

**分层纪律（审计补集②，硬约束）**：组件分两层，落点即分层——

- **底层头 4 个，零 `probe_harness.h` 依赖**：schema 解析、键名表、判定纯函数、报告格式化——**六类纯函数（schema 解析 / report / wait 条件评估 / 几何谓词 / 键名表 / 命中判定）全部落在这层**。进 `devdesk_tests` 的单测 TU **只准 include 底层头**：`probe_harness.h` 拖着 png.h / GL loader / GLFW 窗口设施，而 devdesk_tests 链接集（`tests/CMakeLists.txt:318-331`）没有 PNG 目标（libpng FATAL_ERROR 守卫 `:431-444` 只挂 probe 目标）——纯函数若与编排混在一个头里，单测 TU 一 include 就直接编译失败。键名表层仅可依赖 GLFW 常量头（`GLFW_KEY_*` / `GLFW_MOD_*`，`GLFW_INCLUDE_NONE` 下不含平台 GL 头）。
- **编排头 2 个，include `probe_harness.h`**：解释器（动作 dispatch + wait 轮询循环 + 命中回读执行）与 id dump——持有窗口 / Runtime / 帧循环，只做编排不做纯逻辑。
- 纯函数签名一律收**基础数据**（`Element*` / `LayoutRect` / parentOf 表 / 字符串），树遍历（`walkElements`，住在 probe_harness detail）由编排层做完传入——底层头因此不需要 probe_harness 的任何设施。

| 层 | 组件 | 落点 | 职责与复用 | 测试面 |
|---|---|---|---|---|
| 底层 | 场景解析 | `tests/ui_driver/driver_schema.h` | 读文件 → `platform::json::parse`（新增带错误详情重载，§7.3）→ schema 校验（§4.3）→ `Scene` 结构（settings + `std::vector<Step>`）。非法键/未知 type 给**相近候选**（前缀/子串匹配 ≤5 个，对齐 AC-2 口径）；键名合法性经 `driver_keys.h` 查表 | 无头单测（REGISTER_TEST，进 `devdesk_tests`）：正例 + 负例矩阵（缺 version / 未知键 / 未知 type / 0 步 / 类型错 / 相近提示内容） |
| 底层 | 键名表 | `tests/ui_driver/driver_keys.h` | 语义键名 → GLFW 键码 + 修饰位（§4.4）；仅依赖 GLFW 常量头；被 schema（加载期校验键名）与 steps（执行期查表）共用——这个共用关系正是它必须待在底层头的理由 | 全表无头单测（"Enter"→GLFW_KEY_ENTER、"Ctrl+S"→GLFW_KEY_S+MOD_CONTROL、"Shortcut+"→平台判定位、未知键名 miss + 相近候选）。GLFW 键码→`InputKey` 层在 probe_harness 内，不在无头单测射程（见 §4.4） |

## 4. 场景文件 schema 草案

### 4.1 顶层与通用字段

```json
{
  "version": 1,
  "settings": {
    "defaultWaitTimeoutMs": 5000,
    "failureStrategy": "fail-fast",
    "window": { "width": 1200, "height": 1000 },
    "seed": { "config": { "appconfig命名空间": { "...": "..." } } }
  },
  "steps": [ { "type": "...", "...": "..." } ]
}
```

- 每个步骤对象：`type` 为唯一判别键；可选 `_comment`（JSON 无注释的补偿约定，加载期忽略）；`timeoutMs`（wait 类步骤覆写默认超时）。
- `version` 加载期校验为 `1`；未知顶层键/settings 键/步骤键 → 退出码 2 + 相近键候选（防静默错拼，与 id 候选同机制）。

### 4.2 九种步骤类型

```json
{"type":"click","id":"todo.board.new","button":"left","force":false,"readback":true}
{"type":"click","point":[600,500]}                  // 兜底坐标点击；AC-2 场景禁用，报告标注「坐标步骤」
{"type":"type","text":"缴费"}                        // UTF-8 全量注入（queueText 语义）；前置须已聚焦输入框
{"type":"key","name":"Enter"}                        // 语义键名 + 组合键，见 4.4
{"type":"scroll","dx":0,"dy":-3,"id":"todo.board"}   // id=定位滚动点（frame 中心）；省略=窗口中心
{"type":"drag","from":"idA","to":"idB","steps":8}
{"type":"wait","until":"exists","id":"todo.item.x","timeoutMs":5000}   // exists | missing
{"type":"wait","until":"text","op":"contains","text":"缴费","timeoutMs":5000}   // 全页叶子文本扫描
{"type":"wait","ms":400}                              // 固定模拟帧等待（动画兜底，非首选）
{"type":"assert","check":"exists","id":"..."}         // exists | missing
{"type":"assert","check":"text","id":"...","op":"contains|equals","text":"缴费"}  // op 省略=contains（需求 F-03「文本含/等」）；带 id=该元素，省略 id=全页扫描
{"type":"assert","check":"geometry","id":"...","op":"within-window"}    // within-window | intersects（"other":"idB"）
{"type":"screenshot","path":"todo-new.png"}           // 相对 --out-dir
{"type":"dump","path":"todo-ids.txt"}                 // 当帧元素树落盘（场景编写辅助）
```

示例（todo 新建任务全链，示意——**id 以 `--dump-ids` 实测为准**）：


### 4.3 校验规则（加载期，全部退出码 2）

文件不存在 ｜ JSON 解析失败（§7.3 行号）｜ `version != 1` ｜ 未知键（顶层/settings/步骤，给相近候选）｜ `steps` 缺失或 **0 步（防假绿，对齐 devdesk_tests 0 命中退 2 口径）** ｜ 字段类型错 ｜ 语义键名查表 miss（给相近键名候选）。

### 4.4 键码契约（双份映射问题怎么收）

- **新增的只有一层**：driver 内「语义键名 → GLFW 键码」表（`driver_steps.h` 内 `constexpr` 表）。`"Enter"/"Escape"/"Tab"/"Backspace"/"Space"/"Delete"/"Insert"/"Home"/"End"/"PageUp"/"PageDown"/"Left"/"Right"/"Up"/"Down"/"A".."Z"/"0".."9"/"F1".."F24"`。
- 组合键修饰前缀：`"Ctrl+"`→GLFW_MOD_CONTROL、`"Shift+"`→SHIFT、`"Alt+"`→ALT、`"Cmd+"/"Win+"`→SUPER、`"Shortcut+"`→经 `test_support::setShortcutModifier` 判定（与仓内既有惯例同源：把 EUI-NEO `KeyModifiers::shortcut()` 当唯一判据，测试侧零平台宏，test_support.h §8）。
- **GLFW 键码 → `InputKey` 一层不新增**：复用 `probe_harness::glfwKeyToInputKey`。既有 probe_harness vs `window_input_backend::mapGlfwKey` 双份（`probe_harness.h:534-536` 自警）**本期不动**——那是方案 C 档 2 的键码单源化范畴（§6），在本需求里动它属于范围外。
- 解析链：`"Ctrl+S"` → 语义名表查 S → `GLFW_KEY_S` + MOD_CONTROL（底层 `driver_keys.h`）→ `glfwKeyToInputKey`（probe_harness detail，**编排层执行**）→ `InputKey::S`。底层表无窗口、无头可测；GLFW 键码→`InputKey` 层不在无头单测射程（include probe_harness 即拉 png.h，见 §3 分层纪律），由既有 probe 长期运行覆盖，双份消除属方案 C 档 2。
- 平台注记：修饰位映射到 GLFW_MOD_* 原始位，与平台无关；**判定 `shortcut()` 的行为**（如 app 内 Cmd+S 保存）在 macOS 上应写 `"Shortcut+S"`——场景内该步骤语义双平台一致，键名双平台一致，无平台分叉表。

## 5. F-01～F-08 逐条实现方式 + 先红后绿验证法

> 红绿总则：每个 F-ID 的验证 = 无头纯函数单测（进 `devdesk_tests`，先红后绿，自检「删掉实现代码会红」）+ 场景级 ctest 用例（真窗）。**驱动器自身的负路径（期望失败的场景）不进 ctest 回归**——ctest 的 WILL_FAIL 语义只能把「退出非 0」翻成通过，无法区分「步骤失败（退出 1）」与「用法/场景加载非法（退出 2）」，注册负路径会把真正的用法错误回归一并吞掉；负路径红绿在开发期以临时场景演示并在本卡验收记录留痕。

## 8. 边界与非目标守住（对应需求分析 §6 / §9）

1. **多窗口/独立子窗：本期非目标，边界守住方式**——driver 组装为单窗（probe 同构），主射程 = app 组装内模块页 + **同窗弹层**（下拉/toast/dialog 与主页面同一 Runtime 命中链可达）；独立子窗、托盘菜单、系统文件对话框等 OS 原生控件不在射程：场景引用其元素 → id miss → 步骤 fail，stderr 明示「该 id 不在当前页元素树（独立子窗/OS 原生控件不在驱动射程）」；`--dump-ids` 只出主窗树。方案 B/B-lite（真 app 进程、托盘/多窗全链）维持不做，验收替代手段按需求分析开放问题 7 由审计确认。
2. **滚动到位原语：首版不纳入**。事实：clip 外元素点击必 miss（`runtime_input.h:139-153` 提前返回，**显式否证**需求分析 §9「视口外元素可点」假设，调研 §6.10）；通用 scrollIntoView 需判定目标滚动容器并自算偏移（框架无现成原语，自算 = 复刻布局知识，负资产）。落地：schema/用户文档明示「场景仅支持当前可见（clip 链内）元素」；视口外目标用 `scroll(dx,dy)` + `wait until exists` 组合显式驱动（示例进 USER_GUIDE）；若后续场景普遍撞墙再升原语（届时先做框架侧 scrollable 几何查询，不在 DevDesk 自算）。
3. **动作前自动等待**：首版不做（§5 F-02），失败显式落在 wait 步骤；`--strict-actionability` 后续开关不排期。
4. **id 稳定性登记表**（需求分析开放问题 2）：首版不做 TIN-10 式登记校验——兜底 = 失败时相近 id 候选 + dump 子命令 + 场景评审（场景过独立审计的流程本来就在）；登记表进 backlog 待真实断场景频率数据。
5. **CI 离屏渲染**（开放问题 5）：不排期，维持诚实跳过不劣化（77 + Skipped 单独计数）。
6. **既有 probe 关系**（开放问题 6）：永久并存，不替代不回补。

## 9. 规模结论：**M 维持（上限方向）**

- **维持 M 的依据**：五块核心基建（注入原语/帧驱动/截图/临时数据根/键码映射）全部现成（调研 §5 file:line 全标）；六组装件均为纯组装（解析/解释/轮询/封装/格式化/打印），无能力攻坚；框架增量 ≈10 行只读查询 + 单测；唯一 src/ 触点是 additive 重载且带回退档。
- **顶到上限的因素**：跨仓提交义务一次（档 1）；场景 schema 是长期契约需过独立审计；双平台验证义务两轮；`platform::json` 重载触 src/（虽 additive，仍扩了「零 src/ 改动」的原前提，审计须显式确认）。
- **不升 L 的原因**：无生产逻辑改动、无跨线程注入、无 IPC 常驻缝、CI 不强制离屏——F-09 维持不做、方案 C 只走档 1 是守住 M 的两个闸门，本卡都未松。
