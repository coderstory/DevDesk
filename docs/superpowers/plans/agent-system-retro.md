# agent-system-retro.md — Agent 体系建设总结会纪要（2026-10-28）

> 本会话的功能模块 = 「AI 开发体系」本身（非 DevDesk 功能）。按 DOCS-CONVENTIONS 骨架落盘。

## 一、用户原则全录（宝贵经验，本体系的立法来源）

1. **检索接地**：多调研、多分析、多阅读，Google/GitHub 有大把资料，不要闭门造车。豆包/元宝更准更完整的根源 = 检索接地，不是模型更强。
2. **平实角色观**：ZCode 下就是普通的子任务角色定义，不搞多 agent 编排系统。
3. **失效模式清单**（原话浓缩）：需求分析不全；UI 与效果图差距大；功能漏大量细节；单测敷衍重指标轻验证；调研不积极没最新资料；闭门造车写不稳定代码；过度设计过度防御；注释行数超代码（接口/架构/历史全塞进去）；节奏迟缓、功能点拆到类/方法/文件级还每次全流程；子任务成本不权重（2 行修改也派）；不考虑关联需求与代码；单测全绿当完成证据，人工一看是半成品；验收必须实操实证走完整用户流程；PM 决策要先看同类产品、行业经验与软件自身习惯，不拍屁股；测试要基于业务，覆盖率在 AI 开发时代没有意义。
4. **证据物硬标准**：实证 = 截图、日志、执行数据等实际证据，是完成验收的硬标准。
5. **克制原则**：memory / lessons 不是垃圾桶，写太多会崩。
6. **代码是负资产**：写代码要有完整成熟的技术方案和参照（商业软件都是第三方组件堆的）；最小代码完成 90% 功能，学会取舍；衡量依赖看两点——带来多少价值、功能用了多少（本项目另加静态链接硬约束）。
7. **有手**：方案、猜想、推测要写 POC 代码实证，「不是光长个脑子」；证据等级：实跑 > 一手来源 > 二手推断。
8. **卡片协作**：PM 最终输出 PRD + 功能矩阵（唯一状态源）；QA 出测试清单（验证需求/流程/方法）；研发出技术方案；角色间用卡片交换信息、互相推进。
9. **角色定义五要素**：执行条件（何时执行/不执行）、权限边界（能做/不能做）、规范流程、输入输出契约、硬约束——边界必须清楚。
10. **agent 不只是 md**：配武器（脚本）、带小抄（速查清单）、自进化（沉淀经验）；用 skill 分担职责，用 hooks 强行干预流程做门禁。
11. **本质同源**：agent/MCP/hooks/skill 都是能力扩展机制，只是场景特化；强 agent 给项目安装 hooks/skill/MCP 拉帮结伙增强自己。
12. **参考现成经验**：有很多 create-agent skill 与评测方法论可借鉴，如何写好、如何评测 agent 都有成熟资料。
13. **沉淀总结会**：模块开发完毕执行，AI 侧（复盘/流程完善/审计）+ 项目侧（整顿文件代码）双线。
14. **文档规范**：统一定义存放位置、目录组织、命名方法、内容结构。
15. **自迭代兜底**：本会话生成的任何功能都自带自我更新迭代能力；无更新通道的产物即违规。
