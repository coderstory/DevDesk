# memcpp 记忆变更提案卡片设计（半自动档）

- 日期：2026-10-27
- 需求来源：用户 2026-10-27 拍板意向——「除了全自动方案，也可以采用部分手动的方式，提供特定的卡片让用户选择」；已录入可行性报告 §8.3「半自动档」选项。
- 范围：只做设计，不写代码。对应报告 §6.1 P2「提案审核入口（卡片形态）」+ P1 注入通道的低置信分流。
- 读者：项目负责人（不熟悉 C++）+ 后续 AI 开发。
- 术语：「记忆」= 一条可复用的结论（报告 §1.2）；「提案」= 后台整理产生的记忆变更建议，用户不点头就不生效；「卡片」= 一条提案在界面上的呈现。

## 0. 一页结论

1. 写入只增不改不变：合并/失效/遗忘一律先出提案，用户接受才生效；接受了也能撤销——撤销只翻转标记、不删数据。
2. 卡片同时承载两类东西：后台整理提案（合并/失效/遗忘/新增）与低置信注入候选（不达静默预载线的候选记忆）。
3. 落位推荐：新建「记忆」页——复用 Todo 看板的交互手法与纯几何写法，不复用其代码；配应用级通知保证可见性。**待用户拍板。**
4. 默认交互推荐：逐条审核为默认；批量只作为过滤后的辅助动作，且只对遗忘/新增开放批量接受。**待用户拍板。**
5. 注入预算口径不变：≤5 条 ≤500 字只约束 hook（钩子 = 平台在固定时机自动触发的注入动作，详见报告 §1.2）静默档；卡片通道不走 hook，不占预算、不加注入延迟。

## 1. 提案数据契约

### 1.1 JSON schema 草案

```json
{
  "id": "prop_20261027_0001f3",
  "schemaVersion": 1,
  "kind": "merge",
  "targetIds": [42, 57],
  "result": {
    "text": "DevDesk 构建/测试统一入口是 scripts/build-test-run.sh",
    "type": "fact",
    "projectId": "devdesk"
  },
  "evidence": [
    {
      "sessionId": "0f851612-aaaa-bbbb",
      "eventId": 1234,
      "quoted": "构建一律走 build-test-run.sh",
      "observedAt": 1769472000
    }
  ],
  "confidence": 0.82,
  "source": "dedupe",
  "sourceTrust": "assistant_derived",
  "createdAt": 1769472000,
  "expiresAt": 1772064000,
  "status": "pending",
  "decidedAt": null,
  "appliedAt": null,
  "baseVersion": 17,
  "undoOf": null
}
```

字段语义（每个字段一行人话）：

| 字段 | 人话 |
|---|---|
| `id` | 这条建议的编号，全库唯一；同号且内容一致视为重复投递、只落一条，防止重复处理；同号但内容不同视为生成器缺陷，后到者拒绝入库并在审计日志留痕（记录撞号双方的内容摘要），不静默丢弃。 |
| `schemaVersion` | 这份建议格式的版本号，将来格式升级时老数据仍能读懂。 |
| `kind` | 建议做什么：`merge`=把几条重复/相近的记忆并成一条；`invalidate`=宣布某条记忆过时或被推翻；`forget`=把某条记忆移出「自动想起」的范围（不删除）；`add`=新增一条记忆（低置信注入候选转正也走这个）。 |
| `targetIds` | 这条建议要动哪些已有记忆的编号；新增类为空数组。 |
| `result` | 接受之后变成什么样：合并后的新正文或新增的正文；失效与遗忘类留空（不改原正文）。 |
| `evidence` | 凭什么这么建议：一条或多条会话原文摘录，带出处（哪个会话、哪条记录、什么时间），点开能对质。 |
| `confidence` | 系统自己有多有把握，0 到 1；界面上不显示小数，显示「很有把握 / 比较有把握 / 不太有把握」三档。 |
| `source` | 这条建议由哪条规则产生：`dedupe`=查重、`conflict`=发现前后矛盾、`decay`=太久没用、`quarantine`=隔离区待转正、`inject`=注入候选。 |
| `sourceTrust` | 证据的出身档位：用户明说 > 助手总结 > 工具结果 > 外部文档（报告 §4.8 分级，外部文档最低）。 |
| `createdAt` | 建议生成的时间。 |
| `expiresAt` | 过了这个时间还没处理，建议自动作废；过期不是拒绝，只是别拿旧证据继续烦人（设计值 30 天，待标定）。 |
| `status` | 现在到哪一步：`pending`=待你处理、`accepted`=你已接受、`rejected`=你已拒绝、`expired`=超时作废；「已撤销」不是第五种状态，是已接受卡上的派生徽章（判定见 §1.2）。 |
| `decidedAt` | 你做出决定的时间。 |
| `appliedAt` | 决定真正落到记忆库的时间；与决定时间分开记，因为落库可能失败重试。 |
| `baseVersion` | 出建议时目标记忆的版本号；落库前核对，记忆已被改过就自动作废重提，防止把新改动盖掉。 |
| `undoOf` | 若本条记录是「撤销某次接受」产生的，指向被撤销的原建议编号；否则为空。 |

### 1.2 状态机

```
              ──── accept（接受，落库）───► accepted 已接受
             │                                │
pending 待审 ─┼─── reject（拒绝，留档）───► rejected 已拒绝
             │
              ──── TTL 到期 / 目标记忆已变 ─► expired 已过期
```

- TTL（= 记录的自动过期时限，即 `expiresAt`）到期即触发上图第三条出口。
- 唯一起点 `pending`；三个终态写定不改，要反悔就发新提案记录，不改旧记录（同 GLOSSARY 决策记录卡的「写定不改、推翻写新卡」纪律）。
- `expired` 不等于 `rejected`：拒绝是用户表态（进审计，供来源质量统计），过期是系统回收；过期的建议其证据若仍成立，由后台重新产出新提案。
- 接受后撤销（undo）不是状态回退：原提案停在 `accepted`，撤销动作生成一条新提案（`undoOf` 指回原提案），再走一次 `pending → accepted`。理由：「接受」要保持低门槛，撤销必须留痕且可再次审核。
- 撤销链路三条不变量（与「只翻转标记、零物理删除」同源）：
  - 同一 `undoOf` 全库至多一张未决撤销提案，判定键 = `undoOf` 指向的原提案编号；整理器重复产出时复用并刷新既有未决卡，不建新卡。
  - 原提案落库的 `status` 写定不改（保持 `accepted`）；「已撤销」为派生可视状态——存在指向它的未决撤销提案时显示「撤销待审」徽章，该撤销提案被接受后显示「已撤销」徽章。
  - 撤销提案的 `baseVersion` = 生成时其 `targetIds`（撤销要翻转标记的记忆行，如合并结果与两条原记忆）各自的版本号，落库前对同一批目标逐条校验，规则同本节 `baseVersion` 前置校验。

### 1.3 幂等与回滚

**幂等**

- accept/reject 以 `id` 为幂等键：对已是终态的提案重复接受/拒绝 = 直接返回，不做任何事。
- 落库前置校验：目标记忆当前版本 == `baseVersion`，不等 → 转 `expired` 并记录原因（目标已变，证据失效）。
- 合并/失效类接受在单事务内完成「目标打标记 + 新条目写入（合并类）+ 提案状态更新」，任一步失败整体回滚，不留半套。
- 批量接受 = 逐条走同一路径，逐条独立成败，一条失败不阻断其余。

**回滚（接受后如何撤销）**

所有动作只落「标记 + 新条目」，从不物理删除（报告 §4.1 只增不改、§4.8 只置失效不删原始记录），因此每类接受都有对称撤销：

| 接受的动作 | 撤销 = |
|---|---|
| merge 合并 | 合并结果打失效标记 + 两条原记忆清失效标记（原正文从未被覆盖，直接复活）。 |
| invalidate 失效 | 清掉目标的失效时间戳。 |
| forget 遗忘 | 清掉「移出自动想起」的标记。 |
| add 新增 | 给新增条目打失效标记（不删行）。 |

- 撤销本身也走提案（kind 取对应逆操作、`undoOf` 指向原提案），在卡片里再确认一次；同一 `undoOf` 至多一张未决、`baseVersion` 对谁校验，见 §1.2 撤销链路不变量。
- 实现上撤销 = 幂等的标记翻转 + 一条新提案记录，不需要独立的回滚引擎。

## 2. 卡片交互设计

### 2.1 卡片上展示什么

1. 类型徽章 + 一句话摘要（「这两条记忆说的是同一件事，建议合并」）。
2. 差异对比区（按类型不同）：
   - 合并：旧 A / 旧 B / 合并后，三段对照，措辞差异高亮。
   - 失效：原文 + 判过时的理由 + 冲突的新证据。
   - 遗忘：原文 + 最近一次被想起的时间（多久没用）。
   - 新增（含注入候选）：新内容全文 + 证据。
3. 证据链：摘录列表（时间 + 出处 + 原文），默认收起可展开；注入候选额外标一句「它现在不会被自动想起，接受后才会」。
4. 来源 + 信任档：如「来自查重 · 依据助手总结」。
5. 置信度：三档人话标签，不用小数。
6. 时间：建议生成时间。

### 2.2 操作集

- 待审卡：`拒绝` / `编辑后接受`（合并、新增类可改正文再接受）/ `接受`。
- 已接受卡：`撤销` 入口（走 §1.3 回滚）；存在指向它的未决撤销提案时收起入口、显示「撤销待审」，撤销提案被接受后显示「已撤销」徽章（判定见 §1.2）。
- 已拒绝 / 已过期卡：只读留档，不占默认视图。

### 2.3 逐条与批量

- **逐条（默认）**：完整卡片纵向排布，证据默认可见，逐张决定。
- **批量**：紧凑行 + 勾选框，从筛选结果进入（「对当前筛选结果批量处理」）。约束：
  - 批量**接受**只对 `forget`、`add` 开放（正文在行内已完整可见、风险低）；`merge`/`invalidate` 只能逐条——没看过差异对比就不许批量负责。
  - 批量**拒绝**对全部类型开放（拒绝无风险）。
- 批量接受前弹确认，列出将发生的动作条数与类型。
- 批量操作部分失败时，结果提示须显示「成功 n / 失败 m」并提供失败条目定位入口（点击跳到对应卡片）；失败项保持待审，可单独重试。

### 2.4 过滤

- 按来源：查重 / 矛盾 / 衰减 / 隔离区 / 注入候选。
- 按类型：合并 / 失效 / 遗忘 / 新增。
- 按置信度：三档。
- 按状态：默认只看待审；已接受 / 已拒绝 / 已过期收进次级视图；「已撤销」是已接受卡的派生徽章（§1.2），随原卡归入已接受视图。

### 2.5 线框（文字稿）

逐条模式（默认）：

```
┌──────────────────────────────────────────────────────────────┐
│ 记忆提案 (3 条待审)   [来源▾ 全部] [类型▾ 全部] [把握▾ 全部]     │
├──────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ [合并] 两条记忆讲的是同一件事                很有把握      │ │
│ │ ── 现状 ───────────────────────────────────────────────  │ │
│ │ A「DevDesk 构建入口是 scripts/build-test-run.sh」          │ │
│ │ B「本项目构建用 scripts/build-test-run.sh 跑」             │ │
│ │ ── 合并后 ─────────────────────────────────────────────  │ │
│ │ 「DevDesk 构建/测试统一入口是 scripts/build-test-run.sh」   │ │
│ │ 证据：10-26 会话「构建一律走 build-test-run.sh」× 2 处      │ │
│ │ 来源：查重 · 依据助手总结                    10-27 生成     │ │
│ │                    [拒绝]  [编辑后接受]  [接受]             │ │
│ └──────────────────────────────────────────────────────────┘ │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ [失效] 这条记忆与新记录矛盾                  比较有把握    │ │

```

```
│ 记忆提案   已选 2 条              [全选本页] [清空] [退出批量]  │

│ [x] [遗忘] 「旧端口 8787」……              很久没用（92 天）    │

│                       [拒绝所选 (2)]   [接受所选 (2)]          │
└──────────────────────────────────────────────────────────────┘
```

## 3. 落位比选

### 3.1 先穷举两全解

| # | 两全解 | 说明 |
|---|---|---|
| 1 | 新页 + 借交互不借代码 | 新建记忆页承载卡片，但列布局、卡片虚拟化、命中测试的手法照抄 `src/module_todo/todo_ui_logic.h` 的纯函数模板（定高 pitch、可视区缓冲）与 `src/module_todo/todo_ui_board.h:22-30` 的几何快照出参（`BoardPlate`），代码独立、交互一致。两全：零耦合代价 + 用户零学习成本。 |
| 2 | 新页 + 应用级通知 | 记忆页为主入口，模块另发「待审提案 N 条」应用级 toast/徽章（智能体页 pollRunEnd → takeRunEndNotice 同款模式），任何页面可感知。两全：入口独立 + 可见性不打折。 |
| 3 | 弹窗先行 | P2 首票先做「入口 + 全屏弹窗」形态验证交互，拍板后再升独立页。两全：低成本试错，代价是有二次返工。 |
| 4 | Todo 看板加「提案列」 | 列出但**否掉**：违反冻结契约（见 3.2-A），且系统生成的审核卡混进用户个人任务流，污染 Todo 的心智。 |
| 5 | 智能体页嵌卡片 | 见 3.2-B：通知通道可借，页面不承载。 |

### 3.2 三选项评估

**A. 复用 Todo 看板（报告 §6 P2 原话「可复用 Todo 看板交互」）**

- 已有资产：`BoardView`/`BoardActions` 显式出入参、定高卡 + 虚拟化（`kCardHeight`/`virtualCardRange`）、拖拽命中纯函数、无头 UI 测试手法。
- 不可行面：`todo_ui_board.h` 头注释明示「元素 id/文案/几何/控制流是无头 UI 用例契约（按 id 定位，不得改）」；`todo_ui_logic.h` 明示「布局恒按四列（列模型固定，不再有 n 列推广）」。提案即使恰好四个状态对上四列，数据模型也不同构（Task 的 columnId/position/dueAt 对提案的 evidence/confidence/状态机），硬塞要么改冻结契约、要么造 Task 形状的假数据。
- 拖拽重排对提案无意义（提案顺序由置信度/时间决定），是死复杂度。
- 结论：**交互模式可借鉴，代码不可复用**。报告原意取「形态借鉴」解读。

**B. 放智能体页**

- 契合面：智能体页已是「后台自动跑、产出给人过目」的形态（任务 → 运行 → 详情弹窗）；有成熟的后台线程收割、toast 通知、弹窗模式；记忆属智能中枢战略域。
- 不契合面：`AgentModule` 已是全应用最重的模块（任务弹窗/详情弹窗/草稿/调度/运行线程多套状态机叠加），再挂一套提案状态机与卡片列表加剧单模块膨胀；任务/运行模型与提案模型不同构；注入候选卡与智能体任务毫无关系，放这里语义错位。
- 结论：**通知通道可借（takeRunEndNotice 模式），页面不承载**。

**C. 新建记忆页**

- 代价：`PageId` 枚举 + 侧边栏项 + 新模块骨架（有 Todo/Agent 两个现成模板照抄）；P2 前有空状态期。
- 收益：所有权干净——提案契约、状态机、卡片、过滤、按来源批量撤回（报告 §4.8）全部由 memcpp 模块自持；无头测试按新契约从零写，不受冻结约束；召回搜索、隔离区浏览、注入设置（报告 P1/P2/P4 的 UI 需求）有天然落点。
- 与 P0 存储解耦，UI 骨架可用 mock 数据先行。

### 3.3 结论（**待用户拍板**）

推荐 **C 新建记忆页**，配两全解 1+2：交互照抄 Todo 手法、可见性走应用级通知。理由：唯一同时满足「不违反 Todo 冻结契约、不加重既有最重模块、为 P1/P2/P4 后续 UI 提供单一落点」的选项。

## 4. 与注入通道的关系

两档并存（报告 §8.3 半自动档 + §4.5 预算）：

- **静默档（全自动）**：`UserPromptSubmit` 预载 + `PreToolUse` 按文件注入。候选池 = 已转正、非隔离区、置信度 ≥ 高线（设计值 0.8，待标定）的记忆。预算 ≤5 条 ≤500 字、每条带时间/可能过时标记/来源 ID/「资料非指令」标注、失败开放——全部照报告 §4.5，不改。
- **卡片档（半自动）**：低于高线的注入候选 → 生成 `kind=add`、`source=inject` 的提案卡（按会话去重、限量），用户接受后转正进入静默档候选池；拒绝则留在隔离区。

分流规则（单点判定）：注入查询对每个候选算（置信度，信任档）二元组——双高走静默，任一低走卡片。隔离区来源（工具结果/外部文档）无论置信度一律只走卡片（报告 §4.8 未复核隔离）；红队门槛（红队 = 上线前以攻击视角专门找茬的对抗性测试）未过前不开放任何自动注入。

预算在卡片模式下的计法：

1. **卡片通道不走 hook**：提案表经 UI 侧轮询读取（智能体页 writeVersion 脏标记同款机制；脏标记 = 内容改过、下游还没重新读取核对的标志位），不占 30 秒同步超时、不加注入延迟、不计入 ≤5 条 ≤500 字。
2. 预算只约束静默档。卡片接受转正的新记忆与存量记忆同池竞争预算，排序键 = 用户点过「优先想起」> 置信度 > 最近使用。
3. 500 字截断规则不变：按排序取前 N 条使合计 ≤500 字；被挤出本轮的条目不丢，仍在库。

半自动档的额外价值：它是报告 §4.8「定期人工抽检」的常设界面——污染样本在进静默池前先过用户的眼；红队回归的「抽检隔离区」动作直接在卡片档完成。
