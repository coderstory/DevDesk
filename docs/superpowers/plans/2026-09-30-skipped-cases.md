## S1 托盘图标纯白方块（初版纯黑）——已修（5e92aaf）

### 背景

macOS 菜单栏托盘图标显示为**纯白方块**；据用户观察，初版曾是**纯黑**。图标
没有呈现出任何图形内容，只有一块实色。调查未定位到图标来源与资产，超时跳过。
**后续已修（`5e92aaf`「托盘专用 template 图标替代应用图标兜底」）：本案例
闭环，以下线索 / 假设保留为修复史留痕。**

### 已有线索

- 【实证 / 平台行为】macOS 菜单栏对 template image 有**深浅色自动反色**机制：
  系统按菜单栏明暗把黑白翻转。黑白互换只能解释「纯黑 ↔ 纯白」的翻转方向，
  与两次观察到的现象方向一致。
- 【实证 / 调查时快照】`grep -rn -i "setTrayIcon\|trayIcon" src/` 在 DevDesk
  **零命中**——当时 DevDesk 侧不存在以这两个名字调用托盘图标的代码（修复前
  口径，修后命中见下一条）。
- 【实证 / 修后同步（2026-09-30）】`5e92aaf`：`src/main.cpp` 托盘配置新增
  `.trayIcon("assets/tray-icon-template.png")`（22×22 纯黑 + alpha 蒙版
  template 图标，CMake POST_BUILD 拷进 `<build>/assets`）；真实 API =
  EUI-NEO `DslAppConfig::trayIcon(path)`（`eui/dsl_app.h:155`）。
- 【已定位 / 根因】不传 trayIcon 时 EUI-NEO 兜底取**应用图标**并无条件
  `setTemplate:YES`——模板渲染只取 alpha 蒙版，圆角方形应用图标退化成纯色
  实心方块，颜色随菜单栏深浅翻转（「纯黑 ↔ 纯白」两次观察同源）。

### 剩余假设

- 【假设】深浅色适配翻转：图标以非 template image 方式或黑白不合规范的资产
  传入，被系统反色后整块变实色。
- 【假设】资产缺失回退占位：图标文件未找到 / 未打包，实现走了纯色占位绘制
  路径（黑→某次改动→白）。

### 建议下一步

1. 在 `../EUI-NEO/` grep `statusBar` / `tray` / `menuBar` / `NSStatusItem`，
   定位真实 API 名、图标资产的加载路径与 template image 判定逻辑。
2. 回到 DevDesk 查调用点传入的图标来源（文件路径 / 打包是否覆盖）。
3. 深浅色两种系统模式下各实测一次，区分「翻转」与「占位」两条假设。

## S2 桌宠「显示桌宠」点击无效（重启后正常、点击无日志）

### 背景

设置页桌宠卡的「显示桌宠」按钮点击后桌宠不出现；**重启应用后桌宠正常**；
点击时**一行日志都没有**。调查未定位静默断点，超时跳过。

### 已有线索

- 【实证】启动路径正常：重启后桌宠能正常出现，说明 pet 模块本体、皮肤发现、
  子窗创建链路完好，问题只在**运行时桥路**：
  settings 桌宠卡按钮 → `src/module_pet_bridge.h` 桥 → pet 启动。
- 【实证】点击无日志 = 失败点在**极早处**：要么按钮 onClick 根本没触发，
  要么进入处理后首道守卫直接 `return`（早于任何日志语句）。
- 【假设 / 历史提交嫌疑，未逐条核对】两个历史提交与此链路相关：
  wave1/L7 加按钮的提交、`fix/settings-isolation` 改桥的提交——两者先后
  叠加后按钮与桥可能失配。

### 剩余假设

- 【假设】按钮回调未接线或被运行时条件分支吞掉（模块隔离守卫
  `scripts/check-module-isolation.sh` 静态断言四条桥函数真被调用且近期基线
  全绿——静态接线存在，断点更可能在运行时条件，此为**推断**、本会话未复跑守卫）。
- 【假设】桥函数与 pet 侧启动入口签名 / 注册不匹配，调用落到空实现。

### 建议下一步

1. 在按钮 onClick 入口与 `module_pet_bridge.h` 四条桥函数两端各加一行日志，
   复现一次点击，把断点钉到「onClick 前 / onClick 内 / 桥内 / pet 侧」四段之一。
2. 对照 wave1/L7 与 `fix/settings-isolation` 两个提交的 diff，核对按钮回调
   目标与桥函数现状是否一致。
3. 注意修复落点不得破坏模块隔离守卫（settings 不反依赖 module_pet）。

## S3 桌宠右击菜单失焦不自动关闭

### 背景

桌宠（独立无边框子窗）右击弹出的菜单，在点击其它窗口、桌宠窗失焦后**不自动
关闭**，残留在屏幕上。主窗的同款问题已修，子窗未闭环。

### 已有线索

- 【实证 / EUI-NEO commit 可查】`ca40ff2` 修过**主窗**失焦 → 全局重绘链，
  styledMenu click-away 失效的根因是失焦通知链被饿死；主窗场景已闭环。
- 【推断，未实证】桌宠是 `app::openWindow` 的**独立子窗**，很可能未接入
  同一条失焦通知链——修复只覆盖了主窗的注册路径。

### 剩余假设

- 【假设】子窗没有注册失焦回调，click-away 依赖的失焦事件到不了 styledMenu。
- 【假设】app 层只对主窗统一注册失焦 → 重绘，子窗不在注册集合里。

### 建议下一步

1. 读 `ca40ff2` 的实现，确认失焦注册机制覆盖哪些窗口（仅主窗还是全部窗口）。
2. 按覆盖范围选落点：**DevDesk 侧**（桌宠子窗自己注册失焦回调）或
   **EUI-NEO 侧**（app 层对所有窗口统一注册，反哺上游、走跨仓库 patch 流程）。
3. 修后验证：桌宠菜单打开 → 点击其它 app 窗口 → 菜单应随失焦关闭。

## S4 Dock 点击激活窗口间歇失效

### 背景

macOS 上应用已有可见窗口时，点击 Dock 图标**有时**不能把窗口带到前台激活；
重启或再次点击后恢复，呈间歇性。属 EUI-NEO 上游缺口，跨仓库流程，本批跳过。

### 已有线索

- 【实证 / GLFW 系已知缺口，非本会话代码级实证】GLFW 系应用未处理
  `NSApplicationDelegate` 的 `applicationShouldHandleReopen`——Dock 点击产生的
  reopen 事件没有对应处理，窗口不会被主动激活。
- 【实证 / 观察性】间歇性与以下状态相关，未逐项复现定位：当前 Space、
  窗口 hidden 状态、key 窗状态、`activate` 调用落点。
- 【实证 / 流程约束】修法属 EUI-NEO 上游（NSApplicationDelegate 在 GLFW
  平台层，DevDesk 够不到），须走跨仓库 patch 流程（隔离 agent 产 patch +
  非隔离线应用，见 DevDesk CLAUDE.md「反事故红线」）。

### 剩余假设

- 【假设】补 `applicationShouldHandleReopen` → 激活既有窗口即可闭环主因。
- 【假设】间歇残留另有二因：hidden 窗口未被 `activate` 覆盖，或 key 窗状态
  判断落点不对（只 `makeKeyAndOrderFront` 不 `activateApp`）。

### 建议下一步

1. EUI-NEO 侧实现 `applicationShouldHandleReopen`：遍历可见窗口
   `makeKeyAndOrderFront` + `activateApp`，含 hidden 窗口的 `orderFront`。
2. 复现时记录 Space / hidden / key 窗状态四元组，验证间歇因子。
3. 走跨仓库 patch 流程合入 EUI-NEO 本地 main，DevDesk 侧升级依赖 rev 复验。
