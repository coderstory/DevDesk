# 池 54 · 发布任务分支编辑入口 技术方案（F-54-1 ~ F-54-3）

> 来源：池 53 需求分析 F-30 取舍转正（`docs/superpowers/specs/2026-10-31-池53-发布任务详情发布态-需求分析.md` §六 F-30 行：「分支编辑 UI 已入池 need-54」）。
> 前置：池 53 双模式重构已落地（feat dded2fd8）。本单入口落在**新模式 IA**（编辑态单据式表单流 / Draft），不动旧布局。
> 级别 M；两段式：本卡停等核对后才进实现。

## 一、服务语义考古结论

- `ReleaseStore::updateTaskService(const TaskService&)`（`release_store.cpp:958`）：**整行覆盖写** service_name / service_kind / default_branch / branch / removed，id=0 或行不存在返回 ValidationError / NotFound。当前**零生产调用方**（仅 store 测试直接调），缺口确认属实。
- 字段语义：`defaultBranch` = 基础配置服务目录快照（建任务时拷入）；`branch` = 任务实单分支（release_dialogs.cpp:207 建任务时 `branch = defaultBranch` 预填，注释「执行页可改」——本单即兑现此注释）。合并分支步骤（StepKind::MergeBranch）与提交校验（`validateTask`：branch 为空 → 「服务「X」的分支未填写」，`release_logic.cpp:272`）消费的都是 `branch`。**编辑对象 = branch，仅此一字段**。
- 对账已存在，零新增：`applyContentRevocations`（`release_detail_ui.cpp:42-72`）已实现「branch 变更 + 合并分支已确认 → 自动撤回 doneAt + revoke 日志『服务分支已修改』」；`release_detail_ui.h:23-25` 契约注释明确「服务分支保存后（宿主置 state.dirty）重读对账」。**本单只补 UI 入口与保存路径，对账复用不重写**。
- 关键实现纪律（照 saveConfigEditor 既有契约）：**输入缓冲不得直改 `state.services`**——若 onChange 直改内存，保存后 reload 时 prev(内存)==DB，对账退化为空转，合并分支旧确认不会撤回（bug）。缓冲独立字段，落库成功后置 dirty，由 reload 统一进内存并触发对账。

## 二、IA 决策：编辑态字段区块（服务卡内 44px 表单行），非独立弹层

| 备选 | 取舍 |
|---|---|
| **A. 编辑态服务卡分支行升级为 44px 表单行（选定）** | 与前置单据流同语言：label「分支」定宽 kFormLabelW=96 + `components::input` 32px 高（release_detail_draw.cpp:358-373 同款绑定），常驻可填。发布态/归档态维持现状 12px 只读行（设计文档 §5.3 规格不变） |
| B. 独立小弹层 | 弃：新增一种弹层形态（全模块仅此一处用）、Esc/确认语义新增、编辑时看不到同环境其它服务分支上下文 |
| C. 12px 行点击展开输入 | 弃：可点击性弱（12px 灰字）、多一次交互，违背「编辑态=一次配齐的表单」立场 |

理由：①分支是合并分支步骤的直接输入域，就近展示、填完即走；②编辑态「填」语言 = 常驻输入（前置单号同款），不引入点击展开/弹层两种新交互形态；③行高 44 / label 96 / 输入框 32 / focus 边全部是设计文档 §5.2 已定稿规格的复用，零新视觉发明。**对 §5.3 的偏离声明**：§5.3「分支编辑不在本轮，只读展示」是在 F-30 取舍前提下的措辞；本单转正后编辑态该行改为表单行，发布/归档态规格不变。此项随本卡停等核对，若审计否决走 B 弹层。

## 四、失败路径（F-54-2）

| 场景 | 行为 |
|---|---|
| 分支名非法（含空格/控制字符） | 不落库，notice 错误「分支名不能包含空格或控制字符」，缓冲保留可改 |
| 分支名超长（>200 字符） | 不落库，notice「分支名过长（上限 200 字符）」，缓冲保留 |
| 空/纯空白 | **合法**（trim 后空 =「分支未填写」可标记态，由提交校验拦截提交而非拦截保存）；存空串 |
| 行已被并发移除/不存在 | `updateTaskService` NotFound → notice 原样错误信息，缓冲保留 |
| 写库失败（SQLite） | notice「保存分支失败：…」，缓冲保留（saveConfigEditor 同款，输入不丢） |
| 越权（Pending/Running/Done/Voided） | `applySaveBranch` 首行 `isEditMode` 守卫拒绝并 notice（沿用 toggleConfigSkip 措辞模式）；UI 层发布态根本不渲染输入框，逻辑层守卫为纵深防御（F-03 越权写路径拒） |
| 冲突 | 如实声明：`release_task_service` 无唯一约束，不存在唯一冲突路径；「并发改本行其他字段被旧快照覆盖」是整行覆盖写接口的既有语义（与 saveTask/updateTask 同惯例，详情页为单窗编辑域），本单不为其加增量更新接口（反过度设计） |

## 五、取舍（90% 裁剪）

- **不做完整 git-check-ref-format 校验**（`..`、`~`、`*`、`.lock` 等）：模块定位「记录台不是执行器」（设计文档 §1 永久非目标），分支串不驱动任何 git 操作，只拦会破版显示的空格/控制字符/超长。
- **不做「还原默认分支」按钮**：branch 建任务时已预填 defaultBranch，无此需求；defaultBranch 字段本轮不进 UI，updateTaskService 整行写时原样透传。
- **不做多缓冲**：单槽缓冲（branchEditServiceId），失焦先提交再切换，与前置输入同节奏。

## 七、POC 结论

不做 POC：无新技术——输入控件（components::input）、缓冲-提交模型（saveConfigEditor）、整行更新（updateTaskService）、对账（applyContentRevocations）四件全部是仓内既有且本单全部直接复用，唯一风险点（缓冲直改内存导致对账空转）已在 §一.4 静态推演排除并由 T6 锁定。

## 八、实现后回填（2026-11-01 实现段实测修正，审计对照用）

1. **§二 IA 决策表格的事实修正**：「发布/归档态维持 12px 只读行」是对池 53 IA 的误读——发布/归档走流程轨道（`release_detail_draw.cpp` drawEnvsSection 仅编辑态进入 + `if (publish || readOnly)` 路由），**分支值在发布/归档态本就无展示面**（轨道服务子标只有服务名）。实现为：分支行仅在编辑态渲染（表单行），draw 侧保留 `isEditMode` 守卫作 F-03 绘制点防御，死代码 else 分支已删除。发布态无分支展示是池 53 既有 IA，非本单缺口。
2. **编辑态标红语言**：旧 12px 行的「分支未填写 · 提交校验未通过」红字文案随行退役；新表单行 = label「分支」红字 + 行浅红底（`serviceBranchFlagged` 映射复用），精确缺失文案由校验清单弹层承载。信息不丢（弹层逐字列出），视觉语言对齐 StepRowView invalid 档。
3. **测试数字**：卡面 T1~T8 中 T3（trim）与 T4（空值合法）合并为一条用例实现，实际 7 条 `release_detail_branch_*` 用例，断言面与卡面 T1~T8 等价（trim/空值/校验联动全保留）。
4. **新增管道**：probe 增加 `--screenshot-publish <png>`（发布态中途落图，probe_harness.h ProbeArgs），4 张基准截图 = 2 档窗口 × 编辑/发布两态，归档 `evidence/20261101-pool54-dev/`。
