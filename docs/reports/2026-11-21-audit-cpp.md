## 3. P1 清单

### P1-01 `http_client.cpp` 在 C 回调里用 try/catch + std::stoi，违背「不抛异常」铁律
- **位置**：`src/platform/http_client.cpp:323-327`
  ```cpp
  try { code = std::stoi(codeStr); } catch (...) { code = 0; }
  ```
- **问题**：全仓唯一 `std::stoi` 使用。它位于 `streamHeaderCb`——**libcurl 的 C 回调函数**。若 `std::stoi` 抛出而异常未被此处捕获（例如栈展开期间析构再抛），异常会越过 C 边界，是 UB。同时 `AGENTS.md` §六与 `core/result.h:1` 明写"不抛 C++ 异常"。
- **自相矛盾的证据**：`module_about/about_module.cpp:57` 注释明写「不用 std::stoi：异常路径与本仓库『不抛异常』约定相悖」；`module_todo/todo_view_state.cpp:20` 注释写「手写十进制解析，项目铁律不碰异常，不用 std::stoll」。**团队有共识，此处是漏网**。
- **影响**：中。实践中状态行必为数字，异常概率低；但它建立了"铁律可以有例外"的先例，且是唯一样板。
- **修法**：换手写十进制解析（仓内已有两处范式可直接抄），约 10 行，零异常路径。

## 6. 进行中代码（need#356 半成品）单独评估

评估对象（现已由并发会话存入 `git stash@{0}`，工作树干净）：`src/platform/file_trash.{h,macos.mm,win.cpp,posix.cpp}`、`importer_macos` 扩表、`importer.h` 台账抽象、`wallpaper_service` 删除 API、`rotation::focusPath`、托盘 spec 扩参、`wallpaper_delete_bridge`。

3. **Windows 实现的三级取严**：`PerformOperations` HRESULT + `GetAnyOperationsAborted` + `PostDeleteItem` 逐项 hr，注释解释了"PerformOperations 返回 S_OK 不代表删成功"。这是照着 Microsoft 文档的坑写的，不是抄个 demo。
4. **COM 套间容忍 `RPC_E_CHANGED_MODE`**：照抄 `folder_picker_win.cpp` 的已验证逻辑，不做配对 Uninitialize。正确。
5. **macOS 不消费 `resultingItemURL`**：注释引用 Apple 文档"该 API 会改名"，且已实测（clue#340：改名形态是 `xxx.mp4 22-48-55-039.mp4`）。基于实测而非猜测。
6. **`ImportLedger` 与 `TombstoneLedger` 并列而非继承**：注释明写"语义相反（补墓碑即删台账行），混一个接口会让调用方误用"。抽象判断准确。

**需要关注的点（非缺陷，属设计权衡）**

- **`DeleteSink` 手写 COM 引用计数**（`file_trash_win.cpp:64-133`）：`refs_ = 1` 起手、`Release` 归零自删。正确，但这是唯一一处需要人工保证"创建后必 Release"的地方（`:183` 有 Release）。建议加一条注释说明"若 `CoCreateInstance` 失败仍要 Release sinkRef"——现在的代码顺序是对的（Release 在 if 外），但意图不显。
